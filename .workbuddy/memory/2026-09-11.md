## 开发 小清澈3.0.js（v3.0.0）—— 用户主动调教上下文

**产出**
- `小清澈3.0.js`（基线复制自 `小清澈2.3.js`，`EXT_NAME` 保持 `AiChat`）
- `小清澈3.0-调教机制说明.md`（功能文档）
- `test/teach-smoke-test.js`（32 项专项测试，全绿）
- `test/plugin-smoke-test.js` 改为可传参指定插件文件，用于跨版本回归

**核心机制**
用户发以「小清澈：」开头的消息 → 不触发 AI 调用，但以 **assistant 角色**写入历史，等于"用户替 AI 说出了本应由 AI 说出的话"，下次对话时 AI 会当作自己说过的话延续。

**关键实现决策**
1. **识别正则**：`/^\s*(?:\[CQ:at,[^\]]*\]\s*)?(?:小清澈|Claritas-小清澈)\s*[:：]+\s*([\s\S]*)$/i`
   兼容全/半角冒号、名字别名、大小写、全角空格、可选 @ 前缀、重复冒号。名字走 `teachNames` 配置，正则带缓存。
2. **判定顺序**：调教识别必须早于触发词逻辑，否则 `keywordPrefix` 被配成「小清澈：」时会误触发回复。
3. **因果顺序（最关键的坑）**：调教立即落盘，而普通消息要等 10~15s 防抖结算。若用户先发普通消息、后发调教，历史会因果颠倒。
   解法：历史条目带**单调递增序号 `_seq`**，缓冲结算时把更早的用户消息回插到调教条目之前。
   **踩坑记录**：最初用 `Date.now()` 做排序依据，同毫秒内两条消息时间戳相等导致判定失效（测试 S5 失败）。改用 `nextEventSeq()` 单调计数器后修复。教训：排序不可依赖墙钟。
4. **元数据防泄漏**：`buildMessages` 原本 `messages.push(history[i])` 直接透传，会把 `_seq`/`_teach` 带进 API 请求体。已改为只取 `role`/`content` 两个字段。
5. **权限**：私聊不限；群聊仅 `ctx.privilegeLevel >= 50`（40邀请者/50管理/60群主/100master）。来源 `seal.d.ts`。
6. **管理指令**：`.ai teach` / `.ai teach undo` / `.ai teach clear`，同样受权限约束。

**配置项**：`userTeachEnabled`(bool,默认 true)、`teachNames`(string)、`maxTeachChars`(int,1000)

**边界**：空内容忽略；图片 CQ 剥离（不调视觉 API）；不激活连续对话；不进 buffer（天然不独立触发）；受 `historyTurns` 裁剪。

**测试结果**：`test/teach-smoke-test.js` 32/32 PASS；`test/plugin-smoke-test.js 小清澈3.0.js` 图片白名单 5 场景无回归。

## pc-agent-demo 打通：QQNT 真实控件结构已逆向完成

用户用 `"D:\QQ.exe" --force-renderer-accessibility` 重启并登录 QQ 后，无障碍树完整暴露（586 节点）。

**实测出的 QQNT 结构（关键，与直觉相反）**
```
GroupControl 'chat-header ...' → ButtonControl '寂静挽歌' class='chat-header__contact-name'
                                    同级 TextControl '(9)' = 群人数（私聊无此段）
GroupControl class='group-chat'                        ← 群聊容器
  PaneControl '消息列表' class='ml-area ...'
    GroupControl class='... ml-root ...' id='ml-root'  ← 消息区根锚点
      GroupControl class='ml-list list'
        GroupControl class='ml-item' id='<消息ID>'      ← 消息条目
          message__timestamp / avatar-span / user-name / msg-content-container container--others
            message-content mix-message__inner          ← 正文
```

**三个反直觉结论**

2. **输入框不是 Edit/Document，是 GroupControl**（ProseMirror 富文本）
3. **方向信息就在 class 里**：`container--others` / `container--self`，不需要靠坐标猜

**意外收获（已写入代码）**
- `AutomationId` 就是消息 ID（18~19 位数字）→ 天然唯一稳定，去重问题彻底解决，不再需要内容指纹

  → 直接当「粘贴是否成功」的检测器，比等固定时长可靠
- 顶栏 `user-profile-card__nickname` 就是登录账号昵称 → 自动识别 `Claritas-小清澈`，不用手填配置

**性能实测**：全树遍历 586 节点 0.40s；按锚点有界 BFS 仅 0.04s。故设计为「锚点一次扫描后缓存（5s 或失效重扫）+ 每轮只读缓存 ml-list 的直接子节点」。

**新增命令**：`--peek [N]`（只读解析打印，验证读取层）、`--send TEXT`（真发，群聊默认拒绝，需 `--force`）。

## 修复用户实测反馈的三个问题（私聊 `光みつる` 上验证）

用户跑 `--peek` 后报三个问题，逐一处理：

### ① 双方消息都出现省略号 `…`
**假象，非数据丢失。** 是 `--peek` 打印时调了 `clip(content, 90)` 做了 UI 截断，被误读成抓取不全。
**修复**：`--peek` 改为完整打印正文（去掉 `clip`），并加提示行「末尾没有省略号就说明数据是完整的」。
验证：对方 131 字 / 我方 138 字正文完整落盘到 `peek-fixed.txt`。

### ② 私聊被误判成群聊（`群聊=True 群人数=0`）
**根因**：`group-chat` 这个 class 私有聊和群聊**都会挂**（QQNT 用它做通用容器），拿它当群聊标志必然误判。
**修复**：`is_group` 只认两个真信号 —— ①标题里的 `(人数)` 标记；②可见的群成员面板。且判定前必须过 `_visible()` 过滤（否则会命中原生 DOM 残留节点）。
验证：`--peek` 输出 `群聊=False 群人数=0`，正确。

### ③ 输入框输不进字 / 无法核实
**根因（本次最关键发现）**：**沙盒进程没有前台窗口权限**。后台进程调 `SetForegroundWindow` 静默失败（`last error 5 = ERROR_ACCESS_DENIED`），随后泄漏的 `SendKeys` 打到了当时的真实前台窗口（终端）—— 这才是当初"卡 6 分钟"的真凶。
**修复**：
- 新增 `force_foreground(hwnd)` 硬门禁：用 `GetForegroundWindow()` 复核，`AttachThreadInput` + `BringWindowToTop` + `SetForegroundWindow` + `SetFocus` 重试 5 次，**只有确认真的在前台才返回 True**。
- `type_text()` 在 `force_foreground` 失败时**直接中止并报错**，绝不外发按键。
- `send_text()` 主路径改用**发送按钮的 `InvokePattern.Invoke()`**（跨进程、无需前台、不产生按键）。读回校验 `editor_text()` 是否一致；仅在已确认前台时才用 `Enter` 兜底。
验证：`--input-test` 复现 3/3 —— 写入→读回一致→`send--disabled` 翻转→清空，全程未发任何消息。另用「表情按钮」做代理验证：`InvokePattern` 无需前台即可跨进程触发（面板打开后 Esc 关闭）。

**新增三大调试模式**：`--peek [N]`（只读解析）、`--input-test [TEXT]`（纯写入不发送）、`--send TEXT [--force]`。

**教训（已写入 `windows-uia-automation` skill）**：后台/沙盒进程做 UIA 自动化时，任何依赖前台的动作都必须先验证前台归属，否则按键会泄漏到别的窗口。

**仍未验证**：`--send` 的最后一下真实点击（由用户账号亲自执行）。

## 用户已验证端到端发送 + 新需求：解决「QQ 窗口被顶到最上层」

用户确认 `--send` 真实发出成功，**全链路闭环**。随后提出核心痛点：
本方案会把 QQ 窗口强制顶到最上层，妨碍其他工作。

### 根因定位（只读了代码就能定，因为瓶颈高度集中）

整条链路里**只有「写输入框」一步需要前台**，而且有**两处**提窗口：

| 位置 | 动作 | 后果 |
|---|---|---|
| `agent.py:force_foreground()` | `BringWindowToTop` + `SetForegroundWindow` | 主动拉到 Z 序顶部 + 抢焦点；最小化还会被 `SW_RESTORE` 拉起 |
| `agent.py:type_text()` 内 `editor.Click()` | 真实鼠标按下/抬起 | **二次提升**，还会挪走用户的鼠标光标 |

发送那一步早已免前台（`InvokePattern.Invoke()`）、读消息也免前台。绕不开的原因：
Chromium 的 `ValuePattern.SetValue` / `LegacyIAccessiblePattern.SetValue` 都被拒
（`UIA_E_ELEMENTNOTENABLED`）→ 只能退回 `SendKeys` 粘贴 → Windows 键盘只认前台窗口。

### 实测调研：QQ 端口与 CDP 可行性

- QQ 主进程（PID 14252）监听 `4003/4303/4312/5283/9211`，**`9211` 是它自己的 JWT 服务**（返回 `{"errCode":4001,...}`），**不是 CDP** —— 排查端口时别搞混。
- QQNT 是 Electron，社区（TzdInjectorNTQQ / LiteChii）确认支持 `--remote-debugging-port=9222`。
- 注意：本机 **PowerShell 工具输出为空**（疑似被沙盒静默拦截），但 `Bash` + `tasklist`/`netstat`/`curl` 正常，排查时改用 Bash。
- `wmic process get commandline` 在本环境返回空，拿不到命令行。

### 用户选定路线：先 C 兜底，再验证 A

**方案 C（已完成）——前台存档/还原**
- 新增模块级 `restore_foreground(prev_hwnd)`：复用 `AttachThreadInput` 组合拳把前台还给原窗口，用 `IsWindow` 兜住已关闭窗口，返回是否成功。
- `type_text()` 改为 `prev_fg = _fg_hwnd()` → `try/finally` 里 `_release_foreground(prev_fg)`。
- **去掉 `editor.Click()`**，改用纯 UIA `editor.SetFocus()`。
- 配置项 `uia.restore_foreground`（默认 `true`）可关。

**改造中自己引入又修掉的 🔴 阻塞级问题（重要教训）**
`type_text()` 归还焦点后，`input_test()` 里紧接着的 `clear_editor()` 还在用 `SendKeys`
—— 那会把 `Ctrl+A` / `Delete` 打进用户当时的窗口，**正是我们一直在防的数据丢失级风险**。
修法不是在调用点补丁，而是**把护栏下沉到 choke point**：`clear_editor()` 改成返回 `bool`，
入口自检 `is_foreground()`，不在前台一个键都不发。
**教训：一旦引入「用完即还焦点」，所有后续依赖前台的调用都必须重新抢一次前台。**

**方案 A 探针（`cdp_probe.py`，已写好并自测）**
- 三步：`--port` 探测 CDP → `--dom` 逐 target 找 QQ 输入框/消息列表 → `--type` 实测 `Input.insertText`。
- **安全承诺写进文件头**：永不点发送、永不按回车，最坏只在输入框留测试文字。
- 自测覆盖：①端口 9211「有响应但不是 CDP」②端口 9999「积极拒绝」③**用本地假 CDP 服务器验证 `Session` 的握手 / 事件交错跳过 / id 匹配 / 错误透传**（websockets 17.0.1 sync 客户端）。
- 未验证的只剩：QQ 的 ProseMirror 是否接受 `Input.insertText`（需用户重启 QQ 带参数后实测）。

### ECS 调研结论：技术可行，但不推荐把 QQ 放上去

- QQ Linux 版同为 Electron → **CDP 路线可原样移植**；无头需 `Xvfb + fluxbox + x11vnc/noVNC`，
  依赖含 `libasound2t64`(24.04) / `fonts-noto-cjk` / `dbus-x11`。
- **三个硬阻碍**：①Linux QQ **只有扫码登录**，无头必须先架 VNC 看二维码；
  ②服务器 IP 风控 —— NapCat issue #1728 大量实测「扫码后 2~3 小时被 `KickedOffline`」，
  降级到 NapCat 4.15.19 + Linux QQ 3.2.21 才稳 63+ 小时，**版本差异极大且随腾讯策略变**；
  ③NapCat 官方安全文档明确警告「避免同一 IP/设备同时登录 Bot 与常用账号」。
- **推荐架构**：QQ 客户端留在常开的 Windows（拓扑 B），ECS 只做 LLM 网关/历史/调度（拓扑 D）。
