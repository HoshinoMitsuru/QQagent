# 虚拟后台渲染与操作 QQ —— 可行性与技术路线调研

> 调研时间：2026-09-12
> 调研对象：`pc-agent-demo`（PC 端 QQ AI 代理，UIA 真人操作路线）
> 参考项目：`D:\Psyche\sealdice-core_1.6.1_windows_amd64\code\sealdice-core`
> 约束（用户给定）：虚拟的 QQ 进程仍是 **Windows 端**，**必须保留现有的「Windows 仿真人操作」**，不转协议

---

## 0. 一句话结论

**可行，而且不需要协议、不需要虚拟机、不需要改换技术路线。已全部实测通过（见 §6.4）。**

但需要纠正问题里的一个前提：**「虚拟的服务器进程」不能是 Windows 服务（Session 0）**——
服务与用户会话隔离，UIA 客户端在里面**看不到**用户会话的窗口，`SetForegroundWindow` 也永远失败。
正确的形态是**「常驻后台进程 + 独立 Windows 桌面」**：进程仍在用户会话内（托盘 / 自启），
但 QQ 被启动到一个**用户看不见的桌面**上。

一句话：
> 不是让 QQ「在后台假装渲染」，而是**给它一个自己的桌面，让它在那里当唯一的主角**。

### 0.1 实测之后需要修正的两条旧认知 ⚠️

这两条都是本项目的既有前提，本次实测证明**都错了**，而且改动量很小：

| # | 旧认知（写在代码里） | 实测结论 | 影响 |
|---|---|---|---|
| ① | 「写文本必须抢前台」<br>`agent.py:3713` / `force_foreground()` 整套建立在此 | **不需要前台。**真正的条件是「OS 焦点落在目标窗口的 `Chrome_RenderWidgetHostHWND` 上」。对后台的 QQ，只要 `AttachThreadInput` + `SetFocus(renderer 子窗口)` 就能写进去，**前台全程不变**（§6.5） | 「QQ 被强制置顶、阻塞用户工作」这个已知副作用**可以从根上删掉**；与是否选 R4 无关，现在就能拿 |
| ② | 「隐藏桌面上能抢到前台，只是抢的是那张桌面的前台」 | **非活动桌面上不存在前台窗口**：`SetForegroundWindow` 恒返回 0、`GetForegroundWindow()` 恒为 NULL。但**不需要抢** —— 那张桌面上只有它一个窗口，Chromium 上来就认为自己是 active，连 `SetFocus` 都不必调（§6.4） | R4 的卖点从「抢得到前台」改成「根本不弹、不进 Alt+Tab、不遮挡、不抢焦点」 |

> 这两条合起来的意思是：**「前台」这个变量从头到尾都是假变量。**
> 真正决定 `WM_CHAR` 能否落地的是 *renderer widget 有没有拿到 OS 焦点*（§6.5）。

## 1. 先把业务目标翻译成技术需求

### 1.1 你描述的问题链

| 环节 | 现状 | 痛点 |
|---|---|---|
| A 提供服务给 B | A 自备 QQ 账号，A 的机器上跑 QQ，A 的账号去加 B 的私人 QQ | ① 单账号可对接人数少；② 依赖特定账号；③ 风控风险集中在 A；④ 必须把 A 的 QQ（哪怕小号）暴露到公共环境 |

### 1.2 目标形态（我的理解，如有偏差请纠正）

```
用户 B 双击 qq-agent.exe
   │
   ├─ 后台常驻进程（托盘 + localhost WebUI，B 的真实桌面看不到任何窗口）
   │     │
   │     └─ 一个「虚拟后台桌面」
   │           └─ QQ.exe  ← 在这里**真实渲染**、**是前台**
   │                 └─ agent 用 UIA 读消息 / 切会话 / 粘贴 / 发送
   │
   └─ B 从浏览器打开控制台看状态、扫码登录、配置人格
```

**关键推论**：如果 QQ 账号是 **B 自己的**，那么
- A **不需要任何 QQ 账号** → 风控风险归零、隐私归零；
- 「单账号对接人数少」被 **「一台机器一个账号」** 天然水平扩展掉；
- A 交付的变成**纯软件**。

> ⚠️ 这一节是整份调研的地基。如果你其实想要的是「A 端一台机器跑 N 个 QQ 服务 N 个 B」，
> 那对应的是 **§5 的 R5（多用户会话）**，结论不同，请先告诉我。

### 1.3 拆成三个可独立验证的子问题

| # | 子问题 | 为什么必须单独验 |
|---|---|---|
| Q1 | QQ 在**用户看不见**的情况下，a11y 树还会更新吗？ | 不更新 → 读不到消息，一切免谈 |
| Q2 | 那个环境里，**「写文本」还要不要抢前台**？ | 这是当前唯一必须抢前台的一步（§3.2） |
| Q3 | 抢前台如果**只发生在自己的桌面里**，还算「占用真实前台」吗？ | 不算 → 用户完全无感 |

三个问题的答案组合，决定最终路线。

**结论：参考项目走的是「协议端进程」，不是「虚拟 UI 渲染」。它没有解决你要解决的问题。**

### 2.2 它怎么做到「后台无窗口」

`tray_windows.go` 里全部的相关代码只有两行：

### 2.3 所以它的无头能力从哪来

|  | sealdice-core | 本项目 |
|---|---|---|

| 被风控识别为异常客户端的风险 | **有**（协议指纹 / 行为特征） | **低**（就是一个正常登录的 QQ 在正常收发） |
| 支持「B 端自己跑」吗 | 可以，但 B 仍需交出账号信息给协议端 | 可以，B 用自己的客户端登录 |

> **这就是你的项目相对它的技术优势**，也是你要求「保留仿真人操作」的正当理由。
> 但反过来：**「虚拟后台里做 UI 渲染」这件事，它给不了任何答案，必须自己实测。**

## 3. 已有的实测事实（不重做，直接引用）

### 3.1 免前台能力边界（`技术核实文档.md §4.2`）

| 操作 | 需要前台吗 | 依据 |
|---|---|---|
| 读消息 / 读标题 / 读签名 | **不需要**（最小化也能读） | `archive/probe_minimized.py` |
| 切换会话 | **不需要** | `archive/probe_switch_nofg.py`（`InvokePattern`） |
| 点发送按钮 | **不需要** | 同上 |
| **把文字写进输入框** | ⚠️ **需要** | 剪贴板 + `Ctrl+V` 这条路 |

### 3.2 唯一的硬约束

```
写文本 = 清空输入框（Ctrl+A / Delete）+ 写剪贴板 + Ctrl+V
       ↑ 这三步都是「按键」，按键只送到当前前台窗口
```

`agent.py` 里的守卫（`force_foreground` / `type_text` / `clear_editor`）之所以这么严格，
是因为按键**漏进别的窗口**会造成真实破坏（实测过 `{Enter}` 打进终端把半截命令提交了）。

**所以「写文本免前台」是整个后台化命题的核心。** 只有两条出路：
1. 让「前台」这个身份**只存在于自己的桌面里** → 路线 R4；
2. 绕开按键，用 CDP `Input.insertText` → 路线 R1/R3 的补强（`archive/cdp_probe.py` 已探通）。

## 4. 核心机制：为什么「窗口看不见」会让 QQ 停摆

这是理解所有路线为什么成/为什么败的关键，也是本项目之前实测结论的**理论解释**。

### 4.1 Chromium 的 Windows 原生遮挡计算（Native Window Occlusion）

Chromium 官方文档与博客（2021-12）明确：

> Windows 系统没有直接的办法知道一个窗口是否被完全盖住，所以 Chrome **自己算**：
> 按 z 序枚举桌面上所有窗口，逐个从"未遮挡区域"里减掉它们的矩形，
> 减完如果自己一点没剩 → **判定为 occluded**。
>
> **一旦被判定 occluded，Chromium 就把前台标签当后台标签处理：渲染停止、JS 节流。**

### 4.2 哪些情况会被判为 occluded（官方列出的）

| 情况 | 判定 | 对应本项目的实测现象 |
|---|---|---|
| 窗口被**最小化** | occluded | ✅ `probe_minimized.py`：最小化后 `Invoke` 静默失效 |
| 窗口被**其它窗口完全盖住** | occluded | ✅ README 里的"QQ 被完全遮挡 → 读不到新消息" |
| 窗口在**另一个 Windows 虚拟桌面**上（Win+Tab 那个） | occluded | 未测，但机制上必然 |
| 窗口**被移到屏幕外** | 按后台处理 | —— |
| **屏幕被锁** | 全部 occluded | ✅ 部署手册 §4 里"锁屏后异常"的来源 |

> 💡 **一条重要推论（可直接排除一个看起来最省事的方案）**：
> **「把 QQ 窗口移到屏幕外坐标，比如 `(-32000, -32000)`」是不可行的** ——
> 它正是官方文档点名会被当成后台处理的情况。不要在这条路上花时间。

### 4.3 反过来的推论：什么情况**不会**被节流

只要让 Chromium **算不出「我被盖住了」**，它就会正常渲染。有两条实现路径：

| 思路 | 手段 | 对应路线 |
|---|---|---|
| **关掉这套计算** | `--disable-features=CalculateNativeWinOcclusion` 等启动参数 | R1 |
| **让窗口真的没人盖它** | 单独给一个显示器（R3）或单独给一个桌面（R4） | R3 / R4 |

## 5. 可行路线矩阵

> 判定口径：**R = 能读消息且能发消息且用户无感** 为合格。

| # | 路线 | 原理 | 隔离掉了什么 | 渲染 | 写文本 | 依赖 | 判定 |
|---|---|---|---|---|---|---|---|
| **R0** | 现状：前台模式 | 直接操作用户桌面上的 QQ | 无 | ✅ | **只需 `SetFocus(renderer)`，不需要抢前台**（§6.5 已实测） | 无 | ⚠️ 副作用已可大幅缩小 |
| **R1** | **抗节流启动参数** | 给 QQ 加 4 个 Chromium 开关，关掉遮挡计算 | 遮挡 / 最小化 | ✅ 参数已进 renderer | ✅（§6.5） | 改 QQ 启动参数 | ⚠️ 归因未完成；R4 出现后优先级下降 |
| **R2** | 窗口移到屏幕外 | 改窗口坐标 | —— | ❌ | —— | 无 | ❌ **已排除**（§4.2） |
| **R3** | **虚拟显示器** | 装虚拟显示驱动，把 QQ 放上去（无遮挡） | 遮挡 / 视口 | ✅ | ✅ | 装驱动（需管理员） | ❌ **用户已否决**（D3=b）；且焦点仍是共享的 |
| **R4** | **独立 Windows 桌面** | `CreateDesktop` + `lpDesktop` 把 QQ 启动到隐藏桌面 | **遮挡 + 视口 + 打扰面（弹窗/Alt+Tab/焦点）** | ✅ **已实测：不节流** | ✅ **已实测：免前台、含中文** | **仅 API，零外部依赖** | ⭐ **推荐主线** |
| **R5** | 第二用户会话（FUS） | 建第二个本地用户，在其中跑 QQ，切回主用户 | 上列全部 + 剪贴板 + 账号 | ✅ | ✅ | 建用户 + 切会话 | ✅ 适合 A 端多账号，不适合 B 端 |
| **R6** | VM / Windows Sandbox | 整机隔离 | 全部 | ✅ | ✅ | 重；Sandbox 每次重置 | ✅ 你的 A 端已在用 |

### 5.1 为什么 R4 是最优解

`CreateDesktop` 是 Windows 原生 API（`user32.dll`），**不需要安装任何东西**：

```c
HDESK hDesk = CreateDesktopW(L"QQAgentHidden", NULL, NULL, 0, GENERIC_ALL, NULL);
// 启动 QQ 时指定这个桌面
STARTUPINFO si = {0};
si.cb = sizeof(si);
si.lpDesktop = L"QQAgentHidden";
CreateProcessW(qq_exe, cmdline, ..., &si, &pi);
```

它实际解决了什么（**实测之后重写，与最初的推测有出入**）：

| 最初的说法 | 实测结论 |
|---|---|
| 窗口在用户桌面上不可见 → 不弹窗、不进 Alt+Tab | ✅ **成立** |
| a11y 树不会冻结（算不出遮挡 → 不节流） | ✅ **成立，且比预期更强**：跑 20 秒 `raf` 从 100 涨到 1504、`fps=180`、`visibilityState` 全程 `visible` —— 不只是"没被判定遮挡"，而是**满帧在跑** |
| 「前台是 per-desktop 的 → 在隐藏桌面上 `SetForegroundWindow` 合法成功」 | ❌ **不成立**。非活动桌面上**根本没有前台窗口**：`SetForegroundWindow` 恒返回 0，`GetForegroundWindow()` 恒为 NULL |
| 因此"写文本不抢用户前台" | ✅ **成立，但机理不同**：那张桌面上只有它一个窗口，Chromium 上来就认为自己是 active；且 `WM_CHAR` 通路**连焦点都不需要自己调**（§6.4.3 `none` 档就成功） |

**修正后的价值主张（这才是 R4 真正卖掉的东西）**：

| 卖掉的东西 | 卖不掉的东西 |
|---|---|
| 不弹窗、不闪烁、不进 Alt+Tab | 「不抢前台就能写文本」—— **普通模式下也能做到**（§6.5） |
| 不被任何窗口遮挡 → 渲染不打折 | 「不受最小化影响」—— 最小化本来就不影响读取（`probe_minimized.py` 已实测） |
| 用户完全感知不到后台在跑 | —— |
| 截图能力可取出画面（二维码登录可用） | —— |

**代价与风险（实测之后更新）**：

| 项 | 说明 |
|---|---|
| **agent 也必须跑在那个桌面上** ✅ 已确认 | UIA 的 `GetRootElement()` 返回**当前线程所在桌面**的根。跨桌面看不到对方的窗口 → 需要一个 launcher：在用户桌面创建隐藏桌面 → 在里面启动宿主进程。实测两条都成立（窗口找到、树完整） |
| ~~剪贴板是共享的、需要"用完恢复"~~ | **作废**。写文本不走剪贴板（§7.3） |
| ~~渲染是否真正常【待实测】~~ | **已实测正常**，见上表第 2 行 |
| **没有 explorer shell** | 那个桌面上没有任务栏 / 开始菜单 → 尚未实测影响面。QQ 的托盘图标会消失（可能影响"最小化到托盘"行为） |
| **首次部署需扫码登录** ⚠️ 新增 | 隐藏桌面上的 QQ 必须用**独立 profile**（否则和用户自己的 QQ 抢同一份 `%APPDATA%\QQ`）。独立 profile = 未登录 = **首次要扫码**。好消息：截图能力已实测可用（§6.4.2 ⑤），二维码能取出来给用户看；要设计「截图 → 轮询登录态 → 继续」的流程 |
| **两套 QQ 并存的资源面** ⚠️ 新增 | B 端用户平时自己的 QQ 也在跑。多一个 QQ 实例的内存占用与"用主号还是小号"的选择，见 §11 D4 |
| **桌面堆配额** | 每个桌面占 desktop heap（默认约 48 MB 级别），创建几个没问题，不该无限制创建 |

### 5.2 R3（虚拟显示器）的位置

R3 的成熟度反而更高——有现成产品：

| 项 | 情况 |
|---|---|
| 项目 | `VirtualDrivers/Virtual-Display-Driver`（原 itsmikethetech 版），**2026 年仍在维护** |
| 签名 | **已代码签名（SignPath.io），无需开启测试签名模式** |
| 安装 | `winget install --id VirtualDrivers.Virtual-Display-Driver -e` |
| 效果 | 系统多一个虚拟显示器，把 QQ 窗口放上去 → 无遮挡 → 正常渲染 |
| 缺点 | ① 需管理员权限装驱动；② 有黑屏风险（官方建议先卸 GPU 驱动再装）；③ **焦点仍是共享的**，写文本照样抢用户前台 |
| 定位 | **R1 的加固版**（当启动参数失效时用），或 **R4 的兜底**（万一隐藏桌面不渲染） |

### 5.3 关于「多开 QQ」

你在问题里提到「单 QQ 账号可有效对接的人员数量较低」。
`--user-data-dir=<独立目录>` 可以让 Electron 多开多个 QQ 实例、登录不同账号。

但这条**不解决你真正的目标**（摆脱对 A 账号的依赖），只是把 1 个 A 账号变成 N 个 A 账号；
且本项目 `技术核实文档.md §8.3` 已把「多账号/多开」列为**刻意不做（与合规边界冲突）**。
→ 如果目标是 A 端规模化，正确的解法是 **R5（多用户会话）**，不是多开。

### 6.4.1 为什么被测目标是「一个测试页」而不是 QQ

QQ 在隐藏桌面上只能用**独立 profile** 启动（单实例锁按 profile 区分；用同一份 `%APPDATA%\QQ`
会和用户自己的 QQ 抢同一份 2.27 GB 的数据），于是它是个**未登录实例** ——
没有聊天页、没有输入框，`WM_CHAR` 无处可落，测了也白测。

而驱动侧的 `WM_CHAR → 焦点 renderer 宿主` 是**引擎级代码**，QQ（Electron）走的是同一段。
所以用裸 Chromium 当被测目标，结论可以平移，而且换来三个好处：

- 不需要登录
- 不动用户的任何 profile（临时 `--user-data-dir`）
- **状态可以三方读回** —— 页面把 `rAF 帧数 / visibilityState / activeElement / input 事件数 /
  两个编辑框的内容` 全部写进 `document.title`，于是「隐藏桌面上到底发生了什么」有了自述证据

> 这不是「退而求其次」。它比直接测 QQ 更严格：QQ 的 ProseMirror 只给只读 `TextPattern`，
> 而测试页的 `<textarea>` 会投影出 `ValuePattern`，**能独立核对**。

### 6.4.2 六项实测结果

| # | 观察项 | 判据（怎么算通过） | 结果 |
|---|---|---|---|
| ① | 窗口在隐藏桌面上正常可见 | `EnumWindows` 返回它；`IsWindowVisible=True`、`IsIconic=False`、`cloaked=0` | ✅ |
| ② | **renderer 没有被节流** | 标题里 `raf` 计数**持续增长**（100 → 1504）、`fps=180`、`vis=visible` 全程不变 | ✅ |
| ③ | 无障碍树完整 | 199 节点、有 `EditControl`、能读到输入框的 `ValuePattern` | ✅ |
| ④ | **免前台写入成功（含中文）** | 标题 `inp=28 kb=42 te="R4probe…"`；无障碍树 `EditControl ValuePattern='R4probe…'`；**截图肉眼可见** | ✅ |
| ⑤ | 窗口画面可抓取 | `PrintWindow(..., PW_RENDERFULLCONTENT)` 返回 1；1800×1230；颜色 217 种；非黑占比 1.0 | ✅ |
| ⑥ | **用户桌面前台完全不受影响** | 6 次运行前后都是 `Chrome_WidgetWin_1 / 'WorkBuddy' hwnd=462022` | ✅ |

②④⑤ 三项缺一不可：② 决定「能不能读到**实时**新消息」，④ 决定「能不能发出去」，
⑤ 决定「**首次部署时用户能不能扫二维码登录**」—— 真实部署里 QQ 是全新 profile（未登录），
二维码画在用户看不见的桌面上，抓不到图就是一堵死墙。

### 6.4.3 激活方案消融：**最小必需集合 = 空**

因为「写文本要不要抢前台」是整件事的关键，所以专门做了一次消融（`--focus-plan`）。
每档**独立进程、全新窗口** —— Chromium 的焦点状态有粘性，连跑会让消融失效。

| 档位 | AttachThreadInput | SetActiveWindow | SetFocus(top) | SetFocus(renderer) | 写入 |
|---|---|---|---|---|---|
| `none` | – | – | – | – | ✅ |
| `renderer_only` | – | – | – | ✅ | ✅ |
| `no_attach` | – | ✅ | ✅ | ✅ | ✅ |
| `no_renderer_focus` | ✅ | ✅ | ✅ | – | ✅ |
| `full` | ✅ | ✅ | ✅ | ✅ | ✅ |

**五档全通，包括什么都不做的 `none`。** 原因是隐藏桌面上只有它一个窗口，
Windows 在窗口显示时就把焦点给了它，Chromium 于是从一开始就认为自己是 active。

> ⚠️ 但**这个结论不能外推到用户桌面**。见 §6.5：在用户桌面上，
> 同一个「什么都不做」会被 Chromium 丢弃。两张桌面的差异正是 R4 的价值所在。

同时记下一件事：`SetForegroundWindow` 在隐藏桌面上 **恒返回 0**、`GetForegroundWindow()` **恒为 NULL**。
「非活动桌面没有前台窗口」得到实证 —— 这修正了 §5.1 里「前台是 per-desktop 概念，所以在隐藏桌面上抢得到」的那半句。

### 6.5 实验 D（新增，意外收获）：**免前台写文本**在本机就已可用 ✅

探针：`archive/probe_no_foreground_write.py`（对**用户桌面上处于后台的真实 QQ**做写入）

做这个实验的起因：既然隐藏桌面上连 `SetFocus` 都不需要，那就要问一句 ——
**这个「免前台」是隐藏桌面独有的，还是窗口消息本身就不需要前台？**
两者结论不同、动作不同，不能推测。

### 结果

实验条件：QQ（hwnd=9896602）在后台，前台是 `Windows 默认锁屏界面`（hwnd=132326），输入框为空。

| 阶段 | 做了什么 | 投递 | 读回 `editor_text()` | 写入 | 前台被改 |
|---|---|---|---|---|---|
| `plain` | **什么都不碰**，直接发 `WM_CHAR` | 7/7 返回 1 | `'按住 Win + Alt，使用语音输入文字'`（占位符，即空） | ❌ | 否 ✅ |
| `a11yfocus` | `AttachThreadInput` + `SetFocus(renderer 子窗口)` | 11/11 返回 1 | `'NFa11yfocus'` | ✅ | **否 ✅** |

### 结论

> **`WM_CHAR` 能否落地，取决于「OS 焦点是否落在目标窗口的 `Chrome_RenderWidgetHostHWND` 上」。**
> 与「窗口是不是前台」无关。

- 用户桌面上后台的 QQ：焦点在别人身上 → 消息被 Chromium 静默丢弃（**返回值照样是 1**，
  这是最容易误导人的地方 —— 只看返回值会得出「发了但对方没反应」的错误归因）
- 补上 `AttachThreadInput`（跨线程 `SetFocus` 的前提）+ `SetFocus(renderer 子窗口)` → 成功
- **全程没有调用 `SetForegroundWindow` / `BringWindowToTop`，前台一次都没变**

### 这对项目的直接意义（与是否选 R4 无关）

`agent.py` 里那套 `force_foreground()`（`AttachThreadInput` + `BringWindowToTop` + `SetForegroundWindow`）
在「写文本」这条路径上是**多余的**。改成「attach + `SetFocus(renderer 子窗口)`」后：

| | 现在 | 改后 |
|---|---|---|
| 用户前台 | 被 QQ 顶掉，用户手头的事被打断 | **完全不动** |
| 副作用面 | 抢整个桌面的前台 + 焦点 | 只改 QQ 内部一个子窗口的焦点 |
| 「按键漏进终端」那个老坑 | 存在 | 一并消失 |

> ⚠️ 待验证的副作用：`SetFocus` 到 QQ 的 renderer 之后，**用户敲的键会不会漏进 QQ**？
> 静态推理上不会（用户自己的前台窗口有自己的输入队列），但本次实验期间机器处于**锁屏**状态，
> 无法判断。**这是改用这条通路前必须先补测的一项。**

原计划：写文本走「剪贴板 + Ctrl+V」，所以剪贴板是 per-window-station 共享的，得「用完恢复」。

**实测之后这条整个作废**：隐藏桌面上 `GetForegroundWindow()` 恒为 NULL，
剪贴板 + Ctrl+V 那条路（需要窗口是前台）在那张桌面上**根本走不通**；
而窗口消息（`WM_CHAR`）实测又完全够用（§6.4.2 ④）。

| 原定动作 | 现状 |
|---|---|
| 剪贴板存取、用完恢复 | **不需要做** |
| 唯一的用户环境副作用 | **消失** —— 不改剪贴板、不抢前台 |

### 7.4 顺带解决的一个老问题

`技术核实文档.md §8.1-①`：**QQ 刚启动停在起始页、没有会话 → 所有锚点不存在 → 常驻起不来，需人工点一个会话。**

把这个"必须人工操作"的约束消掉。

### 7.5 新增：首次部署的扫码登录流程 ⚠️

这是实测之后**新暴露**出来的必答题，最初调研时没看见。

**为什么会有这一步**：隐藏桌面上的 QQ 必须用独立 profile
（用同一份 `%APPDATA%\QQ` 会和用户自己的 QQ 抢同一份数据），独立 profile 就是未登录。
所以首次运行必须让用户**扫一次码**，而二维码画在用户看不见的桌面上。

**好消息**：取图这条路已实测可用（§6.4.2 ⑤）。

```
P0  用户双击 exe → 建隐藏桌面 → 启动 QQ（独立 profile，带无障碍参数）
P1  轮询 QQ 窗口的无障碍树，判断是不是停在登录页
P2  是 → PrintWindow(hwnd, PW_RENDERFULLCONTENT) → 存 PNG → WebUI 里显示
P3  轮询：登录成功后锚点（会话列表 / 输入框）会出现 → 关掉二维码界面
P4  把 profile 路径记进 app-settings.json，下次免扫码
```

| 要点 | 说明 |
|---|---|
| 轮询频率 | 二维码约 2 分钟过期，建议 1.5~2 s 抓一次；**不要更密** —— 每次 `PrintWindow` 都要 DWM 出一张全幅位图，太密会跟 QQ 本身抢 GPU |
| 判断"登录成功"的判据 | **不能只看进程还在**。用锚点出现与否（`ml-list` / `ExEditor-qq-msg-editor`），这才是可靠的 |
| 失败态 | 二维码过期 / 需要手机确认 / 风控验证 —— 都要有对应文案，不能只显示一张静止的图 |
| 备选（更省事，但需要用户配合一次） | 在用户自己的桌面上登录同一个独立 profile，登录完再切到隐藏桌面启动。**代价**：要短暂占用用户前台一次 |

## 8. 「虚拟的服务器进程」这个说法需要修正的地方

| 你的表述 | 能不能做 | 说明 |
|---|---|---|
| 虚拟的**服务器进程**（字面 = Windows 服务 / Session 0） | ❌ **不能** | Session 0 与用户会话隔离：UIA 客户端在服务里**看不到**用户会话的窗口；也没有交互式桌面 → `SetForegroundWindow` 永久失败。`跨终端部署与操作手册.md §4` 的表格已经实测印证了这一点 |
| **常驻后台进程**（托盘 / 开机自启，仍在用户会话内） | ✅ **应该这样做** | 这正是 sealdice 的形态，也是你项目现在的形态 |
| 在虚拟后台内**要求进行 UI 渲染** | ✅ **可以** | R3 或 R4 |
| 根据 UI 渲染**实现对 QQ 的操作** | ✅ **可以** | 现有 UIA 代码基本不用改（这是 R4 最大的好处） |
| **无须占用真实前台和焦点** | ✅ **可以，已实测** | R4 做到的方式**不是**"在自己的桌面上抢前台"（非活动桌面上压根没有前台，抢不到），而是**那张桌面上只有它一个窗口，它上来就是 active**；外加 `WM_CHAR` 通路不需要前台（§6.5） |
| **保留 Windows 仿真人操作以规避风控** | ✅ **完全保留** | 见 §9 |

## 9. 风控视角：这么做会不会削弱「仿真人」优势

**不会，而且这是本路线最值得强调的一点。**

| 风控关注的特征 | R4 方案的表现 |
|---|---|
| 网络行为 | **零改动**。QQ 客户端的网络收发路径完全不变 |
| 登录方式 | **零改动**。仍是官方客户端、官方登录（扫码） |
| 客户端完整性 | **零改动**。不 hook、不注入、不 patch |
| 消息发送路径 | 仍是"文本真的进了输入框 → 真的点了发送按钮" |
| 启动参数 | 多了 4 个 Chromium 开关 + 1 个无障碍开关。**这些只影响渲染进程的调度策略与无障碍树暴露，不改变任何网络或协议行为** |
| 窗口位置 | QQ 自己不知道自己在哪个桌面上，"窗口在隐藏桌面"对它等价于"窗口没被任何东西挡住" |

**对比参照**：真正的风控敏感面是协议逆向（sealdice 的 Lagrange / Milky 路线）——
自建 socket 会话、自定义协议指纹。你刻意避开的那条路，才是风险高的那条。

> 一句话：**你花的代价是"窗口放哪"，不是"怎么跟腾讯说话"。**
