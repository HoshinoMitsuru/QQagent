### F3 的三条设计决策（备忘）
1. **armed 绝不进 schema**：给模型的工具定义里没有 armed 参数——模型永远不能
   给自己解锁。armed 只由人工确认路径传入 dispatch。测试断言全量 schema 序列化里
   不含 "armed"。attach 面未确认时 dispatch 返回
   `{"ok": False, "code": "E-CU-004", "needs_confirmation": True, "text": ...}`，
   且**原语根本没被调用**（测试断言桩无 send_text 调用记录）。
2. **dispatch 永不抛异常**：ExecutorError 原样转信封（码不变）、意外异常兜底
   E-CU-001——Brain 的主循环（F4）不被一次工具调用炸掉。
3. **宽松参数矫正**：模型把整数写成 "7"、布尔写成 "true" 时自动矫正，
   矫正不了才报 E-CU-007（信封里附 schema 帮模型自纠）。未知参数直接拒绝
   （allowed 白名单），防模型夹带私货。

### 五个坑（都写进 README 与对应函数的注释了）
1. **在宿主进程里碰 UIA 会把它弄坏**：一次失败的 `Invoke` → `COMError -2147220992`，
   之后每次 UIA 调用都 `-2147220991 事件无法调用任何订户`，**永不自愈**。
   同一张桌面、同一个 QQ，**换新进程读一切正常**。
   → 登录/探测一律派**一次性子进程**；宿主第一次碰 UIA 必须是 agent 那一次。
2. **登录完停在会话列表页**：`ml-list` / `ExEditor-qq-msg-editor` / `send-msg`
   只存在于聊天页（实测树里各 0 个），于是 `dom_exposed()` False 报 `E-QQ-004` ——
   按它去重启 QQ 是白折腾。→ 新增 `E-QQ-008`，判据是「`recent-contact-list` 在不在」。
3. **「点第一条会话」不够**：列表第一条是 `QQ游戏中心`（**公众号 webview**），
   点开有 `chat-header__contact-name` 但**没有聊天区**。
   → 用客观判据**迭代候选**：点一条 → 看 `ml-list` → 不在就换下一条。
4. **`GetWindowTextLengthW` 会挂死状态流**：读标题要**给窗口所属线程发消息**，
   对方不处理就无限期等。控制台 `/api/state` 每 2s 被轮询，于是整个状态流冻住，
   界面显示「心跳停更/连不上」。且在 `EnumWindows` 回调里发消息会**静默拿空**
   （实测 45 个窗口全空标题）。→ **两阶段**（先枚举不发消息，再读标题）
   + `SendMessageTimeoutW(SMTO_ABORTIFHUNG)` + 默认只读 QQ 类名窗口的标题。
5. **`_desktop_locked()` 在非活动桌面上必然为真**（那里本来就没有前台窗口）
   → 每次常驻启动都误报 `E-ENV-006 锁屏`。→ 判据改序：先问「输入桌面能不能打开」。

### 其他踩到的小坑
- `--args --once` 类问题再现：`--chat=mychat` 要写成 `=` 形式（值以 `-` 开头时会被当选项）。
- **venv 的 `python.exe` 在 Windows 上会再起一个子进程**，所以 `desktop.spawn` 返回的 pid
  ≠ 宿主自报的 pid。心跳里的 pid 才是真的（宿主写 `os.getpid()`）。
- 看门（心跳/停止）线程**必须在启动期就起来**，否则等 QQ/等登录那几十秒里界面显示
  「心跳停更」（误判卡死），按停止也没人接。
- 界面白屏级错误：**JS 字符串用双引号跨了行** → 已加 `node --check` + 元素 id / 图标名的
  引用完整性闸门（`test_ui.py §15`），因为后端接口测试全绿也照样白屏。
- `error_codes` 里 `rc` 字段名：宿主进程的返回码**不等于** agent 的返回码，
  启动期失败也走它 —— 原名 `agent_rc` 会把「启动就失败」读成「正常返回 0」。

## 追加：修「走隐藏桌面仍然报 E-FG-001 抢前台失败」

一般原则：**cmd 的块内文本里，`(` `)` `>` `<` `|` `&` 都要转义**。

## 追加：重试上限（用户要求「重复失败就取消，不超过 5 次」）

用户诉求：那条卡住的消息一直在日志里空转，兜底要收口 —— 连续失败就取消、不再重试，
日志打出来就够，不要超过 5 次。**并强调「最大程度谨慎，避免引入新错误」。**

### 这件事的本质：让代码做到配置早就承诺的事
`queue.max_attempts`（默认 3，界面里叫「发送重试上限」，范围 1~10）的说明一直是
「发送前复核对不上就重排，**连续失败这么多次后放弃并撤单**」——
而 `serve_queue` 里那段代码被刻意改成了「永不撤单」（注释写得很清楚，是为 VM 场景的
「消息永不丢」）。于是**配置承诺了、代码没做**。现在把上限接回去。

### 改动（都沿用既有机制，不新造轮子）
- `serve_queue` 失败分支加一道 `_should_give_up(item)` → 到上限走 `_give_up(item)`。
- 新增 `Agent._send_retry_cap()`（读 `queue.max_attempts`）、`_should_give_up()`、`_give_up()`。
- `_give_up`：`self.qq._abort_cleanup(...)` 清草稿 → `queue.drop(scope, aborted=True)`
  → `_save_pending()` → 报 **`E-SEND-017`**（新码）→ **再单独 log 一行完整原文**
  （`report` 的 ctx 是转义成一行的，长文本在那儿不好读也不好复制）。
- `E-SEND-013` 措辞改掉「不放弃」；阈值从「第 5 次 / 每 20 次」改成
  **「上限前一次」**（无上限世界里的阈值在有上限之后没意义了）。
- `_note_stuck` 的阈值解释、`E-SEND-017` 的 fixes 里写明「上限可在界面改 1~10」。

### 语义（实测确认，别想当然）
**失败次数是累计且存盘的**（`to_state`/`from_state` 都带 `fail_count`）：
一次实验把 `fail_count=5` 写进 pending 文件再加载，恢复出来就是 5，
且 `_should_give_up` 立刻为真 → **恢复后第一次尝试就撤单**。
（我一度以为重启会清零 —— 实测推翻了。这其实是更彻底的「不超过 N 次」。）

### 过程中被自己的闸门抓到三个真问题
1. **`agent.py` 里 `self._abort_cleanup(...)` 调错了对象** —— 它是 `QQWindow` 的方法。
   运行时 AttributeError 被兜底吞成一条 WARN：撤单照常、**草稿永远没清掉**。
   → 改成 `self.qq._abort_cleanup(...)`；测试也从 `ag.qq` 打桩。
   ⚠️ 教训：**兜底 except 会把真 bug 降级成一条不起眼的告警**，正是本项目最怕的形态。
2. **`(... .get("max_attempts") or 3)` 把 0 吃成了 3**（0 是假值）。
   配置是**人可以手改的文件**，这种写法一被踩到就是「我明明写了却没用」。
   → 改成显式 `raw is None` 判断；测试里加了「上限写 0 也至少留 1 次」。
3. **`app/host.py` 用了 `BUS` 但没 import** —— `clear_stop_sentinels` 里那句
   `BUS.emit(...)` 会在**真的清掉哨兵时**抛 NameError（pyflakes 抓到；
   之前一直没触发是因为 cleared 恰好为空）。→ 补 `from .logbus import BUS`。

### 一处**没做**的事（故意的）
没有把 `fail_count` 改成「本轮内连续」：累计语义对用户的诉求（不超过 N 次）是符合的，
而且实现更简单、不动存盘格式。代价是「重启不让它重新来过」—— 这符合预期，已写进注释。

### 闸门
离线 254 + 122 + 126 + 31 + 43 + 68 全 0 失败（`test_text_port.py §11` 新增 13 项；
`test_errors.py` 的 E-SEND-013 阈值断言按新契约重写）。
真机：`阿离` 那条恢复后一次尝试即撤单，日志留下
