### 同步到 R4 的手法（更新：不是 `patch -p2 -l`）

- `git diff -- pc-agent-demo-vm` → `sed s#pc-agent-demo-vm/#pc-agent-demo-r4/#` → 先把 R4
  目标文件**整份 LF 化**再 `patch -p1`（逐字节确定匹配，不赌 `-l`/`--fuzz` 对 CR 的容忍度）
  → 打完还原 CRLF。

### 顺手抓到的一个**真回归**（不是我引入的，是 09-28 收拢时漏的）

`reset_to_defaults()` 把 `config.json` **整份换成内置默认值** → 密钥也被换掉了，
而界面文案承诺「API Key 不受影响」。收拢之前 key 住在 secrets 里，所以那句话当时是对的；
收拢之后它变成了**假承诺**：用户点一次「恢复默认」就得重新粘一遍 Key。

- 修法：先把盘上现有的 `llm.api_key` 捞出来（掩码则丢弃），写回模板再落盘；
  返回值加 `kept_api_key` 供界面/测试对账。
- **同时踩到一个陷阱**：`agent_defaults()` 返回的是**模块级 `_LOCAL_DEFAULTS` 本体**，
  老代码 `template = dict(agent_defaults())` 只是**浅拷贝** —— 只要在 template 上做
  `_set_path`，就会把用户的密钥写进那份全局默认值（下一个新装用户直接带着别人的 Key）。
  所以必须 `copy.deepcopy`。测试里加了一条断言专门盯这件事
  （`SET.agent_defaults()["llm"]["api_key"] == ""`）。

## 收尾五：`--dry-run` 漏发修复（真事故，已修 + 回归）

用户跑 R4 的隐藏桌面常驻，选了「只读运行」，结果日志里既有一堆 `DRY`
**也有两条真的 `SEND`**（一条发到群、一条发到私聊），于是问「这不对吧」。

### 诊断

不是配置问题，是 `dry_run` 的守卫**只盖了一半**：

| 入口 | 谁把消息送进队列 | dry_run 拦得住吗 |
| --- | --- | --- |
| 常驻读取（当前打开的会话） | `step()` → 防抖 → `_flush()` | ✅ 拦住（写进上下文就 return） |
| **发现（列表里别的会话冒未读红点）** | `discover()` → 占位入队 | ❌ **完全没查** |
| 对话内指令回执 | `_queue_ack` | ✅ 拦住 |

而 `deliver()` 最后那道模式闸只认 `self.no_send`，不看 `self.dry_run`。
于是发现路径一路「入队 → prepare 调模型 → deliver 真发」。
三棵树（vm/r4/cu）的 guard 位置一一对应，洞是同一个。

证据链（`pc-agent-demo-r4/dist/logs/hostd.log`）：
① 该文件整份从 `[15:56:46] HOST 宿主进程启动 pid=33020` 起，界面侧同一时刻写着
`进入回复主循环（dry_run=True no_send=False）` → 同一个进程，从第一秒就是只读；
② `[15:57:21] INFO 写入路径 = wmchar（…）` —— 这行只在真把文字写进输入框时才打；
③ 两条 SEND 后面都没有「彩排模式…本条不会真的发出」（那是 `--no-send` 才有的行）。

### 修法（入口挡 + 出口兜）

1. **主修**：`discover()` 里在 `ensure_pending` **之前**加 `if self.dry_run:` →
   记一条 `DRY`（本来会发现什么），不入队、不调模型、不发送；顺手让指纹照样落盘
   （`set_fp` 只改内存，不 save 就会每 2 秒重复报同一条）。
2. **兜底**：`deliver()` 的模式闸改成 `if self.no_send or self.dry_run:`，
   并且**分两种措辞** —— `no_send` 是「彩排，本该走到这里」，
   `dry_run` 走到这里是**不该发生的事**，记为 `WARN` 并点名「请查 discover() 与新加的通路」。
   将来再添新路径漏了守卫，日志会立刻显形，而不是又静默发一次。
3. **回归**：`test_discovery.py` 新增 `test_dry_run_never_sends`（+8 条，43 → 51）：
   造「别的会话冒未读红点」，断言不入队 / 不调模型 / 一条没发；
   再直接调 `deliver()` 验证兜底。为让兜底失败时能**干净判 FAIL**（而不是 TypeError 崩），
   顺手把假 QQ 的 `send_text` 签名补齐 `resume=`，与真实 `QQWindow` 对齐。

**验证回归真的能抓 bug**：临时把两处守卫摘掉再跑 → 正好两条 FAIL
（`n=2 scopes=['private:1001','group:2002']` / `sent=[('阿离', …)]`），无崩溃；随后还原并核对 md5 未变。

### 顺带解决的事

- **残留宿主**：用户以为进程都关了，其实 `qq-agent.exe` pid 33020（隐藏桌面宿主）还活着，
  一边占着 exe 导致默认变体打包失败（WorkBuddy 的 safe-delete shim 报错），
  一边在隐藏桌面上继续切会话。用项目自己的哨兵 `dist/state/hostd.stop` 让它**优雅退出**
  （2 秒内 rc=0，两个哨兵自清，16:10 之后 0 条 SEND）。
  ⚠️ 线索：关界面不等于停宿主。
- **VM 的 `build.bat` 一直是坏的**：图标那步调的是根目录 `build_icon.py`，
  而它早已移进 `archive/` → 必然 `goto :fail`。R4/CU 早修过，VM 漏了。
  按同样的写法补齐（路径改对 + 产出缺图标就报错），VM 这才打得出来。
- 文档同步：三份 README 的 `--dry-run` 说明写清「只读 vs 彩排」的分工与这次修的洞；
  `test_discovery.py` 计数 43 → 51（README 两处 + 文件清单一处）。

## 收尾六：运行中换模式（同日晚些时候）

**用户提的问题**（原话大意）：r4 方案设成只读之后，「只有关闭再重启才能转入会正常

### 根因：三处界面层疏漏（后端并不缺能力）

1. **隐藏桌面卡在「运行中」时没有任何换模式的入口** —— 只画了「停止（连宿主一起）」
   和「抓图」。而「停止」按 2026-09-26 的语义会把那张桌面上的 QQ 一起收走、虚拟桌面
   销毁，于是「切一次模式」= 停 + 冷启 QQ + 等窗口 + 认登录，几十秒到一两分钟。
2. **「常驻运行」卡的「重启常驻」并不改模式**：它调 `/api/agent/restart` 且不带
   `dry_run`，服务端「没给就沿用」→ 点了还是原来那个模式。按钮叫「重启」，人理所当然
   以为能顺手换模式 —— 这种落差本身就是疏漏。
3. **界面上根本看不到当前模式**：`dry_run` / `no_send` / `agent_enabled` 一直写在宿主的
   心跳里，但 `daemon_status()` 从没往外露，于是卡片上只有一句「运行中」，看不出它
   到底发不发消息。（2026-10-09 早先那次「界面说只读、日志里却发了」的误判就长在这片
   空白上。）

### 改法

- `app/host.py`：
  - `daemon_status()` 暴露 `dry_run` / `no_send` / `agent_enabled` / `profile`。
  - 新增 `mode_text(st)`：四态措辞的唯一来源（会真发 / 只读 / 彩排 / 只摆着）。
  - 新增 `HOSTD_LAUNCH = state/hostd-launch.json`：`start_daemon()` 记下**入参**，
    `restart_daemon()` 照着回放（桌面名/profile/qq_exe/chat/stop-qq-on-exit/有无回复循环）。
    记录缺失时退回用心跳能还原的那部分，并把没还原到的项放进 `degraded` 报出来 ——
    不假装完美还原（那几项留空等于回落默认值，可能换了 profile，最该让人看见）。
  - `stop_daemon(keep_qq=True)`：切模式专用，跳过 `_cleanup_after_stop()`，QQ 与桌面
    原样留着 → 新宿主在 `_ensure_qq()` 里凭 `--user-data-dir` 直接认领到它，
    十几秒回到回复循环、免扫码。**默认行为不变**（用户点「停止」= 这一套不要了）。
  - `restart_daemon(dry_run=?, no_send=?)`：只换模式重启宿主；模式没变就什么都不做
    （并如实回报 `unchanged`，不假装切过）；宿主没在跑 / `--no-agent` 起的都明说原因，
    不做任何动作。
  - CLI：`daemon restart --mode keep|send|dry|rehearse`；`daemon status` 加印「模式」一行。
- `app/server.py`：新增 `POST /api/host/restart`。**目标模式必须显式给**（缺了报
  `E-WEB-004`）—— 不学 `/api/agent/restart` 的静默沿用，那条语义正是「以为切过去了，
  其实没有」的温床。
- `app/web/index.html`：隐藏桌面卡加「模式」一格（未运行时标「上次模式」）+ 运行中的
  显式切换按钮 + 一句「切回去只要十几秒、QQ 不动」的提示；常驻运行卡同样加切换按钮；
  顺手**修掉停止确认框里的一句假话**（原文说「QQ 默认会留着」，而 `stop_daemon()`
  默认就是杀 QQ + 销毁桌面）。
- `agent.py`（三棵树同构）：`serve_queue()` 开头加 `if self.dry_run: return False`。
  只读**连队列都不消费** —— 否则「正常 → 只读」这一次切换必然撞上的遗留项会先被
  `prepare()` 调一次模型（违背只读「不调模型」的承诺），再被 `deliver()` 的兜底当
  「已处理」收下并随即被 `drop` 掉：那条回复**永久没了**。而本项目对「已生成但没发出去」

这种「两遍都说得通」的语义上。重启没有歧义：新模式配一个干净的队列。

### 产物核验：一次「假通过」和它掩盖的真事故（同日晚些时候）

重打完之后本来该收工，但我按「用证据而不是时间戳说明产物是新的」这条标准又核了一遍 ——
**结果查出 VM 的两个变体根本没重打**，而且**第一版核验脚本自己先假通过了一轮**。

**核验脚本的第一版错在哪**：我拿 `# ⚠️ 只读模式：**队列一个字都别碰**` 当特征串。
那是**注释**，而注释**根本不进字节码**（code object 里没有注释）→ 新旧产物在这条
判据上**都报 0**，于是「8 个产物全 BAD」被我误判成「needle 取错了」，实际是
「判据无效」。教训：**注释和 docstring 都不能当字节码锚点**（docstring 进 `co_consts`，
但它只能证明「有」，不能证明「改没改」）。

**改法：逐函数比对字节码**（脚本 `.workbuddy/Claw/tmp/verify_exe_guard.py` 第二版）——
把 exe 里抠出的模块 `marshal.loads` 成 code object，再把**当前源码**用同一个解释器
`compile()` 一遍，两边按 qualname 摊平成 `{函数 -> co_code}` 对表；
静态文件 `app/web/index.html` 也整份逐字节比。`co_code` 不含文件名、不含行号表
（3.11+ 行号在 `co_linetable` 里），所以「完全一致」= exe 里跑的就是当前源码。
**这套判据一上就点名了 `Agent.serve_queue` 有差异**。

**真事故**：`vm/qq-agent-noadmin.exe` 与 `vm/qq-agent-console.exe` 还是 16:17 那批旧货
（`index.html` 75256 字节 vs 源码 77243，三个新按钮一个都没有）。
根因在批量重打脚本 `rebuild_all.ps1`：PowerShell 里
`if ((Invoke-Build ...) -eq 0) { Move-Item ... }` —— 函数除了 `return $rc` 还
`Write-Output` 了别的字符串，于是 `(Invoke-Build ...)` 返回的是**数组**；
`@("line","rc=0",0) -eq 0` 得到 `@(0)`，而 **`if (@(0))` 在 PowerShell 里是 $false**
（单元素数组按元素转 bool，0 → false）→ 改名的 `Move-Item` 一次都没执行，
dist 里躺的还是上一批同名文件。同理 `-ne 0` 对数组恒为真 → 脚本里 `$fail` 永远置 1，
那次「r4 默认版构建失败」也是同一个假象。
→ **改法：不靠脚本里的 if，构建完手动 `Move-Item`，三步各自核对时间戳 + 大小。**

修正后 8 个产物全部 `[OK] … 与源码逐函数一致`；VM 的 `test_exe` 也拿新产物重跑 45/45。

顺带把构建日志收进 `.gitignore`（`pc-agent-demo*/build-last.log`、`/build-all.log`）——
它们是每次打包都重写的完整 stdout，几十 KB，没有入库价值，但会一直在
`git status` 里晃，容易被 `git add -A` 顺手带进去。

## 同日续：进程内保活（r4 + vm），以及一个新错误码 `E-ENV-009`

用户定的边界：**只做进程内保活，不动这台机器的任何配置**。
所以 `keep_awake()` 里刻意**不**做 powercfg / 注册表 / 组策略那三样，
并把「它压不住什么」写在注释和 `EXE使用说明.md` 里：

- 压得住：空闲触发的关屏 / 锁屏 / 睡眠 / 关显示器（都是同一个「系统空闲计时器」）。
- **压不住**：手按 `Win+L`、笔记本合盖、组策略或安全软件强制的锁屏，以及**已经锁上的**。
  最后这条要反复说：解锁要凭据、且必须在 Winlogon 安全桌面上输入，
  **没有任何受支持的办法能让程序替用户做这件事** —— 只能一开始就别让它锁。

落地位置：`run_forever` 里**两道附着检查之后**才申请（启动期就失败的话进程马上就退，
没必要那时候占着系统的电源请求）。牌挂在当前线程上，**进程退出系统自动收回**，
所以刻意**不写** `off()` —— 有归还时机的写法反而更危险（把最要命的收尾那几秒交出去）。

顺带补的 `E-ENV-009 无法申请「保持唤醒」`：失败路径原先是一句裸 `log("WARN", …"失败"…)`，
它会踩到 `test_errors.t11_no_code_escape`（那条守卫要求「说了失败就得给码」）。
改成 `report("E-ENV-009", …)` —— 不是为了躲测试，而是因为**带码与否在功能上毫无区别，
区别只在出事时用户查不查得到怎么办**。同时在 `test_discovery` 里加了一条断言把它钉住：
打桩 `ctypes.WinDLL` 抛 `OSError(5)`，断言 `_LAST_CODE["code"] == "E-ENV-009"`
（`report()` 在节流之前就写 `_LAST_CODE`，所以被抑制也不影响）。

⚠️ 以后跑 `test_ui.py` 要当心：它会 `POST /api/admin/harden` **真改本机电源/屏保设置**，
跟「不要越界动本机配置」直接冲突 —— 这轮因此没跑它。
