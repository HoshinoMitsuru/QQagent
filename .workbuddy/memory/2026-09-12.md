## 00:0x–00:2x · 错误体系：一个码只对应一个根因

### 起点

用户要求：「确保所有可能出现的问题都有完善的对应报错反馈，避免报错混淆，帮助精准定位」。

排查后发现，真正的混淆源不是「报错太少」，而是**一句话覆盖多个根因**。
最典型的一句在 `run_forever` 里：

```
找不到 QQ 窗口。请确认 QQ 已启动，且带 --force-renderer-accessibility 参数。
```

它同时压在三个根因上，而处理动作完全不同：

| 真实根因 | 正确动作 | 按那句话去做的后果 |
|---|---|---|
| QQ 没启动 | 启动 QQ | 无损失 |
| QQ 在跑但窗口缩在托盘/最小化 | 把窗口显示出来 | **白重启一次，正在输入的文字会丢** |
| 窗口可见但无障碍没生效 | 完全退出后带参重启 | 白折腾 |

报错混淆的代价是**把人引向错误的修复动作**，比没有报错更坏。

### 本轮抓到的真问题（都是检查项自己抓出来的）

1. **`resolve_api_key` 依赖当前工作目录**（最值钱的一条）。原写法：
   ```python
   if path and not os.path.isabs(path) and not os.path.isfile(path):
       path = abs_here(path)
   ```
   「CWD 下刚好存在同名文件」时会优先用 CWD 那个 → 从项目目录启动读到项目里的密钥，
   从别处启动读到别的（或读不到）。表现为「同样配置换个目录结果就不一样」。
   改成相对路径一律按数据目录解析。
2. **8 处「说了失败但没给码」**的降级报错（上下文损坏/落盘失败、清理草稿、OCR、刷新指纹、扫会话列表、收尾三步）。
3. **`check_accessibility` 提前返回时漏了 `uia` 字段** → 界面和报告里看不到「UIA 线程初始化了没」，
   而那恰是排查「读不到界面」时最该先看的一行。
4. **诊断结果里 `ok` 与 `healthy` 混用一个字段** → 界面会把「体检发现 3 个问题」显示成「接口调用失败」，
   恰好丢掉最有价值的信息。拆成两个字段。
5. 3 条过于笼统的 `fixes`（写成了解释而不是动作）。

### 两条防回归检查（会随代码增长自动生效）

1. **源码扫描**：不允许再出现「讲了失败但没给码」的报错
   （匹配 `log("ERR"|"WARN", "…失败/找不到/无法…")` 且同处无 `E-XXX-000`）。
2. **目录自检**：编号格式、域前缀、必填字段、以及每条 `fixes` 是否有**可执行的抓手**
   （界面元素名 / 路径 / 命令 / 明确动词）。写成「这是正常现象」会被判不合格。

### 错误抑制的动机（值得记住）

常驻循环每 ~0.8s 一轮，持续性故障（QQ 最小化、锁屏、切不过去）会以**每秒一条**重复，
几分钟几万行 —— 第一现场被埋掉，界面日志面板也没法看。
`Throttle` 窗口内只输出一次完整诊断，过期后输出「已抑制 N 次」+ 完整块。
