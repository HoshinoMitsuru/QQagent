# QQAgent 控制台 · 使用说明（R4 独立桌面托管版）

> 面向：希望「双击就能用」的人。
> 目标：**你只需要打开一次 QQ 并登录**，其余全部在界面里点。

---

## 0.0 先读这一节：R4 和之前的版本不一样

这是 **V2（R4 独立桌面托管版）**。它多了一条路线：
**把 QQ 启动到一张你看不见的桌面上**，于是它不占屏幕、不会误关，
而且在那张桌面上「前台」是它自己独占的 —— 发消息不需要抢你的前台、
也不会把按键漏进别的程序。

界面上的 **「隐藏桌面（独立 profile）」** 卡片就是这条路线的总开关。
它与上面那张「常驻运行」卡片（旧路线：在自己的桌面上跑、需要抢前台）**互斥**，
一次只能开一个。

### ⚠️ 两张卡操作的是**不同的号**，别点错

界面上下相邻的两张卡，看起来都是「让 AI 开始回复」，但**操作对象完全不同**：

| 卡片 | 它操作哪个 QQ | 会不会打扰你 |
|---|---|---|
| **隐藏桌面（独立 profile）** | 隐藏桌面上那个**用独立 profile 的号**（你要的小号） | 不会。那张桌面上没有你的窗口 |
| **常驻运行（操作你桌面上的 QQ）** | **你自己桌面上正在用的那个 QQ**（= 你的主号） | 会。发送期间抢一次前台，键盘输入可能被打断 |

**这两张卡互斥**，一次只能开一张。

> 这条警告是踩出来的：有人在 R4 版 exe 上点了「常驻运行 → 开始常驻」，
> 于是程序去操作他桌面上登录着的**主号**，并且**真的往一个群里发了一条 AI 回复**。
> 当时界面上没有任何一处告诉他「你要操作的是哪个号」。
> 现在：卡片标题写明了操作对象，「开始常驻」会弹二次确认（显示上次读到的会话、
> 回复范围、以及本次用哪份配置），点下去之前你有机会看清。

### ⚠️ exe 的数据目录是**它自己所在的那一层**

双击 `dist\qq-agent.exe` → 数据目录就是 `dist\`，配置从 `dist\config.json` 读。
它**不是**源码目录里那份配置。第一次运行会在 exe 旁边生成一份**全新默认配置**
（日志里会写「这是首次运行，已生成 config.json」）。

这条也踩过：有人以为用的是之前调好的配置，实际跑的是默认值
（而默认 `私聊限定 = 关`，也就是**群聊也会回**）。

### 它多出两个前提，务必先看

| 前提 | 为什么 | 怎么办 |
|---|---|---|
| **那台机器得先登录过这个 QQ 号** | 隐藏桌面上没人能扫码（二维码画在你看不见的地方） | 第一次用：命令行跑 `python -m app.host start --visible`，QQ 窗口会出现在你眼前，登录完关掉它即可（登录态留在独立 profile 里）。**之后**宿主都会自动点掉登录页上的「登录」按钮，全程不需要你 |
| **那个号得至少有一个真实会话** | 回复循环要找**输入框和消息区**，而这两个锚点只存在于聊天页；QQ 登录完停在会话列表页 | 让它有一个普通联系人即可。宿主会自己按顺序点开会话列表里的条目，直到找到能用的那个（列表第一条可能是公众号，点开是个网页、没有聊天区） |

### 三个 exe 变体

| 文件 | 什么时候用它 |
|---|---|
| `qq-agent.exe` | **默认交付版**。双击会弹 UAC 申请管理员权限 |
| `qq-agent-noadmin.exe` | **不想看到 UAC 弹窗**、或要从非提升的终端里启动它（自动化测试只能用它，见下） |
| `qq-agent-console.exe` | 排错用：保留控制台窗口，能看到实时输出 |

> **为什么「非提升的进程启动不了默认版」**：默认版带着
> `requireAdministrator` 清单，而 `CreateProcess`（`subprocess` 用的就是它）
> **不会弹 UAC** —— 权限不够时它直接返回 `WinError 740`。
> 所以自动化测试要测 `qq-agent-noadmin.exe`：两者代码完全一样，只差那份清单。

### 一个不影响使用的小差异：打包版的图是 BMP

面板上「抓一张现在的画面」用的是 `PrintWindow`，抓图优先存 PNG，
**但这个版本没有 Pillow**（打包时刻意排除了，省体积），所以存成了 BMP
（约 2.5 MB）。浏览器照样能显示，面板上也会把真实文件名写出来。
源码模式下（装了 Pillow）存的是 PNG（约 55 KB）—— 两者只是体积差别。

### 构建 exe

```bat
build.bat              :: 默认交付版 -> dist\qq-agent.exe
build.bat nadmin       :: 免 UAC 变体 -> dist\qq-agent-noadmin.exe
build.bat console      :: 控制台变体 -> dist\qq-agent-console.exe
build.bat dir          :: 目录版（启动快，交付物是一个文件夹）
```

构建产物名由开关自动决定，不会再互相覆盖。脚本自己找 Python（优先本地
`.venv`，其次 PATH），缺依赖时会提示装到哪。

### 打包产物的验收

```bat
python test_exe.py dist\qq-agent-noadmin.exe
```

它测的是**真的 exe**：拷到干净的临时目录里像用户那样跑起来，再用 HTTP 打它的接口。
冻结后才会暴露的那两类问题（状态写到临时解压目录导致重启就丢、
隐式导入漏掉导致某个功能一点就 `ModuleNotFoundError`）**只有这一步能发现**。

## 0. 一页速览

```
1. 把 qq-agent.exe 拷到虚拟机上任意**可写**目录（例如 D:\QQAgent\）
2. 双击它 → 弹 UAC → 点「是」
3. 浏览器自动打开控制台（托盘里会出现图标）
4. 按界面上的顺序点：① 定位 QQ → ② 启动 QQ → ③ 体检 → ④ 填 API Key → ⑤ 开始常驻
```

需要你做的只有两件事：**把 QQ 打开并登录**、**在界面里填一次 API Key**。
其余（找 QQ、带正确参数重启、等待就绪、启动常驻、看日志）都在界面里。

## 1. 为什么是「一个 exe + 一个网页」

原来这套东西要你开终端敲一串命令：

```powershell
cd D:\Psyche\Sealdice-AIChat\pc-agent-demo
$env:Path = "...\venv\Scripts;$env:Path"
python -X utf8 agent.py --peek 10
python -X utf8 agent.py --input-test
python -X utf8 agent.py --send "测试"
python -X utf8 agent.py
```

现在这些命令**没有消失，而是变成了界面上的按钮**。这一点是刻意的：命令行还在、
还能用、还是同一份代码（见 §6），出问题时你可以照旧手工跑一遍对比。
界面只是把「顺序 + 参数 + 校验」固化了，不替你做决定。

## 2. 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| 系统 | Windows 10 / 11（64 位） | 依赖 UIAutomation，仅 Windows |
| 权限 | 管理员 | 自启注册、VM 加固、结束 QQ 进程需要它 |
| QQ | QQNT（新版 Electron 版） | 老版 QQ 的控件结构不同，本项目未适配 |
| 网络 | 能访问你的模型接口 | 内置默认是 DeepSeek 官方地址 |
| 依赖 | **不需要装 Python** | 解释器和全部库都打进了 exe |

> **不要放到 `C:\Program Files`**。那里不可写，程序会退而把数据放到
> `%LOCALAPPDATA%\QQAgent\`。想便携使用（整个目录拷来拷去），就放可写目录。

## 3. 界面上的五个步骤

### ① 定位 QQ 程序

点「重新查找」。查找顺序：手动指定 → 注册表 → 常见安装目录 → 各盘根目录。

> 本机的 QQ 在 `D:\QQ.exe` —— **盘根、非标准路径**，前三种都找不到，靠第四种兜住。
> 如果你的 QQ 更奇怪，在「运行环境」里直接填完整路径。

### ② 启动 QQ

「启动 QQ」只在 QQ **完全没在跑**的时候可用。它会带上
`--force-renderer-accessibility` 参数启动 —— **没有这个参数，UIA 树是空壳，
读不到任何消息**。

> 登录必须你自己来。程序不碰登录、不碰验证码、不碰任何账号凭据。

### ③ 界面可读（无障碍树体检）

点「体检」。这一步判断的是「agent 到底能不能看见 QQ 的界面」，判据是
**能不能读到会话列表和消息列表**，而不是去猜命令行参数。

> 为什么不看命令行：启动参数**只在 QQ 主进程首次启动时生效**。QQ 已经在跑的时候
> 再执行一次带参数的命令，它只会把已有窗口唤到前台，参数根本不应用。
> 查命令行会告诉你「参数都在」，而实际什么都读不到 —— 我们只认读得到东西。

**如果体检失败**，点「重启 QQ 到可读状态」。它会完全退出 QQ（含托盘进程）再带参数拉起。
登录态保留、一般不用重新扫码，但**正在输入的文字会丢** —— 所以这个按钮有二次确认。

### ④ 填参数

「参数配置」共 7 组：

| 分组 | 你至少要动的地方 |
|---|---|
| **模型接入** | **API Key（必填）**；接口地址、模型名按需改 |
| 对话行为 | 是否回群聊、非文本消息怎么处理、回复字数上限 |
| 节奏与聚合 | 对方连发消息时合并成一次调用 |
| **对话内指令** | 在 QQ 里用 `.ai reset` / `.ai help` 控制它（见 8.7） |
| 风控与排队 | 每分钟最多回几条 —— **决定能同时服务几个会话** |
| 多会话发现 | 扫会话列表找新消息，这是多会话能力的核心开关 |
| 前台与稳定性 | 用完是否归还前台、消息方向判定、OCR 兜底 |

下面还有一组「运行环境」：QQ 路径、监听地址与端口、CDP 开关、开机自动启动等。

> **API Key 只写进 `secrets.local.json`，不会写进 `config.json`。**
> 后者是「可以公开」的那个文件，前者已被 `.gitignore` 排除。
> 界面回显的 Key 永远是掩码，接口也不会把明文吐回来（有测试守着这条）。

### ⑤ 开始常驻

**建议先点「只读运行（不发送）」观察几分钟**：日志里能看到它读到了谁的消息、
方向对不对、昵称对不对，但一条都不会发出去。确认无误后再切到会真的发送的常驻。

停止用「停止常驻」。它不会硬杀进程：先放一个停止哨兵文件，给主循环最多 12 秒
**把队列里已经生成好的回复发完**，再退出。这一步不能省 —— 丢了就是
「对方明明发了消息，我们却永远不回」。

## 4. 从只读到真发：验证顺序

界面的「验证与试运行」里，建议按这个顺序走。会碰 QQ 的任务必须串行执行，
常驻运行时它们会被自动禁用（避免两个进程抢同一个输入框）。

| 顺序 | 按钮 | 会不会发消息 | 期望看到什么 |
|---|---|---|---|
| 1 | 自检 | 否 | 密钥 OK、模型几百毫秒返回 |
| 2 | 只读诊断 | 否 | `群聊=False`、`【我方】/【对方】`与界面左右一致 |
| 3 | 会话列表体检 | 否 | 能看到 agent 眼里的会话列表与未读徽标 |
| 4 | 输入框写入测试 | **否** | 写入生效 → 回读一致 → 清空成功 |
| 5 | 彩排：完整读一轮 | 否 | 读消息 → 生成回复 → 三重身份复核 |
| 6 | 彩排：写到输入框为止 | **否** | 和常驻同一条链路，只在最后一击前收手 |
| 7 | **真发一条** | **是** | QQ 里真的出现这条消息 |

第 4 步失败通常意味着中文进不了输入框（剪贴板链路问题）；
第 5、6 步失败通常意味着身份复核没过 —— 那说明**检测机制在正常工作**，
日志里会写明是标题对不上还是 QQ 号对不上。

## 5. 虚拟机路线：这台机器的加固

你选择 VM 路线是为了彻底绕开两件事：**抢你屏幕**和**锁屏不可用**。界面上的
「虚拟机加固与无人值守」就是为此准备的。

### 5.1 禁用自动锁屏

一键执行这些改动（全部可逆，都能在「电源和睡眠」里手动改回）：

| 项 | 改什么 |
|---|---|
| 显示器自动关闭 | `powercfg /change monitor-timeout-ac 0` |
| 硬盘自动关闭 | `powercfg /change disk-timeout-ac 0` |
| 系统自动睡眠 | `powercfg /change standby-timeout-ac 0` |
| 系统自动休眠 | `powercfg /change hibernate-timeout-ac 0` |
| 电池下显示器/睡眠 | 同上，`-dc` 版本 |
| 屏保 | 注册表 `ScreenSaveActive=0` |
| 锁屏界面 | 组策略 `NoLockScreen=1`（**仅专业版生效**，家庭版会失败但不影响其它项） |

> 为什么非做不可：**桌面锁屏时，UIA 的读取还能工作，但点击、按键、Invoke 会全部失败。**
> 表现是日志里不断重复「发现 → 入队 → 复核失败 → 重排」，看起来像程序坏了。
>
> ⚠️ 宿主机锁屏**不影响** guest（虚拟机照常运行），但**宿主机睡眠/休眠会挂起虚拟机**。

### 5.2 开机自动启动

注册一个登录计划任务，带「最高权限」标记。用计划任务而不是启动文件夹，
是因为**以最高权限运行的登录任务不会弹 UAC** —— 无人值守的虚拟机上这是决定性的。

### 5.3 建议的部署方式

```
虚拟机（Windows，常开）
├─ qq-agent.exe          管理员启动，托盘常驻
├─ QQ（带无障碍参数）      你手动登录一次，之后一直是登录态
└─ 控制台网页             从宿主机浏览器也能开（见 §7）

宿主机
└─ 完全不参与，也就完全不受打扰
```

## 6. 命令行还留着（出问题时的退路）

同一个 exe 就是 agent 本体，把参数透传进去即可 —— **界面里跑的和命令行里跑的是同一份代码**：

```powershell
qq-agent.exe --run-agent --selftest
qq-agent.exe --run-agent --peek 10
qq-agent.exe --run-agent --input-test
qq-agent.exe --run-agent --send "测试"
qq-agent.exe --run-agent                  # 常驻（不开界面）
qq-agent.exe --run-qqid  --enroll-all     # 给所有会话取号
qq-agent.exe --version
qq-agent.exe --help
```

其它开关：

| 开关 | 作用 |
|---|---|
| `--safe` | 安全启动：不自动拉起 QQ、不建托盘、不开浏览器。只起 HTTP 服务 |
| `--run-agent X` | 以 agent.py 的身份运行 X（内部使用） |
| `--run-qqid X` | 以 qqid.py 的身份运行 X（内部使用） |

## 7. 从别的设备打开界面

控制台默认只监听 `127.0.0.1`（只有本机能开）。想在宿主机浏览器里操作虚拟机里的控制台：

1. 界面里「运行环境 → WebUI 监听地址」改成 `0.0.0.0`，保存，重启程序
2. 程序启动时会在日志里打印形如 `http://192.168.x.x:8765/?t=<令牌>` 的地址
3. 用那个地址从宿主机打开

> **安全边界**：这个界面能读你的聊天记录、能冒充你发消息、还能结束你的 QQ 进程。
> 所以每次启动都会生成一个随机令牌，**首屏 HTML 也必须带令牌才能打开** ——
> 不知道令牌的人连页面都拿不到。即便如此，也请只在可信内网（NAT 后的虚拟机网络）里用，
> **绝对不要**把端口映射到公网。
>
> 令牌在启动日志里，也在托盘菜单「打开控制台界面」直接打开的地址里。

## 8. 排错对照表

**先看这一条**：程序里所有失败都会带一个错误码（形如 `E-QQ-004`）。
界面上的码**可以点** —— 点一下会弹出这个码的「可能原因 + 怎么办」。
如果懒得点，直接按下面的表查：

| 错误码 | 一句话 | 先做什么 |
|---|---|---|
| `E-ENV-001` | 数据目录不可写 | 把 exe 移到 `D:\QQAgent\` 这类可写目录 |
| `E-ENV-003` | 没有管理员权限 | 右上角「提权重启」 |
| `E-ENV-005` | 端口被占用 | 「运行环境」里换个端口 |
| `E-ENV-006` | 桌面已锁屏 | 解锁；或点「执行加固」禁用自动锁屏 |
| `E-QQ-001` | 找不到 QQ.exe | 「运行环境」里手填完整路径 |
| `E-QQ-002` | QQ 没在运行 | 点「启动 QQ」 |
| `E-QQ-003` | 找不到可见的 QQ 主窗口 | 把 QQ 从托盘点出来（**不用重启**） |
| `E-QQ-004` | 无障碍树是空壳 | 点「重启 QQ 到可读状态」（**必须完全退出后带参重启**） |
| `E-QQ-005` | 重启 QQ 失败 | 任务管理器里确认没有 QQ.exe 残留 |
| `E-UIA-004` | 找不到输入框 / 锚点 | 确认 QQ 停在某个会话的聊天界面 |
| `E-FG-001` | 抢前台失败 | 别用计划任务/服务起交互进程；先解锁屏幕 |
| `E-FG-004` | 切换会话后标题没变 | 先把窗口还原（别最小化） |
| `E-SEND-001` | 剪贴板写入失败 | 关掉剪贴板管理器/同步工具 |
| `E-SEND-002` | 发送按钮仍是禁用态 | 先跑「输入框写入测试」 |
| `E-SEND-003` | 输入框回读不符 | 自动化运行期间别手动编辑那个输入框 |
| `E-SEND-004` | 身份复核：标题不符 | 这是**防发错人**在起作用；先解决切会话 |
| `E-SEND-005` | 身份复核：QQ 号不符 | 最严重的一类，程序已拒发；跑一次「给所有会话取号」 |
| `E-SEND-007` | 该会话没有 QQ 号 | 跑一次「给所有会话取号」（降级为仅按昵称复核） |
| `E-SEND-010` | 本条回复已作废，粘进输入框的内容已清掉 | 不是故障：看它**上面**那条带码的报错（`E-SEND-002/003/006`）才是根因 |
| `E-SEND-011` | 输入框里留下一段没发出去的草稿 | 看一眼 QQ 输入框，删掉或直接回车发出；这是为了**不抢你的前台** |
| `E-SEND-012` | 暂未发出，**草稿已保留**，队列会继续重试 | 正常，不要去清空那个输入框 —— 队列正拿着同一条回复重试 |
| `E-SEND-013` | 有一条回复反复发不出去，改为长退避重试 | 不会丢；看「常驻运行 → 待发出回复」里列出的原因码 |
| `E-SEND-015` | 从磁盘恢复了一批没做完的待回复 | 正常，说明重启没有丢消息；它们会继续发送 |
| `E-SEND-016` | 退出时仍有已生成但没发出的回复 | 会落盘，下次启动自动继续；不要去删 `state/pending-replies.json` |
| `E-READ-001` | 读到了新消息但一条都没进上下文 | 日志里会列出**每条被跳过时的原因**；最常见是方向判反 → 跑「实时读取监视器」。注意：**全是自己刚发出去的消息**不算异常，这种情况不会报 |
| `E-READ-002` | 某个会话一直没被读过 | 确认「多会话发现」已开启 |
| `E-LLM-001` | 没有 API Key | 「模型接入」里填一次 |
| `E-LLM-002` | 连不上模型接口 | 检查网络与接口地址 |
| `E-LLM-004` | 密钥无效（401/403） | 重新粘贴 Key |
| `E-LLM-005` | 接口地址或模型名不对（404） | 核对模型名与地址 |
| `E-LLM-006` | 被限流或额度用尽（429） | 调大「最小 LLM 间隔」；查服务商额度 |
| `E-LLM-011` | 密钥或接口地址里混进了非 ASCII 字符 | 清空后**重新粘贴**一次，只粘 `sk-` 开头那一串；报错里会指出是第几个字符 |
| `E-LLM-012` | 调用模型时出现未分类异常 | 看「详情」里的异常类型；**这条不代表网络有问题** |
| `E-CFG-001` | 配置文件语法错 | 报错里带行列号；或用「恢复默认值」重建 |
| `E-CFG-003` | 风控两项互相压制 | 两个数要同时放宽才有效 |
| `E-PROC-002` | 常驻运行中不允许执行该任务 | 先「停止常驻」 |
| `E-PROC-007` | 单轮循环耗时远超轮询间隔 | 看「常驻运行」里的**阶段耗时排行**，它直接指出慢在哪一步 |
| 心跳已停更 | 某一步卡住了（不一定是进程死了） | 看提示里的**阶段名**与该阶段上限；见下方 §8.2 |

### 还不确定？用「诊断报告」

右上角 **诊断报告** → 跑 17 项检查 → **复制报告**。报告里：

- 先列**需要处理的项目**（带 `[X]` / `[!]`），每项给「现状」和「建议」
- 再列全部检查项
- 最后是环境明细（版本、路径、端口、进程数…）

把那段文本贴出来，就不用再回答「你的数据目录在哪」「QQ 是最小化的吗」这类问题了。

> 报告里的 `[X]` 才是要动手的，`[-]` 是「该项不适用」，`[!]` 是警告。

## 8.1 专项排查：**对方发了消息，但程序没回应**

这是最容易误判的一类问题 —— 因为「**读不到**」和「**读到了但被跳过**」在日志上
几乎一模一样。用下面这条命令把它切开。

### 第一步：跑「实时读取监视器」（只读，不会发送任何东西）

在控制台的「验证与试运行」里点 **实时读取监视器**（默认跑 60 秒），或命令行：

```powershell
qq-agent.exe --run-agent --watch 60
```

它会盯着**当前打开的那个会话**，然后照着提示做一件事：
**去 QQ 里给这个会话发一条消息**。1 秒内应该看到它被报出来：

```
  [第7轮] ★ 新增 1 条（本轮共读 12 条）
      【对方】测试目标A      key=aid:7684140137907339382        在吗
```

### 第二步：根据输出分诊

| 你看到的 | 结论 | 下一步 |
|---|---|---|
| 有 `★ 新增`，标着**【对方】** | **读取这一层是通的** | 问题在后两层：按常驻日志里的 `E-LLM-*` / `E-SEND-*` 查 |
| 有 `★ 新增`，标着**【我方】** | **方向判反了**，常驻会把它当自己的消息跳过 | 把「前台与稳定性 → 消息方向判定」改成 `position` 或 `last_only`，再用「只读诊断」复核 |
| 完全没有 `★ 新增` | 读取这一层确实读不到 | 见第三步 |
| 提示「会话列表已更新，但消息区**没有**读到新条目」 | **消息区的无障碍树被冻结** | 让 QQ 窗口真的可见（别最小化、别被完全盖住），虚拟机里保持控制台窗口活动 |
| 提示「key 不稳定」 | 消息 ID 读不到，退化成内容指纹 | 重复发完全相同的内容会被当成同一条丢掉；换一句再试 |
| 提示方向相关 ⚠ | 同上第 2 行 | —— |

### 第三步：如果确认是「读取这一层读不到」

按顺序试：

1. **让 QQ 窗口真的可见** —— 不要最小化，也不要被别的窗口完全盖住。
   虚拟机里特别注意：别让控制台窗口全屏盖住 QQ。
2. **换一个会话再跑一次**。如果换个会话就能读到，说明与「当前会话」这个状态有关 ——
   把两次 `--watch` 的输出都留出来。
3. **跑一次「只读诊断」**，它会打印每条消息的方向、key 与正文，把输出发出来。

> 补充：常驻运行时会自己把这一类问题记成 `E-READ-001`（读到 N 条新消息但一条都没进上下文），
> 并在日志里列出**每条被跳过时的原因**。界面「常驻运行」卡片也会直接显示
> **本轮读到 / 其中新增 / 被跳过** 三个数 —— 这三个数不相等就要留意。

## 8.2 专项排查：**「心跳已停更」是什么意思？和虚拟机性能有关吗？**

### 先说结论

**主因不是虚拟机** —— 之前那个提示有个**设计缺陷**：心跳的"停更"阈值写死 30 秒，
而模型调用的超时上限默认是 **60 秒**。也就是说：

> 只要一次模型调用超过 30 秒（含卡到 60 秒超时），界面**必然**弹出「心跳已停更」。

这是**必然误报**，而且会把人引向错误方向（去重启一个其实健康的进程）。已修好。

### 心跳到底在测什么

心跳是常驻主循环**每转一圈写一次**的时间戳。主循环是**串行**的：

```
读消息 → 结算缓冲 → 扫会话列表 → 队列服务（可能：切会话 → 总读取 → 调模型 → 发送）→ 落盘
```

所以「心跳停更 X 秒」的真实含义是：**这一圈已经跑了 X 秒还没跑完**，
而不是"进程死了"。其中有几步天生就慢：

| 阶段 | 典型耗时 | 该阶段上限 |
|---|---|---|
| 调模型 | 1~3 秒（慢接口/慢网络更久） | **模型「超时」设置（默认 60s）** |
| 切会话 + 发送 | 1~3 秒（抢前台、剪贴板、按键、若干固定 sleep） | 30s |
| 扫会话列表 | 随会话数量线性增长 | 30s |
| 读消息 / 重扫锚点 | 0.1s 起（节点多或虚拟机慢时更久） | 20s |

### 修好之后怎么看

界面「常驻运行」卡片现在直接显示：

- **当前阶段** —— 例如「调模型 已 42s」，卡在哪一步一眼可见
- **上一阶段耗时 / 上一轮总耗时**
- **各阶段耗时排行** —— 平均、最大、次数。**这张榜就是「是不是虚拟机太慢」的直接证据**
- **心跳** —— 距上次更新的秒数，以及**该阶段自己的上限**

「心跳已停更」现在只在**超过该阶段自己的上限**时才出现，提示里会写明阶段名；
日志里还会多一条 `E-PROC-007`（带阶段、耗时、CPU 核数）。

### 按阶段对照处置

| 慢在哪一步 | 说明 | 怎么办 |
|---|---|---|
| **调模型**（最常见） | 这步**同步**跑在主循环上，期间不读消息、也不写心跳 | 日志里若有 `E-LLM-003` 就是超时：把「模型超时」调小，或换更快的模型/接口。接口本身慢时，心跳停更 60s 以上属预期 |
| **切会话 / 发送** | 需要抢前台，窗口不可见时会反复重试 | 让 QQ 窗口保持可见（见 §8.1） |
| **读消息 / 扫会话列表** | UIA 是跨进程 COM 调用，控件越多越慢 | 给虚拟机加 **1~2 个 vCPU** 与内存；确认虚拟机没被挂起 |
| 阶段名长时间不变且超过它自己的上限 | 这才是真的卡住 | 「停止常驻」→ 重启；日志里该阶段附近应有具体错误码 |

### 虚拟机到底有没有关系

有，但它是**放大器**，不是主因：

- **vCPU 太少**（只给 1 个）时，QQ（Electron，本身就吃 CPU）与 Python 抢同一颗核，
  上面每一步都会变慢，遍历控件树的操作尤其明显。
- **没有 GPU 加速 / 虚拟机控制台窗口被关掉**时，Chromium 会节流渲染，
  消息区的无障碍树更新变慢甚至冻结（见 §8.1 的交叉验证）。
- **虚拟机被挂起/暂停**（例如宿主机睡眠）时进程完全冻结 ——
  这时心跳会停更**几分钟甚至更久**，恢复后会一次性追上来。这一条才是真正的"虚拟机问题"。
- 建议：**2 vCPU + 4 GB 内存**起步；关掉虚拟机里的自动锁屏与睡眠（见 §5.1）。

## 8.3 专项排查：**看到它"呼出 QQ → 粘一段字 → 还回焦点 → 又呼出 QQ → 把字删了"**

> ⚠️ **这一节已过期**：那条"删草稿"的行为已在 2026-09-12 按 VM 场景移除（见 §8.4）。
> 现在草稿会被保留并由队列继续重试发送。保留本节只为解释历史日志里的
> `E-SEND-010/011`。

这是**设计好的中止清理**，不是错乱。完整因果链：

1. 这条回复本来要发出去，所以它会：抢前台 → 把文字粘进输入框 → 把前台还给你。
2. 发送前的某道闸没过 → 本条**作废**（日志里会有一条带码的报错，见下表）。
3. 作废后要处理「已经粘进去但那句话」→ 这就是你看到的第二次呼出与删除。

### 第 2 步为什么没过

| 日志里的码 | 意思 | 怎么办 |
|---|---|---|
| `E-SEND-002` | 粘贴后发送按钮一直是禁用态 | **在慢速虚拟机上最常见**。把「发送按钮等待」调大（默认已放宽到 3 秒） |
| `E-SEND-003` | 输入框回读与我们写进去的不一致 | 自动化运行期间别手动编辑那个输入框 |
| `E-SEND-006` | 会话签名在写入前后变了（有人切了会话） | 自动化运行期间别手动切会话 |

## 8.4 消息永远不会丢：这是现在的最高优先目标

**场景已经确定：跑在专用虚拟机上，所以「打扰」不再是约束，正确性才是。**
据此把三处会导致"消息永远没人回"的行为全部反转：

| 原来的行为 | 为什么它是错的 | 现在 |
|---|---|---|
| 中止时**删掉**输入框里的草稿 | 删掉的就是一条已经写好的回复 | **保留**（`E-SEND-012`），队列拿着同一条继续重试 |
| 重排时把 `reply` 清空（重新生成） | 白花一次模型调用，内容还会变 | **保留**，只重试**发送**，不重新生成 |
| 重试上限用尽就撤单 | 那批消息**永远没有回应** | **不撤单**，长退避重试（`E-SEND-013`） |
| 重启丢掉内存里的待发队列 | 那批消息的正文已写进上下文并标为已读，重启后不会再被认成新消息 | **落盘**（`state/pending-replies.json`），启动时恢复（`E-SEND-015`） |

### 三条保证

**① 已生成的回复一定会被送出去。**
回复一旦生成就**冻结**：`item.reply` 不再被清空、项不再被丢弃。
发送失败只是让它在队列里多等一会儿，退避时间随失败次数增长但**永不放弃**。

**② 后到的消息不会被"挤掉"，而是排到老的后面。**
回复是按当时的上下文写好的，所以**新消息不能并进这一条**（并进去意味着发出去的那句话
没涵盖它，而它又已经进了队列不会被单独处理 —— 等于没被回应）。
现在新消息记进这一条的"迟到桶"，等它发完之后**结转成新的一条**，
到那时做一次完整重读，把迟到的和期间新来的**一起读全**。

**③ 挤压时先发老的。**
队列的排序规则是：**已定稿待发的项优先**（它们代表「已经答应要发、还没发出去」的回复），
然后按到达时间 FIFO。所以「后来补上的消息」不会越过「本应发出但未发出的」。

### 你现在该看哪里

界面「常驻运行」卡片上新增了一个数：**待发出回复**。

- 它是 **0** = 一切正常
- 它 **> 0** = 有已经写好的回复卡在发送环节。卡片会列出是哪个会话、失败了几次、
  失败原因码是什么。**这些回复不会丢**，但如果这个数一直不降，
  就按那个原因码去修（多半是 `E-SEND-002` 或 `E-FG-001`）。

> **千万别删 `state/pending-replies.json`** —— 那才是真正会丢消息的操作。
> 里面存着「已经生成好、还没送出去」的回复。

### 顺带改掉的两个默认值（都为了发送链路更稳）

| 配置 | 原默认 | 现默认 | 原因 |
|---|---|---|---|
| 用完后归还前台 | 开 | **关** | 不归还就没有「抢不到前台」这类失败；下次操作也不用重新抢。机器是专用虚拟机时，让 QQ 一直留在前台**更可靠** |
| 中止时保留草稿 | —（原来是删） | **开** | 草稿 = 可恢复的进度 |

> 在**你自己每天用的电脑**上跑，把「用完后归还前台」打开，否则 QQ 会一直霸占最上层。

### 常见现象速查

| 现象 | 最可能的原因 | 怎么办 |
|---|---|---|
| 双击后什么都没发生 | 数据目录在只读位置，或端口被占 | 把 exe 移到可写目录；看 `logs\ui.log` |
| 托盘没有图标 | 图标创建失败 | 日志里有 WARN；用界面右上角「退出程序」退出 |
| ② 一直说找不到 QQ | 非标准安装路径 | 「运行环境」里手填 QQ.exe 完整路径 |
| ③ 体检失败，说"读不到界面" | QQ 没带无障碍参数 | 点「重启 QQ 到可读状态」 |
| 程序看起来卡住没输出 | 日志卡在缓冲里 | 子进程已强制无缓冲；仍异常就用 `build.bat console` 版本 |
| 改了参数没生效 | 常驻进程仍持有旧配置 | 保存后按提示重启常驻 |
| 日志被同一个错误刷满 | 持续性故障（如 QQ 被最小化） | 同一错误码 60 秒内只输出一次完整说明；看第一条的码 |

日志文件：`<数据目录>\logs\ui.log`。界面上可以「下载日志」。

## 8.5 专项排查：**密钥被界面上的"掩码"覆盖了**

如果你看到类似这样的报错：

```
E-LLM-002 连不上模型接口
  可能原因：网络不通 / DNS 解析失败
  ...
  详情　　：UnicodeEncodeError: 'latin-1' codec can't encode characters in position 11-18
```

**别看那几条网络建议 —— 它们全是错的。** 真实情况是：

`latin-1` 只出现在 HTTP 请求头的编码里，而程序里唯一动态的头是
`Authorization: Bearer <你的密钥>`。`position 11-18` 换算过去正好是
**密钥的第 5～12 个字符**。

### 它是怎么坏的

旧版本有个 bug：界面上显示的密钥是**掩码** `sk-1••••••••ghij`（首尾各留 4 位），
而判断"用户有没有真的改密钥"的逻辑只认"**全是** `•`"这一种形式 ——
于是这个掩码被判成"用户真的填了密钥"，**在保存设置时被写进
`secrets.local.json`，把真实密钥覆盖掉了**。

`Bearer ` 占 7 个字符，加上掩码前面那 4 个真字符，那 8 个 `•` 正好落在位置 11~18
—— 和报错完全对上。

### 怎么修

**到「模型接入 → API Key」里，先清空、再重新粘贴一次真实密钥**，然后保存。

现在的版本会主动帮你确认是哪一种情况：

| 位置 | 提示 |
|---|---|
| 保存设置时 | 直接拦下并说明「`secrets.local.json` 里存的不是真密钥，而是界面上的掩码」 |
| 调用模型时 | 报 `E-LLM-011`，写明「这是掩码不是密钥」并给出 U+2022 指纹 |
| 正常粘贴时 | 若密钥里混了中文/全角字符，指出**具体第几个字符**有问题 |

> 密钥只需填一次。之后在界面上改别的设置、再点保存，不会动它 ——
> 这正是上面那个 bug 现在被回归测试守着的地方。

## 8.6 专项排查：**"清了上下文，它却还在聊之前的事"**

这是**两条真实通道**造成的，都要堵。

### 通道一：输入的名字根本匹配不上

`--forget` 最早只认**会话键**（形如 `private:3302676083`），而界面上写的是
「会话名或片段」—— 你按昵称（`光みつる`）输入时**什么都清不掉**，
而程序只是打印一句"没有匹配"，很容易被忽略。

现在：

- **昵称和会话键都可以**输入；
- 匹配不到时会列出「会话键 ↔ 昵称」对照表，直接照着抄：

```
[X] 没有匹配『这个名字不存在』的会话。现有会话（可输入**会话键**或**昵称**）：
    private:3302676083                 昵称：光みつる　上下文 12 条
```

### 通道二：一条**基于旧上下文生成的回复**还躺在盘上

这是更隐蔽的一条。程序在发送失败时会**保留**已经生成好的回复
（见 §8.4「消息永远不会丢」），它存在 `state/pending-replies.json` 里。
而"清空上下文"如果不管它，进程重启后这条回复会被恢复并**照原样发出去** ——

> 你看到的就是：上下文明明清了，它却在回复里聊着清除之前的话题。

**判据**：那条回复的内容只对应**清除之前**的消息，完全不含清除之后的消息。

现在「彻底忘记」会三样一起清：

| 清的 | 不清的后果 |
|---|---|
| 会话上下文 | 等于没清 |
| **基于该上下文生成、还没发出的回复** | 重启后照原样发出去，看起来像没清干净 |
| 轮询基线标记与指纹快照 | 「发现」路径的指纹比对还指着旧内容 |

界面上会明确告诉你丢弃了几条、原本要发什么：

```
[✓] 会话上下文：12 条 → 已清空
[✓] 待发回复：1 条 → 已丢弃
      原本要发：…（内容）
[✓] 轮转状态：基线标记与指纹快照 → 已重置
```

> ⚠️ 这和「绝不丢消息」是有冲突的，所以**必须显式**：清空上下文是你的明确指令，
> 而那条回复的前提已经被你抹掉了，留着它就是"用一个已作废的前提去说话"。
> 程序不会静默丢弃，一定会把内容和原因打出来。

### 还有一件事：QQ 界面上的未读数字

清完之后，**QQ 界面上那些历史消息仍然在屏幕上**。正常情况下下次启动会重建基线
把它们标为已读，不会再进上下文。

但如果你清的那个会话不是**当前打开的那个**（走的是「发现」路径），
界面上的**未读数字**会让最后几条被重新读进来 —— 这是降级方案唯一能用的线索，
是有意设计的。

**想彻底干净**：先在 QQ 里点开那个会话把未读消掉，再跑一次「彻底忘记」。

## 8.7 在 QQ 里直接下指令（`.ai`）

不想回到这个网页时，可以直接在 QQ 聊天里发一条以 `.ai` 开头的消息来控制它。
**指令本身不会转发给模型，也不会写进上下文。**

| 指令 | 作用 |
|---|---|
| `.ai reset` | 清空本会话的上下文（含被教过的话）、退出连续对话，并丢掉还没结算的防抖缓冲 |
| `.ai clear` | 同 `.ai reset` |
| `.ai help` | 回一段可用指令说明 |
| `.ai 任意内容` | 剥掉 `.ai` 后当普通提问交给模型（≈ 直接聊天，且跳过触发词限制） |

- 前缀还认 `。ai` `/ai` `.aichat`，大小写不敏感；前缀后必须跟空格或冒号。
- 你自己在 QQ 里手输的、以及对方发的都算；**机器人自己刚发的回复会被自动排除**，不会自触发。
- 执行完会回一句话确认（走正常的发送队列，照吃风控限速）。想静默执行就在
  「对话内指令」里关掉 `reply_ack`。

还有几条指令（`.ai stop/end`、`.ai on/off`、`.ai teach`、`.ai persona`、`.ai img`）
**PC 端还没移植**，现在发过去只会收到一句「未移植」的说明，不会转发给模型。
其中人格切换和图片识别是**明确不做**的部分。

> 想关掉整套指令：控制台「对话内指令 → 启用对话内指令」关掉即可，
> 之后 `.ai` 开头的内容会被当成普通消息交给模型。

## 8.8 专项排查：**同一条回复反复发不出去（日志被它刷满）**

如果日志里反复出现这样的两行，间隔约半分钟，而且失败次数一直涨：

```
SEND  → '某个会话'(QQ …) （回复内容…）
QUE   '某个会话' 未发出，保持原回复原地重试（第 218 次失败｜E-SEND-003｜草稿已不在，将重新写入）
```

那是一条回复**卡在发送环节**，而**每次重试都在重复同一个注定失败的步骤**。

### 上次的真实成因：多行文本的换行对不上

对比报错里的「期望」和「实际」，注意标点之间的差别：

```
期望=…）⏎⏎……我听见了。      ← 模型输出里有空行分段
实际=…）……我听见了。童声…    ← 回读拿到的没有空行
```

QQ 的编辑器是 contenteditable，**段落是各自独立的节点**，从界面回读时拿不到段间的换行。
而当时的校验用的是**原始字符串包含**，于是：

- 只要回复里带空行分段（很常见），回读就**永远**对不上 → 判定失败
- 连"草稿还在不在输入框里"也用了同一个判据 → 每次都判"不在"
- 于是每轮都重新粘贴 → 又失败 → **无限重试**（实测跑到第 224 次，将近两小时）

现在改成**归一化空白后再比较**：换行、空格、空行的表现形式差异不再算失败，
但内容真正写错（错字、截断、写错内容）**仍然会被拦住**。

> 取舍很明确：**少一个空行，远好过两个小时发不出去。**
> 为了不掩盖问题，只有空白差异时会记一条 INFO 说明「归一化后一致」。

### 顺带改掉的两件事

**① 退避不再 30 秒封顶。**

原来的退避上限是 30 秒，所以一条过不去的项会变成**每 30 秒一次的无限重试**。
现在改成阶梯退避：

| 失败次数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8+ |
|---|---|---|---|---|---|---|---|---|
| 下次重试 | ~2s | 5s | 15s | 30s | 1min | 2min | 5min | **10min** |

前几次仍然很快（瞬时故障要能自愈），之后逐步拉长到 10 分钟一次。
**仍然不丢弃** —— 项留在队列里，只是来得越来越慢。

**② 反复失败会明确报一次 `E-SEND-013`。**

这个码之前定义了却从未触发过，所以上次那份日志里**没有任何一行**说明
「有一条回复已经卡了两小时」。现在第 5 次失败会报一次，之后每 20 次再报一次
（带会话名、失败次数、最后一次原因、回复开头、草稿是否还在输入框）。

### 遇到时怎么办

| 步骤 | 做什么 |
|---|---|
| 1 | 看 `E-SEND-013` 里的「最后一次原因」是哪个码，按那个码处理（多半是 `E-SEND-002/003`） |
| 2 | 若原因含 `E-SEND-003`：确认版本已是新版（旧版会因换行差异永久失败） |
| 3 | 若原因含 `E-SEND-002`：把「发送按钮等待」调大 |
| 4 | 想让这条**不再重试**：点「彻底忘记某会话」（见 §8.6）—— 它会连同待发回复一起清掉 |

## 9. 启动失败排查：**双击后一闪就没了怎么办**

windowed 程序没有控制台，所以「启动失败」和「启动后按设计退出」**长得一模一样**。
按下面顺序走，三步之内一定能定位。

### 第一步：先分清是哪种

| 现象 | 多半是 | 怎么确认 |
|---|---|---|
| 双击后一闪 → 浏览器**打开了**一个页面 | **已经有一个实例在跑，本次是正常退出**（不是崩溃） | 见下方「② 已经有一个实例」 |
| 双击后一闪 → 浏览器**没打开** | 要么崩溃，要么撞上了没有端口记录的旧实例 | 见「① 崩溃」与「③ 看日志」 |
| 双击后弹了一个消息框 | 它把原因写在框里了，照着做 | —— |

> 现在这两种情况都会**弹消息框说明原因**（含 pid、端口、怎么办）。
> 如果连消息框都没看到，就按 ① 走。

### ① 用「诊断版」看真实报错

`dist\qq-agent-console.exe` 是带控制台的版本，**启动过程会打印到窗口里**。
双击它（或在 `cmd` 里运行），出问题时窗口会保留输出，直接就能看到是哪一步炸了。

```powershell
cd D:\QQAgent
qq-agent-console.exe
```

如果它抛了异常，还会写一份完整报告到 `logs\ui-crash.log`（含回溯、参数、环境、
数据目录）。**把那个文件发出来即可定位。**

### ② 「已经有一个实例在跑」——换版本时最常见

升级 exe 是个常态操作，而旧实例多半还在跑（可能只剩一个托盘图标看不见）。
单实例锁是**全局**的，所以新 exe 会识别到旧的那个，然后**按设计正常退出**。

程序现在会：

1. 打印/弹框说明「已有实例」+ pid + 端口 + 怎么办；
2. **如果检测到运行中的是另一个 exe 路径（也就是你在换版本），自动接管** ——
   先结束旧实例，再用本版本启动。所以正常情况下你不需要做任何事。

需要手动接管时：

```powershell
qq-agent.exe --takeover
```

它会结束所有旧实例，然后用本版本启动。

### ③ 看日志

无论哪种情况，`logs\ui.log` 里都有启动过程的完整记录，包括
「已经有一个控制台在运行（pid …，端口 …）→ 本次启动正常退出」这类说明。

```powershell
notepad <数据目录>\logs\ui.log
```

### 常见原因速查

| 症状 | 原因 | 处理 |
|---|---|---|
| 一闪就没了，浏览器没打开 | 旧实例占着单实例锁 | `qq-agent.exe --takeover` |
| 一闪就没了，浏览器**打开**了 | 同上（这是**正常退出**，不是崩溃） | 用浏览器里那个界面；要换版本用 `--takeover` |
| 控制台版报 `NameError` / `ImportError` | exe 打包不完整或代码有错 | 记下报错，`logs\ui-crash.log` 里有完整回溯 |
| 控制台版报端口相关错误 | 端口被占用 | 「运行环境」里换端口，或关掉占用端口的程序 |
| 弹框说「数据目录不可写」 | exe 放在 `C:\Program Files` | 移到 `D:\QQAgent\` 这类可写目录 |

> **开发提示**：`test_exe.py` 专门负责「真 exe 能不能启动起来」——
> 它跑 `--safe` 并检查服务真的监听了。改完 `app/main.py` / `app/platform_win.py`
> 这类启动链路代码后**一定要跑它**：源码模式下看不出来的启动崩溃，只有它能抓到。

## 10. 数据都在哪

```
<exe 所在目录>            ← 可写时用这里（便携模式）
├─ qq-agent.exe
├─ config.json            agent 的全部行为参数（可直接编辑，界面保存不会抹掉注释）
├─ secrets.local.json     API Key（不入库）
├─ app-settings.json      壳自己的设置（QQ 路径、端口、自启）
├─ state\                 会话上下文、QQ 号缓存、轮转指纹、心跳、停止哨兵
│  ├─ pending-replies.json  **已经生成好、还没发出去的回复**（别删，见 §8.4）
│  └─ ui.json             控制台端口与令牌（换版本时靠它识别旧实例）
└─ logs\
   ├─ ui.log              运行日志
   └─ ui-crash.log        启动崩溃报告（只有崩过才有，见 §9）
```

放 `C:\Program Files` 这类只读位置时，上面这些会自动落到
`%LOCALAPPDATA%\QQAgent\`（界面「路径信息」里能看到实际用的是哪个）。

## 11. 安全与合规（别跳过）

1. **这是「替你操作你这台电脑上已登录的 QQ」**，不碰协议、不碰群控、不碰任何账号凭据。
2. **只限个人自用、非商业、非群控**。历史上已有「QQ 自动抢红包」类工具被认定
   不正当竞争的判例（杭州法院）。一旦演变成对外提供服务或批量操作，性质就变了。
3. **不要在同一 IP/设备上同时跑自动化账号和日常主号**，尤其是放到服务器上的时候。
4. **CDP 端口（如果开了）等于宿主机上的任意代码执行入口**。默认只绑 `127.0.0.1`，
   需要远程访问就开 SSH 隧道，**绝不暴露公网**。
5. **前台守卫不要拆**。代码里的 `force_foreground` / `clear_editor` 自检是为了防止
   按键泄漏到你的其它窗口 —— 这是数据丢失级别的风险，不是代码风格问题。
