## 19:2x–19:4x · 「虚拟后台渲染 + 操作 QQ」可行性调研

### 用户交办

背景：A 要服务 B 就得自备 QQ，单账号能对接的人少、依赖特定号、有风控风险，
且公开服务必须把 A 的 QQ 暴露到公共环境。问：**能否让 B 端打开 exe 后起一个虚拟的
「服务器进程」，在这个后台（不占真实前台与焦点）内要求 UI 渲染，据此操作 QQ？**
参考 `D:\Psyche\sealdice-core_1.6.1_windows_amd64\code\sealdice-core`，
**但必须保留 Windows 仿真人操作**（不转协议）。

### 核实参考项目：它走的不是这条路

`sealdice-core` 的 QQ 接入**全靠独立协议端进程**：`lagrange/Lagrange.OneBot.exe`（78 MB，
Lagrange.Core = .NET 实现的 NTQQ 协议）+ `milky/lagrangeV2.exe` / `yogurt.exe`。
core 负责生成配置 → 起子进程 → 用 WebSocket 连它（`dice/platform_adapter_lagrange_helper.go`）。

它的「后台无窗口」**只有一行代码**：`tray_windows.go` 里
`win.ShowWindow(win.GetConsoleWindow(), win.SW_HIDE)` —— 藏掉自己的控制台。

**结论：它的无头能力来自「走协议所以不需要图形界面」，不是来自「后台渲染 UI」。
所以「虚拟后台里做 UI 渲染」这件事它给不了答案，必须自己实测。**
值得借鉴的只有**进程形态**：托盘 + localhost WebUI + 命名 Mutex 单实例 + 托管子进程
（本项目已基本同构，唯一差异：目前是「附着已开的 QQ」而非「托管 QQ」）。

### 关键机制：查到了「窗口不可见就冻结」的理论依据

Chromium 官方（Blog 2021-12 + `windows_native_window_occlusion_tracking.md`）：
Windows 上 Chrome **自己算遮挡** —— 按 z 序枚举桌面上所有窗口，从"未遮挡区域"逐个减掉，
减完没剩就判 occluded；**一旦 occluded，前台标签按后台处理：渲染停止、JS 节流**。

被判 occluded 的情况：最小化 / 被完全盖住 / **在另一个 Windows 虚拟桌面上** / 屏幕被锁 /
**被移到屏幕外**（原文 "minimized or otherwise moved offscreen"）。

→ 这一条**直接排除了「把窗口移到 (-32000,-32000)」这个最省事的直觉方案**。
→ 同时给项目已有实测（`probe_minimized.py` 的 Invoke 静默失效、README 的"遮挡后读不到"、
部署手册的"锁屏后异常"）补上了统一解释。

### 为什么要用测试页而不是直接测 QQ

隐藏桌面上的 QQ 只能用**独立 profile** 启动（否则和用户自己的 QQ 抢同一份 `%APPDATA%\QQ`，2.27 GB）
→ 未登录 → 没有聊天页/输入框 → `WM_CHAR` 无处可落。而 `WM_CHAR → 焦点 renderer 宿主`
是**引擎级代码**，Electron 走同一段。换来：不需要登录、不动用户 profile、**状态可三方读回**
（页面自述标题 / Chromium 投影的 a11y 树 / `PrintWindow` 截图）—— 比直接测 QQ 更严格。

### 激活方案消融：**最小必需集合 = 空**

`none` / `renderer_only` / `no_attach` / `no_renderer_focus` / `full` —— **五档全通，连"什么都不做"也通**。
原因：那张桌面上只有它一个窗口，Windows 在窗口显示时就把焦点给了它，Chromium 上来就认为自己是 active。
> ⚠️ **每档必须独立进程、全新窗口** —— Chromium 焦点状态有粘性，连跑消融就废了。

同时记下：`SetForegroundWindow` 在隐藏桌面上**恒返回 0**、`GetForegroundWindow()` **恒为 NULL**。
→ **非活动桌面上不存在前台窗口**，这修正了原方案里"前台是 per-desktop 所以抢得到"的那半句。

### ⚠️ 最重要：免前台写入在本机就已可用（§6.5）

起因：既然隐藏桌面上连 `SetFocus` 都不需要，那"免前台"是隐藏桌面独有的，还是窗口消息本来就不需要前台？

**这一轮踩到并修掉的三个坑（都不是 R4 的问题，是自己的）**

1. **`--args --once` 传不进去** —— argparse 把以 `-` 开头的 `--once` 当成**另一个选项**
   而不是 `--args` 的值 → "expected one argument" + `SystemExit(2)`。
   而 `--args "--once --dry-run"` 能work是巧合：argparse 只对**含空格**的未知串
   才按位置参数处理。→ 必须写 `--args=--once`。
   教训：子进程退出码 2 却连结果文件都没有时，先怀疑 **argparse 在 import 前就退出了**。

2. **`--once` 在队列等待期就退出，一条都没发** —— `serve_queue` 是两阶段的
   （第一趟 prepare 生成，第二趟 deliver 发送），而 `--once` 只调一次就走。
   补了有限等待（静默窗上限 + 15s）。
   ⚠️ 判据踩坑：`while queue.unsent()` **一次都没进** —— 因为 `unsent()` 的语义是
   「已定稿(frozen)待发」，而 prepare 刚跑完时项还没定稿。
   正确判据是 `queue.items`（队列里还有没有项）。

3. **写入三档全败（投递 42 条、回读空）** —— 根因是**取号步骤抢走了编辑器焦点**：
   `qqid` 打开资料卡再关掉，DOM 焦点没了，之后投多少 WM_CHAR 都被丢弃。
   修：`_type_via_wmchar` 里补 `self.editor.SetFocus()`（控件级，不走输入队列，
   隐藏桌面照样有效）。V1 的 `type_text` 本来就有这一句，我搬路径时漏了。
   再加一条：**回读校验必须归一化换行**（`_norm_ws`）——
   ProseMirror 里换行不产生可见字符，写入 `A\n\nB` 回读是 `AB`，
   不归一化会把**明明成功的写入**判成 E-SEND-003，导致反复重试最后撤单。
