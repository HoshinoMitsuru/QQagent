# 跨终端部署与操作手册

> 适用对象：`pc-agent-demo`（PC 端 QQ AI 代理，路线 A）
> 目标：让你能在**任意一台设备**上把这套东西跑起来 / 管起来，并且尽量不打扰你的正常用机。
> 配套文档：`下一步操作清单.md`（本机 Windows 的最小验证流程）、`README.md`（设计说明与踩坑记录）

---

## 0. 一页速览：该把 agent 跑在哪台机器上

| 拓扑 | 跑在哪 | 打扰程度 | 前置条件 | 推荐度 |
|---|---|---|---|---|
| **A. 本机 Windows** | 你现在这台 | 中（方案 C 后降为"闪一下"） | 无 | ⭐ 验证阶段用 |
| **B. 另一台 Windows 常开主机** | 旧笔记本 / NUC / 备用机 | 极低（不占用你的屏） | 一台常开的 Windows + 一次 RDP 登录 | ⭐⭐⭐ 长期推荐 |
| **C. Ubuntu ECS 跑 QQ** | 云服务器 | 无（但代价大） | Xvfb + VNC 扫码 + 承受风控 | ⭐ 不推荐，见 §7 |
| **D. ECS 当控制层 + B 当执行层** | 混合 | 极低 | 拓扑 B + 一条 HTTP/WS 通道 | ⭐⭐⭐ 进阶推荐 |

**一句话结论**：想让"别的设备"来干活，最稳的是**把 QQ 客户端留在 Windows 上（拓扑 B），而不是搬到 Ubuntu ECS 上（拓扑 C）**。原因见 §7。

## 1. 环境准备（一次性）

### 1.1 Python 隔离环境

```powershell
# 方式一：WorkBuddy 自带隔离环境（本项目当前就用这个）
$env:Path = "C:\Users\Psyche\.workbuddy\binaries\python\envs\default\Scripts;$env:Path"

```

> 要么把 venv 的 `Scripts` 目录加进 `PATH` 后裸调 `python`（上面这种），要么用 `& "完整路径\python.exe"`。

### 1.2 依赖清单

| 包 | 用途 | 必需 |
|---|---|---|
| `uiautomation` / `comtypes` | 读控件树、模拟按键（路线 A 的核心） | 是 |
| `pyperclip` | 剪贴板写入（中文只能走粘贴） | 是 |
| `requests` | 调 OpenAI 兼容接口 | 是 |
| `websockets` | `cdp_probe.py` 连 CDP 调试端口（方案 A） | 方案 A 必需 |
| `pytesseract` / `Pillow` | OCR 兜底 | 否 |

### 1.3 密钥

`config.json` 里 `llm.api_key` 留空时，会去 `llm.api_key_file` 指的 JSON 里按 `api_key_json_keys` 顺序找。
当前指向 `.../wechat_et_qq_client/tools/data/secrets.json` 的 `llm.api_key`，已实测可读到。

## 2. QQ 启动参数（决定你能用哪条路线）

QQ 的启动参数**只在主进程首次启动时生效**。QQ 已经在跑时再执行一次带参数的命令，只会把已有窗口唤到前台，**参数不会应用**。

> ⚠️ 必须**完全退出** QQ：托盘图标右键退出，确认任务管理器里没有任何 `QQ.exe` / `QQEX.exe` 残留，再重新启动。

### 路线 1：只跑 UIA（现状，需要抢前台）

```powershell
"D:\QQ.exe" --force-renderer-accessibility
```

- 必须带 `--force-renderer-accessibility`，否则 Electron 的无障碍树是空壳，读不到任何消息。
- `--send` / `--input-test` 需要 QQ 在**前台**，会把窗口顶到最上层（方案 C 已把持续时间压到最短）。

### 路线 2：加开 CDP 调试端口（方案 A，彻底不抢前台）

```powershell
"D:\QQ.exe" --remote-debugging-port=9222 --remote-allow-origins=* --force-renderer-accessibility
```

- `--remote-debugging-port=9222`：开 Chrome DevTools 协议端口（QQNT 是 Electron 内核，原生支持）。
- `--remote-allow-origins=*`：允许任意来源发起 WebSocket 连接（只是本机回环，别把端口暴露到公网）。
- 迁移期建议把 `--force-renderer-accessibility` 一起留着：CDP 读、UIA 读可以互为备份。

**验证参数是否真的生效**（不要靠猜）：

```powershell
# 看主进程命令行里有没有这两个参数
Get-CimInstance Win32_Process -Filter "Name='QQ.exe'" |
  Where-Object { $_.CommandLine -like '*remote-debugging-port*' } |
  Select-Object ProcessId, CommandLine | Format-List

# 看端口有没有起来
netstat -ano | findstr "9222"
```

**注意**：`127.0.0.1:9211` 是 QQ 自己的内部 JWT 服务，**不是** CDP，别被它误导。
判断标准：`curl http://127.0.0.1:9222/json/version` 返回带 `"Browser"` 字段的 JSON 才是 CDP。

## 3. 三种部署拓扑的操作步骤

### 3.1 拓扑 A：本机 Windows（最短路径）

```powershell
cd D:\Psyche\Sealdice-AIChat\pc-agent-demo
$env:Path = "C:\Users\Psyche\.workbuddy\binaries\python\envs\default\Scripts;$env:Path"

python -X utf8 agent.py --peek 10        # 1) 只读：核对方向、昵称、正文
python -X utf8 agent.py --input-test     # 2) 只写：验证输入框链路（不发送）
python -X utf8 agent.py --send "测试"     # 3) 真发：最后一步，自己确认
python -X utf8 agent.py                  # 4) 常驻
```

**必须从你自己的交互式终端启动**（原因见 §4）。

### 3.2 拓扑 B：另一台 Windows 常开主机（长期推荐）

适合场景：把这套东西挪到一台不用来工作的机器上，你的主力机彻底不受打扰。

**第 1 步：在目标机上装好环境**
把 `pc-agent-demo/` 整个目录拷过去（`config.json` 里的 `api_key_file` 路径记得改成目标机上的实际路径，或直接把 key 填进 `llm.api_key`）。

**第 2 步：RDP 登录一次，把 agent 拉起来**

```powershell
cd C:\pc-agent-demo
$env:Path = "<venv>\Scripts;$env:Path"
Start-Process -FilePath "python" -ArgumentList "-X","utf8","agent.py" `
  -RedirectStandardOutput "logs\agent.out.log" -RedirectStandardError "logs\agent.err.log" `
  -WindowStyle Hidden
```

> **关键坑**：直接启动的应用进程在 **RDP 断开后会被锁进"已断开会话"**，前台权限、渲染都可能异常。
> 想让它断开 RDP 后照常跑，用下面两种方式之一：
> 1. **把会话切回控制台**（推荐，Windows 10/11 自带）：
>    ```powershell
>    # 先 query session 查到你 RDP 会话的 ID，再切回物理控制台
>    query session
>    tscon <会话ID> /dest:console
>    ```
> 2. **用计划任务 + "不管用户是否登录都要运行"**：勾选该选项后进程跑在 Session 0，
>    **没有前台权限** → 只能走方案 A（CDP）。这也是为什么方案 A 值得做。

**第 3 步：远程看日志**

```bash
# 从你的主力机 SSH 进去 tail
ssh user@主机 tail -f C:/pc-agent-demo/logs/agent.out.log
```

> **务必加 `-u`**（或像我上面那样重定向）：Python 输出到管道是**块缓冲**的，
> 不加 `-u` 时日志会卡在缓冲区里，看起来像"程序卡死了"（我们踩过这个坑，白等 6 分钟）。

### 3.3 拓扑 C：Ubuntu ECS 跑 QQ —— 见 §7，结论是不推荐

### 3.4 拓扑 D：ECS 当控制层，Windows 当执行层（进阶）

分工建议：

| 层 | 放在哪 | 负责 |
|---|---|---|
| **执行层** | 常开的 Windows（拓扑 B） | 唯一接触 QQ 的地方：读消息、发消息 |
| **控制层** | 现有 Ubuntu ECS（`aligera.website`） | LLM 网关、对话历史、行为策略、定时任务、日志归档 |
| **接入层** | 你的任意设备（手机/平板/笔记本） | 通过 HTTP/WS 下发指令、看状态 |

好处：**QQ 客户端永远在住宅网络的 Windows 上，不碰服务器 IP → 规避风控**；同时你从任何设备都能管。
落地方式：给 `agent.py` 加一个 `--serve` 模式暴露一个最小 HTTP 接口
（`GET /peek`、`POST /send`、`GET /status`），ECS 上的服务再反向调用它。
⚠️ 这条通道**必须只走内网或带鉴权的隧道**，绝对不能裸奔在公网上。

## 4. 前台权限：这套方案最容易踩的"隐形地雷"

这是整个项目里最反直觉、也最容易误判成"代码写坏了"的地方。

**规则**：Windows 只允许**交互式登录会话里、且当前有输入焦点归属**的进程调用 `SetForegroundWindow`。
违反时**不报错**，而是静默失败（`GetLastError() = 5 / ERROR_ACCESS_DENIED`）。
更糟的是，紧接着发出的 `SendKeys` 按键**不会消失**——它们会打进当时真正的那个前台窗口。
我们实测过：`{Enter}` 打进了终端，把半截命令行当命令提交了，看起来就是"程序卡死"。

**结论表**：

| 启动方式 | 能抢前台吗 | 可选路线 |
|---|---|---|
| 自己的交互式终端里直接跑 | ✅ | 路线 1（UIA）或路线 2（CDP） |
| 计划任务（"不管用户是否登录都要运行"） | ❌ | 只能路线 2（CDP） |
| Windows 服务（nssm 等） | ❌ | 只能路线 2（CDP） |
| SSH 进来的会话（OpenSSH Server） | ❌ | 只能路线 2（CDP） |
| 沙盒 / 后台子进程 | ❌ | 只能路线 2（CDP） |

**代码里的守卫**（别绕过它们）：
- `force_foreground()`：抢前台后**用 `GetForegroundWindow()` 复核**，没抢到就返回 `False`；
- `type_text()`：抢不到前台**直接中止**，一个键都不发；
- `clear_editor()`：**入口自检前台**，不在前台就拒绝发 `Ctrl+A` / `Delete`；
- `send_text()`：主路径走 `InvokePattern.Invoke()`（不需要前台、不产生按键），`Enter` 只是兜底且需前台确认。

> **方案 C 的代价要记住**：`type_text()` 现在写完全把前台**还给**你原来的窗口。
> 所以任何"在 `type_text` 之后再发按键"的代码都必须**重新抢一次前台**——
> `clear_editor()` 的自检就是为此加的护栏。改代码时别把它删了。

## 5. 命令速查表

| 命令 | 作用 | 会不会打扰你 | 会不会发消息 |
|---|---|---|---|
| `agent.py --selftest` | 自检配置/密钥/模型连通/调教解析 | 否 | 否 |
| `agent.py --replay "在吗"` | 不开 QQ，回放一条看模型怎么回 | 否 | 否 |
| `agent.py --peek [N]` | 只读解析并打印最近 N 条消息 | 否 | 否 |
| `agent.py --input-test [文本]` | 写入 → 回读 → 清空 | 是（闪一下） | **否** |
| `agent.py --send "文本"` | 真发一条 | 是（闪一下） | **是** |
| `agent.py --send "文本" --force` | 同上，但允许在群聊里发 | 是（闪一下） | **是** |
| `agent.py` | 常驻循环自动回复 | 每次回复闪一下 | **是** |
| `agent.py --dry-run` | 常驻但只读不发 | 否 | 否 |
| `cdp_probe.py` | 探测 CDP 端口与可注入目标 | 否 | 否 |
| `cdp_probe.py --dom` | 定位输入框/消息列表 | 否 | 否 |
| `cdp_probe.py --type "文本"` | 实测 CDP 写入（写完清空） | **否** | 否 |

**跨设备调用**：以上全是命令行，所以**只要能在目标机上开一个终端（本地终端 / SSH / 远程桌面），就能远程驱动它**。
CDP 端口默认只绑 `127.0.0.1`，从别的设备访问要开隧道：

```bash
# 在你的笔记本上，把远端 9222 映射到本地（只读探测用）
ssh -L 9222:127.0.0.1:9222 user@装有QQ的机器
# 另开一个终端
python -X utf8 archive/cdp_probe.py --dom
```

> ⚠️ **永远不要**把 `--remote-debugging-port` 暴露到公网或 0.0.0.0。
> CDP 等于宿主机上的任意代码执行入口，任何一个能连上的人都能读你的聊天记录、冒充你发消息。

## 7. 调研：能不能在 Ubuntu ECS 上跑？

**结论：技术上可行，但不建议把 QQ 客户端放上去。ECS 更适合当控制层（拓扑 D）。**

### 7.1 技术上打通需要什么

QQ Linux 版同样是 **Electron 内核**，所以 **CDP 路线可以原样移植到 Linux**——这是它相对 UIA 的又一个优势。
无头服务器上需要：

```bash
# 1) 补齐 Electron / CJK 运行依赖（Ubuntu 24.04 注意 libasound2t64）
sudo apt-get install -y libgbm1 libnss3 libasound2t64 libgtk-3-0 \
  libxshmfence1 libxdamage1 libdrm2 libxkbcommon0 fontconfig fonts-noto-cjk dbus-x11

# 2) 造一块虚拟屏（否则登录对话框映射不出来）
Xvfb :1 -screen 0 1920x1080x16 &
export DISPLAY=:1
fluxbox &                       # 没有窗口管理器时，登录框可能无边框、无法聚焦

# 3) 扫码登录必须"看得见"界面 —— 临时开 VNC 投到浏览器
sudo apt-get install -y xvfb x11vnc novnc websockify fluxbox
x11vnc -display :1 -rfbauth ~/.vnc/passwd -forever -shared -bg
/usr/share/novnc/utils/novnc_proxy --vnc localhost:5900 --listen 6081 &

# 4) 用调试参数启动 QQ
DISPLAY=:1 qq --no-sandbox --remote-debugging-port=9222 --remote-allow-origins=*
```

### 7.2 但有三个硬阻碍

| 阻碍 | 具体表现 | 严重度 |
|---|---|---|
| **扫码登录** | Linux QQ **没有 CLI 登录**，只能扫二维码。无头服务器必须先架 VNC/noVNC 才能看到二维码（一次性成本） | 中 |
| **服务器 IP 风控** | 社区（NapCat）有大量实测：服务器上 Linux QQ 扫码后**约 2–3 小时就被 `KickedOffline`**；有人降级到旧版组合（NapCat 4.15.19 + Linux QQ 3.2.21）才稳定 63+ 小时。**版本差异极大，且随腾讯策略变动** | **高** |
| **常用号风险** | NapCat 官方安全文档明确警告："避免在同一 IP/设备上同时登录 Bot 账号与常用账号，以防常用账号受到异常影响" | **高** |

另外，Electron + Xvfb 常驻至少吃 **2 核 4G**，还要考虑和现有 ECS 上 `aligera.website` 服务的资源争抢。

### 7.3 建议

1. **不要把 `光みつる` 这类常用号放到 ECS 上登录**——风控成本和收益完全不成比例。
2. 真要用服务器，**换一个专用小号**，并接受"可能几小时掉一次线、需要重扫"的运维成本。
3. **推荐做法**：QQ 客户端留在常开的 Windows（拓扑 B），ECS 只做 LLM 网关 / 历史记录 / 调度（拓扑 D）。
   这样既不动服务器 IP、又复用了你已有的 ECS 基建，还顺带把"从任何设备可控"这件事解决了。
4. 如果哪天决定走协议/注入路线（NapCat 等），要清楚这是**另一条完全不同的技术路线**，
   侵入性比现在的"替人操作 QQ"强得多，且**不能与现有 UIA/CDP 方案混用**。

## 8. 排错对照表

| 现象 | 最可能的原因 | 怎么办 |
|---|---|---|
| `--peek` 报"找不到可见的 QQ 主窗口" | QQ 在托盘里 / 窗口被最小化 | 把 QQ 主窗口显示出来；不要用最小化状态 |
| 读到的消息全空 | QQ 没带 `--force-renderer-accessibility` 启动 | 完全退出 QQ，用 §2 的参数重启 |
| `无法把 QQ 窗口切到前台` | 进程没有前台权限 | 改从交互式终端启动；或切到方案 A（CDP） |
| 发送按钮一直禁用 | 文本没真的进输入框 | 先跑 `--input-test` 定位；看是否 `Click` 被去掉后 SetFocus 不够 |
| 发送后 QQ 窗口留在最上层 | `restore_foreground` 失败 | 日志里会有 WARN；把 `uia.restore_foreground` 保持 `true`，或改用方案 A |
| 命令行报 `意外的标记"-X"` | PowerShell 不允许直接执行带引号的路径 | 把 venv `Scripts` 加进 `PATH` 后裸调 `python`，或用 `& "路径\python.exe"` |
| 程序"卡住"好几分钟没输出 | Python 输出到管道是块缓冲 | 加 `-u`（`python -u -X utf8 agent.py`）或重定向到文件 |
| 日志显示"前台窗口归还失败" | 抢回前台时被系统拒绝 | 属已知限制，不影响功能；长期解法是方案 A |
| `cdp_probe.py` 说端口不是 CDP | 端口被 QQ 其他内部服务占用 | 换端口（如 9223）；确认 QQ 命令行带 `--remote-debugging-port` |

## 9. 安全与合规约束（别跳过）

1. **CDP 端口 = 宿主机任意代码执行入口**。只绑 `127.0.0.1`，需要远程访问就开 SSH 隧道，**绝不暴露公网**。
2. **前台守卫不要拆**。`force_foreground` / `clear_editor` 的前台自检是为了防止按键泄漏到你的其他窗口——这是数据丢失级别的风险，不是风格问题。
3. **群聊默认放开是个行为选择**。`private_chat_only=false` + `group_requires_trigger=false` 意味着群聊里会自由发言，容易刷屏或说错话；正式跑之前建议至少加上触发词。
4. **合规提示**：本项目是"替你操作你这台电脑上已登录的 QQ"，不碰协议、不碰群控。
   但历史上已有"QQ 自动抢红包"类工具被认定**不正当竞争**的判例（杭州法院）。
   本项目**仅限个人自用、非商业、非群控**；一旦演变成对外提供自动化服务或批量操作，性质就变了。
5. **账号安全**：不要在同一 IP/设备上同时跑自动化账号和日常主号（尤其是放服务器上）。

## 10. 迁移到方案 A（CDP）的推荐步骤

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 用 §2 路线 2 的参数重启 QQ | 端口 9222 起来 |
| 2 | `python -X utf8 archive/cdp_probe.py` | 确认 CDP 可用 + 目标列表 |
| 3 | `python -X utf8 archive/cdp_probe.py --dom` | 拿到输入框/消息列表的 DOM 事实 |
| 4 | `python -X utf8 archive/cdp_probe.py --type "CDP 写入测试"` | 验证 `Input.insertText` 是否被 ProseMirror 接受 |
| 5 | 把 `--type` 的输出发回给我 | 我据此实现 `send_backend: "cdp"` 的正式版 |
| 6 | 在 `config.json` 增加开关，UIA / CDP 双后端可切换 | 平滑迁移，随时回退 |

第 4 步是**唯一的未知数**：QQ 的输入框是 ProseMirror，理论上 `Input.insertText` 走浏览器输入管线能被它接住；
万一接不住，退路是用 `Input.dispatchKeyEvent` 逐键合成，或者直接对 ProseMirror 的事务层下手。
