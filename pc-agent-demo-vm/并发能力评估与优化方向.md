# 并发能力评估与优化方向

> 前提：只考虑**私聊 + 纯文本**，目标是在**不把消息发错人**的前提下，评估可负载的并发交流量，并给出优化方向。
> 所有耗时数据标注了来源：`实测`（本次跑的基准）/ `推导`（从代码里的固定等待累加）/ `估算`。
> 基准脚本：`bench.py`（只读，不抢前台）。

---

## 0. 结论速览

| 结论 | 内容 |
|---|---|
| **当前架构的本质** | 原本是**单通道**：读写都绑定"QQ 里当前显示的那一个会话"。**2026-09-11 晚已加入「发现」层**（扫会话列表判谁在等我，免前台），读写解耦为两阶段 → 见 §10.6。但受**虚拟列表**限制，可见会话上限 ≈ **7~8 个** |
| **第一个必须解决的问题** | 不是性能，是**正确性**：`deliver()` 发送前不校验目标，配合 1.8s 的模型生成窗口，**切会话就会发错人**（D1，已修） |
| **现状可负载并发** | **8~15 个活跃私聊会话**（每条回复 1.8s 模型 + 0.6~1.1s UI，被人因打扰上限压住）；实际**可被发现的**会话数另受 7~8 上限约束 |
| **最大吞吐（纯技术）** | 约 **19 条/分钟**。注意：瓶颈**不是 UI**，而是**模型串行 + `min_llm_interval_seconds: 2.0` 的全局限流** |
| **真正的天花板** | **人因**：每条回复独占前台 385ms。按"前台占用率 ≤10%"算，可持续吞吐只有 **约 15 条/分钟** |
| **优化后（UIA + 并行模型 + 批量租约）** | 吞吐 ≈ **21 条/分钟**，并发 ≈ **20 个会话** |
| **CDP 化后** | 前台占用归零 → 人因天花板消失，吞吐 **150 条/分钟**量级，并发 **60~100 个会话** |
| **最大优化杠杆** | ①修 5 个正确性缺陷（不做则并发 = 错发）②模型并行 ③CDP 化 |
| **前台依赖的真实范围**（2026-09-11 第四轮实测） | 只有**「写文本」一步**必须抢前台。读取**既不依赖前台也不依赖窗口可见**（最小化后照常）；**切会话也不需要前台**（`InvokePattern`）→ 详见 §10.8 |

## 3. 现状架构：为什么它是"单通道"

```
step()   ──►  refresh_layout()  ──►  _sync_scope()  ──►  read_messages()  ──►  _ingest()
                                          │                    │
                                   读「当前窗口标题」      只读「当前渲染的 ml-list」
                                          ▼
flush()  ──►  generate_reply(scope)  ──►  deliver(scope, reply)  ──►  qq.send_text()
                                                                          │
                                                                  写进「当前打开的会话」
```

**读和写都锚定在"当前显示的那个会话"上**，没有任何一层携带"这条消息属于谁"的独立身份。
所以：

| 维度 | 现状 |
|---|---|
| 上下文隔离 | ✅ **已做对**。`ConversationStore` 按 `scope` 分桶（`agent.py:513-672`） |
| 消息聚合 | ✅ 已有自适应防抖（`Debouncer`，`agent.py:682-797`） |
| 会话切换 | ⚠️ 被动——用户手动切，程序跟着换 scope（`_sync_scope`，`agent.py:1726`） |
| **主动切到指定会话** | ❌ **不存在** |
| **发送目标校验** | ❌ **不存在** |
| **读非当前会话** | ❌ **不可能**（UIA 只能读渲染出来的那个会话） |

## 4. 五个正确性问题（并发化之前必须修）

### 🔴 D1 `deliver()` 发送前不校验目标 —— **模型生成期间切会话 = 发错人**（最高危）

`agent.py:1892-1898`：

```python
def deliver(self, scope: str, reply: str) -> None:
    log("SEND", clip(reply, 70))
    self.store.history(scope).push("assistant", reply, source="auto")   # scope 只用于写历史
    if self.dry_run:
        return
    if not self.qq.send_text(reply):        # ← 写进「当时打开的会话」，完全不校验
        log("ERR", "发送失败，本条回复未送达")
```

**放大因素**：模型生成实测 **1.81s**。用户在等待回复时切到别的会话，是**极其常见**的操作。

**为什么现有防线挡不住**：
- `InvokePattern` 免前台 → 只解决"怎么发送"，与"发给谁"无关
- `editor_text()` 回读校验 → 校验的是**输入框内容对不对**，与**目标会话是谁**无关
- 结果：A 的消息 + A 的上下文，生成了给 A 的回复，**发进了 B 的对话框**

### 🔴 D2 批次与 scope 解绑 —— 用"结算时刻的会话"去套"入队时刻的消息"

- `Debouncer.pending` 是**全局单例**（`agent.py:708`），`PendingMessage`（`agent.py:674-679`）**不携带 scope**
- `flush()` 取 `scope = self.scope`（`agent.py:1844`），而 `self.scope` 由 `_sync_scope()` 从**当时的窗口标题**推导
- `_sync_scope()` 只在 `step()` 开头执行（`agent.py:1753`），而主循环是 `step(); flush()`（`agent.py:1922-1923`）

→ 在 `_sync_scope()` 之后、`flush()` 之前切会话，批次会**带着旧会话的消息、用新会话的 scope** 生成并发送。
（`_sync_scope` 里的 `flush(force=True)` 覆盖了大部分情况，但**不是全覆盖**，窗口 ≈100ms。）

### 🔴 D3 `scope` 用昵称当主键 —— 重名即串味

`agent.py:1722-1724`：

```python
def current_scope(self) -> str:
    kind = "group" if self.qq.is_group else "private"
    return f"{kind}:{self.qq.dialog_title or '(未命名会话)'}"
```

私聊里 QQ **没有** `user-name` 元素（已逆向确认），标题就是昵称。
→ **两个同名联系人 = 同一个 scope**：上下文互串 + 发送目标无法区分。
需要换成会话列表项里更稳的身份（`AutomationId` / UIN），标题只做显示。

### 🟠 D4 跨会话冷却**直接丢消息**，且全局串行限流

`agent.py:1818-1821`：

```python
cooldown = float(self.cfg["chat"].get("reply_cooldown_seconds") or 0)
if cooldown > 0 and time.time() - self._last_reply_at < cooldown:
    log("SKIP", "命中冷却窗口，本条丢弃")     # ← 丢弃，不是延迟
    continue
```

- `_last_reply_at` 是**全局**的 → 回复 A 后 1.5s 内，**B 的消息被直接丢掉且无补偿**
- `LLMClient.wait_turn()`（`agent.py:815-820`）+ `min_llm_interval_seconds: 2.0` 是**全局串行 sleep**
  → 它把模型调用强行变成 2s 一次，**直接把吞吐封顶在 30 条/分钟**

### 🟠 D5 非当前会话的消息被漏读并**永久丢弃**

- 只有当前打开的会话会被 `read_messages()` 读到
- 切过去时 `_sync_scope()` 会调 `baseline()`（`agent.py:1737`），而 `baseline()`（`agent.py:1513-1521`）把该会话**已有消息全部标记已读**
- → 离线期间 A 发的消息，等你切过去时被**静默忽略**，永久丢失

> 此外还有一个小问题：`Debouncer` 的 `due_at` 是**全局单时间戳**（`agent.py:709, 751`），
> 任何会话来新消息都会顺延它 → **话多的 B 可以无限推迟 A 的结算**（跨会话饥饿）。

## 5. 并发量估算

### 5.1 两个天花板

| 天花板 | 由什么决定 | 现状数值 | 优化后 |
|---|---|---|---|
| **技术天花板** | 1 / 单条处理耗时（UI 串行 + 模型是否并行） | **19.2 条/分** | 66.7 条/分 |
| **人因天花板** | 前台占用率 ≤ 你还能用这台电脑 | **≈15 条/分**（占用 10%） | 21 条/分（批量租约） |
| **CDP 后** | 人因天花板消失，只剩技术天花板 | — | **150 条/分**量级 |

**现状技术天花板推导**：
单条 = 模型 max(1.81s, `min_llm_interval` 2.0s) + UI 1.12s = **3.12s** → 60/3.12 = **19.2 条/分**

**人因天花板推导**：每条回复独占前台 385ms → 占用率 = T × 0.385 / 60
- T = 15 → 9.6%（可接受边界）
- T = 20 → 12.8%（能感觉到卡顿）
- T = 30 → 19.3%（基本没法工作）

### 5.2 折算成"能同时服务几个私聊"

设每个活跃会话平均每分钟产生 1 条回复（会被防抖聚合成约 1 次调用）：

| 路线 | 吞吐 | **可负载并发会话** | 说明 |
|---|---|---|---|
| **现状（UIA + 模型串行 + 全局限流）** | 15~19 条/分 | **8~15 个** | 瓶颈在人因 + 全局限流，**不是 UI** |
| + 关掉 `min_llm_interval` + 模型并行 | 21 条/分 | **15~20 个** | 仍然被人因压住 |
| + 批量前台租约 | 21 条/分 | **20 个** | 打扰次数 N→1，占用降到 285ms/条 |
| + CDP 化（免前台） | ≈150 条/分 | **60~100 个** | 人因约束归零 |

> **延迟口径**：以上按"平均首响 ≤ 10~15 秒"折算。若要求首响 ≤ 5 秒，并发数要再打个 6~7 折。

### 5.3 一个容易被忽略的次生瓶颈：轮转读

多用户下要"发现非当前会话的新消息"，只能**依次把每个会话切过去读**：

```
每个会话的巡检成本 = 切换(0.3~0.8s) + 读(0.08s) ≈ 0.4~0.9s
轮转 10 个会话 = 4~9 秒/轮   →  单个会话的「发现延迟」就是 4~9 秒
```

而且**切会话会真实改变你屏幕上的 QQ**（即使不抢焦点也看得见闪烁）。
→ 所以**"无脑轮转读"在 UIA 路线下不可行**。

> ✅ **2026-09-11 晚更新：这个瓶颈已经绕开了，但不是靠"减少切换成本"，而是靠"根本不去切"。**
> 会话列表项上**可以读到未读徽标**（`3条未读` / `99+`），且扫一遍列表**完全免前台**（实测 7 个会话中位 84ms）。
> 于是把「发现」和「读取」彻底拆开：扫列表只负责判「谁在等我」→ 占位入队；
> 等静默窗关闭、真的排到它了，**才付那一次 0.4~0.9s 的切换成本**去读全文。
> 代价是发现延迟不再是 0，而是「静默窗(5s) + 排队等待」；收益是**轮转读的开销从 O(N·0.6s) 降到 O(0.084s)**。
> 详细设计见 §10.7，以及 `README.md` 的「多会话发现与延迟总读取（降级方案）」。
>
> ⚠️ 但它撞上了另一个更硬的天花板：**会话列表是虚拟列表**，实测 7 项 × 96px = 672px、
> 视口 821px、`ScrollPattern` 不受支持 → 折叠线以下的会话**不在 UIA 树里**。
> 所以「发现」能覆盖的会话数上限 ≈ **7~8 个**（可见性上限，不是性能上限）。

## 6. 优化方向（按收益/成本排序）

### P0 · 正确性（不做这些，并发就等于批量错发）

| # | 措施 | 针对 | 成本 |
|---|---|---|---|
| 1 | **发送前目标校验**：`deliver()` 在 `send_text` 前重新取 `current_scope()` 与目标比对，不等即中止 + 告警；并把 `InvokePattern` 对象**提前取好**，把「校验→调用」压到最短 | D1 | 小 |
| 2 | **发送后自证**：发完立刻 `read_messages()`，确认"最后一条是我方 + 内容匹配"；不匹配则立即告警并停止后续发送 | D1 | 小 |
| 3 | **`PendingMessage` 携带 scope**，`flush()` 改用批次自带的 scope；`due_at` 改成 **per-scope** | D2、饥饿 | 小 |
| 4 | **会话身份换主键**：用会话列表项的 `AutomationId`/UIN，标题只做显示 | D3 | 中 |
| 5 | **冷却改为延迟排队**（而不是 `continue` 丢弃） | D4 | 小 |
| 6 | **未读回补**：切过去时不要无条件 `baseline()`，改为按未读计数补处理 | D5 | 中 |

### P1 · 吞吐（把 1.8s 移出关键路径）

| # | 措施 | 收益 | 成本 |
|---|---|---|---|
| 7 | **模型调用并行化**（线程池 / 队列 + worker），UI 只做串行投递 | 关键路径去掉 1.81s，吞吐 19.2 → 66.7 条/分 | 中 |
| 8 | **关掉或调小 `min_llm_interval_seconds`**（现在 2.0s 全局串行 sleep，直接封顶 30 条/分） | 立刻解封上限 | 极小 |
| 9 | **批量前台租约**：连续发送时不归还焦点，批次结束才 `restore_foreground` | 打扰次数 N→1，占用 385→285ms/条 | 小 |
| 10 | **最小切换调度**：当前会话优先 + 按会话分组批处理 | 省 0.5s/条（不切换时） | 小 |
| 11 | **同会话消息合并**（已有防抖）→ 进一步加强为"按会话排队 + 静默期合并" | 往返次数↓ + 回复质量↑ | 中 |

### P2 · 架构（量级提升）

| # | 措施 | 收益 | 成本 / 风险 |
|---|---|---|---|
| 12 | **CDP 化**：免前台 → 人因天花板消失；`Input.insertText` 代替"清空+剪贴板+粘贴"再省 ~175ms | 吞吐 **150 条/分**量级 | 需实测 ProseMirror 接受度（`cdp_probe.py` 已就绪） |
| 13 | **多实例 + CDP**：N 个 QQ 客户端，各自独立渲染层 → 真并行 | 线性 ×N | 需要多个 QQ 号；UIA 路线下无意义（前台仍是全局唯一） |
| 14 | **直连内部发送接口（hook IPC）** | 数量级提升（不需要切会话） | **越界**（等于 NapCat 那条路），**不推荐** |

## 8. 一句话建议

**先把 D1/D2 修掉（发送目标校验 + 批次绑定 scope）——这是"不发错人"的底线；
再关掉 `min_llm_interval_seconds` 的全局限流、把模型调用并行化——这是"能用"的门槛；
最后走 CDP——这是"好用"的路径。**

在 D1 修掉之前，**不建议把这个 agent 同时挂在多个会话上跑**：
当前实现下，只要你在等回复时切一次会话，就有实打实的概率把 A 的回复发进 B。

> ✅ **2026-09-11 晚更新**：D1（发送前不校验目标）已修 —— `deliver()` 现在是**带租约的事务**，
> 三重闸（标题 / QQ 号 / 会话签名）任一不过就中止并重排，`max_attempts` 次后撤单。
> D2（批次与 scope 解绑）、D3（scope 用昵称）、D5（非当前会话消息被丢弃）也已修。
> D4（跨会话冷却丢消息）改为**排队 + 合并**，不再直接丢。
> 所以上面那句"在 D1 修掉之前"的限制**已解除**；现在的真实约束换成了
> **会话列表可见性上限 7~8 个**（§5.3 / §10.6）与**账号风控额度**（§9）。

## 9. 特定假设下的并发量估算

> **用户给定的三个前提**
> ① 用户发出**本轮全部消息**后，可接受 **10~30 秒**等待
> ② 模型用 **deepseek-flash**
> ③ 发送对象按 **QQ 号**锁定（而不是昵称）
>
> 新增脚本：`bench_llm.py`（模型侧批次基准，不碰 QQ、不发送）

### 9.1 实测：deepseek-flash 的批次-耗时曲线

`bench_llm.py --rounds 3`，输入为 `flush()` 同款合并格式（`【发送者】：内容` 换行拼接）：

| 批次 n | 输入字数 | 模型耗时 avg | 回复字数 | 相对单条 |
|---|---|---|---|---|
| 1 条 | 11 | **1.25s** | 19 | 1.00× |
| 2 条 | 25 | **1.55s** | 26 | 1.24× |
| 4 条 | 62 | **1.59s** | 31 | 1.27× |
| 6 条 | 94 | **1.77s** | 38 | 1.42× |

生成速率稳定在 **15~21 字/秒**。

> **这是本次最重要的一个发现**：批次从 1 涨到 6（**负载降为 1/6**），
> 模型耗时只涨 **42%**。也就是说 —— **合并批次是纯赚的**，
> 长等待窗口在"减少模型调用次数"这件事上收益极大，而成本几乎可以忽略。

### 9.2 三个前提各自带来什么

| 前提 | 对并发量的作用 | 方向 |
|---|---|---|
| ① **10~30s 等待窗口** | 把一轮对话的 N 条消息**合并成 1 次回复**（实测 N≈2~6）。这是唯一真正**放大**并发量的杠杆 | ⬆️ 放大 N 倍 |
| ② **deepseek-flash** | 单次生成降到 1.25~1.77s（此前 deepseek-chat 同类场景约 1.8~2.0s）。但只要模型调用还是**串行**的，它就在关键路径上 | ⬆️ 小幅 |
| ③ **按 QQ 号锁定** | 安全性的代价：UI 层没有别的办法，**必须真的切到那个会话再发** → 单次 UI 串行段从 0.62s 抬到 **≈1.2s** | ⬇️ **降低约 48%** |

**注意 ③ 是一个 trade-off，不是免费优化**：`S_ui` 0.62s → 1.2s（切换 0.3~0.8s + 读 0.08s + 写发 0.535s）。用约一半的吞吐换"绝不发错人"，这个交换是值得的。

### 9.3 容量分量（把瓶颈逐个算出来）

| 分量 | 数值 | 依据 |
|---|---|---|
| μ 技术 · LLM 并行 | **50 次/分** | 60 / 1.2s（UI 是唯一串行资源） |
| μ 技术 · LLM 串行 | **21.4 次/分** | 60 / (1.2 + 1.6) |
| μ 技术 · LLM 串行 + 现有限流 | **18.8 次/分** | 60 / (1.2 + max(2.0, 1.6))，被 `min_llm_interval_seconds: 2.0` 卡住 |
| μ **人因**（前台占用 ≤10%） | **15.6 次/分** | 60 × 0.10 / 0.385s |
| μ **人因** + 批量前台租约 | **21.1 次/分** | 60 × 0.10 / 0.285s |
| μ 技术 · CDP 化 | **150 次/分** | 60 / 0.4s，且前台占用归零 |
| μ **账号风控**（估算，需实践校准） | **10~20 次/分** | 个人号持续高频发送的耐受度 |

### 9.4 结论：稳定可承载的私聊并发量 ≈ **15~30 个会话**

取各分量的**最小值**作为有效容量 μ_eff，再按 `C_max = ρ × μ_eff / r_reply` 折算（ρ=0.7 留出稳定裕度）：

| 路线 | μ_eff | C（r=0.5/分） | C（r=1/分） | C（r=2/分） |
|---|---|---|---|---|
| 只做窗口优化（模型仍串行、限流仍在、UIA 无租约） | 15.6 | **22** | **11** | **5** |
| + 模型并行 + 批量前台租约 | **20** | **28** | **14** | **7** |
| + CDP 化（免前台） | **20** | **28** | **14** | **7** |

> `r` = 每个会话每分钟的**回复轮次**。按"每个用户每 1~2 分钟发起一轮对话（一轮 2~6 条，被 30s 窗口合并成 1 次回复）"折算，**r ≈ 0.5~1 次/分**。
> 对应本表的 **C ≈ 14~28 个私聊会话**。

### 9.5 两个反直觉结论

**① 做了「模型并行 + 批量租约」之后，再上 CDP 对"并发量"几乎没有帮助。**

因为此时 μ_eff 已经不是技术瓶颈，而是**账号风控**（10~20 次/分）。CDP 的价值转移到别处：

- **零打扰**：你可以正常用这台电脑（UIA 路线下每次回复都要抢你 385ms 前台）
- **无桌面会话也能跑**：SSH / 计划任务 / 服务里都能工作（UIA 路线下这些全都不可用）

**② 真正的最终天花板不是技术，是"你的 QQ 号看起来还像不像真人"。**

按 r=1 算，C=14 意味着系统每分钟发 14 条消息。对个人号来说这已经偏激进了；
若 C=28，就是每分钟 28 条 —— **几乎必然触发腾讯风控**。
所以工程上建议**按 15~25 个会话设计**，并把「账号风控」当成比性能更硬的约束来对待。

### 9.6 这套方案要成立，必须补上的四个前置条件

| # | 条件 | 不做的后果 |
|---|---|---|
| 1 | **静默窗口必须配硬上限**（W_silence=10~30s **且** T_max=30s） | 用户每 20 秒一句、间隔始终 < W → **永远不结算，回复饿死** |
| 2 | **到期时间必须加抖动（jitter）** | C 个会话的窗口可能同时到期 → 一起涌入 UI 串行队列 → 最后一个等 (C-1)×1.2s |
| 3 | **切会话后必须等目标渲染完成 + 校验 QQ 号** | 切了但没渲染完就读写 → 仍是发错人（这正是前提 ③ 要解决的问题） |
| 4 | **按 QQ 号锁定前，得先能拿到 QQ 号** | 见下方待验证实验 |

### 9.7 针对前提 ③ 的待验证实验

| # | 要验证什么 | 影响 |
|---|---|---|
| 1 | 会话列表项能否读到 **QQ 号 / UIN**（或稳定 `AutomationId`） | 决定 ③ 能否实现；拿不到就只能退回昵称，重名风险仍在 |
| 2 | **切会话能否用 `InvokePattern`（免前台）** | 决定切换成本是 0.3s 还是 0.8s，直接影响 S_ui 与吞吐 |
| 3 | 切开一个会话的真实渲染完成时间 | 校准 S_ui；也是"切完必须校验"的等待时长 |
| 4 | 账号在什么发送频率下触发风控 | 校准 μ_风控 —— 这是决定最终并发量的那个数 |

## 10. 落地实现（2026-09-11 晚）

§9 是估算，这一节是**已经写进代码并通过实测**的部分。

### 10.1 取 QQ 号：唯一可行通路是「资料卡」

现在的 scope 主键是 **`private:<QQ号>` / `group:<群号>`**，不再是昵称。取号通路逐条实测：

| 通路 | 结果 | 证据 |
|---|---|---|
| 会话列表项及全部后代 | ❌ | AutomationId 全空；Name/HelpText/ItemStatus/FullDescription 全空 |
| UIA 通用属性（AriaRole/PositionInSet/SizeOfSet/Level） | ❌ | Chromium 一律填 `group` 与 `0` |
| 全树 AutomationId | ❌ | 192 节点里只有 5 个非空 |
| 全树「5~12 位数字」文本 | ❌ | 0 个 |
| **资料卡** | ✅ | `buddy-profile__header-uid` → `TextControl 'QQ 3302676083'` |
| CDP 9222 | ⏳ | 未启用，需重启 QQ |

三个关键实测事实：

1. **资料卡是独立顶层窗口**（title=`资料卡`，class=`Chrome_WidgetWin_1`，pid=QQ 主进程），
   不在主窗口的 UIA 子树里 —— 只扫主窗口会永远找不到。
2. **唤出它不需要鼠标**：对 `chat-header__contact-name` 调 `InvokePattern.Invoke()` 即可。
   但它会把弹窗激活，**QQ 因此被顶到前台** → 取号是一次性操作，之后只读缓存。
3. **群聊卡片的号是裸数字**：`'1098451742'` + `' (7人)'` 两个独立 TextControl，没有 `QQ` 前缀。

另一个坑：**资料卡窗口不会被销毁**，关闭只是 `visible=False`。不过滤可见性就会在切换会话后
立刻"找到"上一次的旧卡片，读到上一个用户的资料 —— 这是「发错人」的另一种形态。

> 取号命令：`python qqid.py --enroll-all`，缓存在 `state/uid-map.json`。

### 10.2 防错发：三道闸

`deliver()` 被改造成**带租约的发送事务**，任何一闸不过就中止 + 重排：

| # | 闸 | 挡什么 | 判据 |
|---|---|---|---|
| ① | 标题复核 | 根本没切过去 | 标题 == 目标显示名 |
| ② | QQ 号复核 | 标题重名 / 改备注 | 缓存里的 QQ 号 == 目标 QQ 号 |
| ③ | **会话签名复核** | **生成/写入期间被切走** | `(标题, 群标记, 最后 6 条 ml-item 的 AutomationId)` 写入前后完全一致 |

第 ③ 闸的核心是**消息 ID**：`ml-item` 的 AutomationId 是 18~19 位全局唯一消息 ID，
两个会话的可见消息集合不可能相同 —— 它比标题强得多，也顺带覆盖了「切了但没渲染完」。

**必须 `force=True` 重扫锚点。** 切换会话后 `self.ml_list` 可能仍指向旧容器，
用陈旧引用读出的 ID 恰好等于切换前的值 → 复核**假通过**。这不是理论风险，是实现陷阱。

实测（`test_send_guard.py`，12/12 通过）：同会话内签名稳定、切走后必然变化、
切回后可复现、QQ 号复核能拒绝错目标。

### 10.3 排队与风控：把「什么时候发」和「发什么」解耦

```
读消息 → 准入判定 → 防抖聚合 → 入队(QueuedReply)          ← 不碰 UI、不调模型
                                    ↓ pick()（到点 + 风控放行）
                          生成回复（不占前台，1.3~1.8s）
                                    ↓
                          切会话 → ①②复核 → 捕获签名 → 写入 → ③复核 → 发送
```

关键结构变化：**模型调用移出了 UI 临界区**。原来 `flush()` 是「聚合 → 调模型 → 发送」一气呵成，
现在拆成 `flush()`（只入队）和 `serve_queue()`（生成 + 发送）。

风控预算（`queue` 配置段）：

| 参数 | 默认 | 作用 |
|---|---|---|
| `max_replies_per_minute` | 12 | 60s 滑动窗口上限 |
| `min_interval_seconds` | 5.0 | 相邻两次发送的硬间隔 |
| `merge_if_wait_over_seconds` | 5.0 | 补充消息合并阈值 |
| `max_hold_seconds` | 30.0 | 静默窗顺延的硬上限（防「每 20s 一句」饿死） |
| `jitter_seconds` | 3.0 | 到期抖动，避免多会话同时涌入 |

### 10.4 补充消息的 5s 阈值

| 情况 | 返回 | 结果 |
|---|---|---|
| 不在队列里 | `absent` | 走正常防抖 |
| 还要等 **> 5s** | `merged` | **并进**他待提交的上下文，不额外回一次 |
| **≤ 5s** 就能轮到 | `close` | 不掺和，照常另排一次回复 |

实现位置：`_ingest` 在 `deb.add()` **之前**先问 `queue.offer_followup()`。
这个顺序很关键 —— 先入防抖就会变成两条独立回复，合并就失效了。

### 10.5 仿真结论：12 条/分下安全区约 15 个会话

`python reply_queue.py --report`（10 分钟，每用户 0.75 轮/分）：

| 并发 | 实际频率 | 队列残留 | 单回复吸收 |
|---|---|---|---|
| 5 | 3.9/分 | 1 | 1.56 |
| 10 | 7.5/分 | 1 | 1.64 |
| 15 | 11.1/分 | 3 | 1.63 |
| 20 | 11.9/分（顶上限） | 14 | 1.73 |
| 30 | 11.9/分 | 22 | 2.55 |
| 40 | 11.9/分 | 36 | 3.21 |

对照 §9.4 的解析估算（C≈14~28），实测落在同一区间，且更保守 —— 因为仿真里
阈值合并、抖动、硬上限都真实参与，不是纸面推导。

**反直觉但有意义的一点**：负载越高，「单回复吸收」越大（1.56 → 3.21）。
排队机制在压力下会**自发变得更省额度**（把更多消息合进一次回复），
这正是它比"每条都回"抗压的原因。

### 10.6 降级方案：发现与读取分离（2026-09-11 第三轮，已落地）

**它解决的是 §5.3 那个次生瓶颈，以及 §4 的 D5。**

#### 10.6.1 为什么要"降级"

桌面 UI 上每个会话**只保留最新一条消息的节选**（而且被截断）。这意味着：

| 想法 | 为什么不行 |
|---|---|
| 拿节选当 AI 的上下文 | 截断 + 单条，凑不出对话，硬喂只会让 AI 胡说 |
| 靠节选判断"恢复了没有" | 只能判"变没变"，判不出"变成了什么" |

所以降级方案把**唯一能可靠拿到的信息**（有没有新东西）用到极致，
而把**必须完整才能用的信息**（正文）推迟到代价必须付的那一刻。

#### 10.6.2 两阶段结算

```
阶段 1 · 免前台（每 2s，实测 84ms）
    list_sessions → 指纹比对 → ensure_pending（占位入队，pending_read=True）
        └ 指纹 = (预览文本元组, 未读条数)；时间 token 在解析阶段就切掉
        └ 只记 unread 条数，不读正文、不碰前台

    静默窗（5s 阈值，复用防抖器的 current_base，上限 queue.max_hold_seconds）

阶段 2 · 需要前台（排到时只付一次）
    _ensure_session（force_foreground + 坐标点击）
    → _read_into_history（读最近 30 条 → split_new → _admit 分流写入**它自己的**上下文）
    → generate_reply（不占前台，因此移出了 UI 临界区）
    → RateBudget 放行 → deliver（三道闸租约发送）→ _refresh_fp
```

两阶段的价值：`prepare()` 不发送 ⇒ **不吃风控额度** ⇒ 可以早于风控放行执行
（`pick(ignore_budget=True)`）。模型那 1.3~1.8s 因此完全落在 UI 串行段之外。

#### 10.6.3 四个关键设计点

| 点 | 做法 | 不这么做会怎样 |
|---|---|---|
| **未读线索的最后价值** | 首见会话建基线时 `skip_last = unread_hint`（上限 8） | 要么回灌 30 条历史，要么把对方刚发的几条当历史吃掉 |
| **总读取拿到 0 条 → 撤单** | `_read_into_history` 返回条数，0 就 drop | 为一条已被用户自己读过/已撤回/其实是自己发的消息，白回一句 |
| **防自我叫醒** | 发送成功后立刻 `_refresh_fp()` 重采指纹 | 自己发的那条改掉预览 → 下轮又触发发现 → 再切过去读 → 发现没新消息 → 撤单。白付切换成本，严重时死循环 |
| **D5 的正确修法** | `_seen` **按 scope 隔离**（`dict[scope, OrderedDict]`），基线门控用**内存态** `has_seen(scope)` | 用持久化的 `baselined` 门控，重启后内存已读集合是空的却以为建过基线 → 静默丢弃离开期间到达的消息 |

#### 10.6.4 一个真机才暴露的 bug（B5）

`element.Click()` 不是"点这个控件"，而是"把光标移到控件中心、**在那个屏幕坐标上按一下**"。
所以坐标点击的硬前提是**目标窗口必须是最上层**。

实测：前台是编辑器时，`click_session()` **返回 True 而标题完全没变** ——
因为它内部有「点两次」兜底，且只要 `header_title()` 非空就算成功，而旧会话的标题也是非空。
最后只表现为 `_ensure_session` 卡在「切换后渲染未稳定」。

`type_text()` 一直有 `force_foreground()`，切换路径漏了。修法两处：

1. 切会话前 `force_foreground(hwnd)`；
2. 抬升前把用户原来的前台窗口存进 `qq.fg_before_switch` —— 否则之后 `type_text()` 读到的
   「原前台」已经是 QQ 自己，方案 C（用完即还）会静默失效。

**这是纯离线单测永远测不出来的那类 bug**，也是新增 `test_live_chain.py` 的理由。

### 10.8 前台依赖的实测盘点（2026-09-11 第四轮）

**它解决的是什么**：之前整个设计都建立在"必须抢前台"这个前提上（§10.2 的租约、
方案 C 的用完即还、B5 的抬升窗口）。实测逐条打表之后发现**这个前提被高估了**。

| 操作 | 机制 | 需要前台？ | 需要窗口非最小化？ | 抢焦点？ |
| --- | --- | --- | --- | --- |
| 扫会话列表 / 读消息 / 读签名 | UIA 属性读取 | ❌ | **❌** | ❌ |
| **切到目标会话** | **`InvokePattern.Invoke()`** | **❌** | ✅ | ✅（副作用） |
| 切到目标会话（兜底） | `item.Click()` 坐标点击 | ✅ | ✅ | ✅ |
| 清空输入框 / 写文本 | `SendKeys(Ctrl+A / Ctrl+V)` | ✅ | ✅ | ✅ |
| 点「发送」按钮 | `InvokePattern.Invoke()` | ❌ | —（未测） | ❌ |

#### 三个实测结论

**① 读取既不依赖前台，也不依赖窗口可见。**
`probe_minimized.py`：最小化后控件树 417 节点、7 个会话、9 条消息、
输入框与发送钮的定位**全部不变**。
（此前文档里"最小化会让无障碍树失效"是**错的**，已更正。）

**② 切会话不需要前台 —— 这条以前一直走弯路。**
会话列表项支持 `InvokePattern`；QQ 完全不在前台（前台是别的程序）时
`Invoke()` 照样把会话切过去了（`probe_switch_nofg.py`）。
所以 UI 串行段里的"切会话"从"抬前台 + 坐标点击"降级为"一次 Invoke"：
**不再依赖窗口在最上层**，也不会再出现 B5 那类"点空了却报成功"的静默故障
（成功判据同时改成了 `标题 == 目标名`）。

**③ 但"免前台"≠"不打扰"。**
`Invoke` 之后 QQ 会被激活顶到最上层 —— Chromium 内部对目标元素 `SetFocus` 的副作用。
实测：前台从别的程序变成 QQ，且**连等 4 秒也还不回去**。
既然这个激活是我们引起的、我们也不需要它，就在切换完成后**显式归还**。

归还本身还挖出一个更深的坑：`restore_foreground` 原本是**另一份**实现，
它 `AttachThreadInput` 到**目标窗口**的线程 —— 对 `Invoke` 造成的激活**必失败**；
而 `force_foreground`（附加到**当前前台窗口**的线程）一次成功。
原因是「前台归属权」握在当前前台窗口的那个线程手里。两份实现已合并成一个。

#### 对"部署形态"的意义（§9 的容量结论要不要改）

| 项 | 变化 |
|---|---|
| 人因天花板（前台占用率 ≤10%） | **切会话那部分开销消失了**（不再需要抬前台），但"写文本"仍要抢前台 → 天花板**小幅放宽，未消失** |
| 能不能跑在最小化的窗口后面 | ✅ **能**。发现/读取全程免前台免可见性；只有真正切过去和写文本时才需要把窗口还原出来 |
| 最终消除前台依赖的路径 | 仍是 **CDP**（`Input.insertText` 免前台），见 §10.7 第 3 项 |

> 换句话说：现在**不必**为了让"前台是 QQ"而专门搞一台虚拟机 —— 唯一的硬约束是
> 「写文本」那一步，而在同一台机器上让 QQ 可见、抢一次前台再还回去，成本很低。
> 虚拟机的价值剩下"隔离打扰"（剪贴板污染、光标、按键风险），不再是"绕开前台"。
