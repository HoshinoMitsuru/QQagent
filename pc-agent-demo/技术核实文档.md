## 1. 这是什么（一句话 + 边界）

**一句话**：一个**只操控本机已登录 QQ 客户端界面**的 AI 代理 —— 用 Windows 无障碍接口（UIA）读消息、调大模型生成回复、再用剪贴板 + 按键把回复打进去发出去。**不碰协议、不碰账号凭据、不碰群控。**

### 边界（汇报时最该先说清的）

| 做 | 不做 |
|---|---|
| 读取本机 QQ 窗口里**已渲染**的界面元素 | ❌ 不解析 QQ 网络协议、不注入、不 hook |
| 用操作系统的公开接口（UIA / 剪贴板 / 按键） | ❌ 不使用任何账号密码 / token / 第三方登录 |
| 只服务**一台机器上的一个已登录账号** | ❌ 不做多账号、不做群发、不做批量操作 |
| 回复**私聊或群聊里对本人说的话** | ❌ 不做抢红包、不做营销引流、不做自动加好友 |

> 更细的法律边界讨论见 `EXE使用说明.md §11 安全与合规`。

## 3. 技术路线选型：为什么不做协议

| 路线 | 能否做到 | 为什么没选 |
|---|---|---|
| **A. UIA 操控本机客户端**（**当前方案**） | ✅ 已落地 | 只依赖操作系统公开接口；不需要逆向协议；账号安全风险最低 |
| B. 逆向 QQ 协议 | 技术上可能 | 违反用户协议；版本一变就全废；账号封禁风险高；**且与"跟朋友聊天"这个目标不成比例** |
| C. 第三方协议库（OneBot 等） | 需额外部署协议端 | 多一个需要长期维护的组件；仍属协议路线，同样的合规问题 |
| **D. CDP（Chromium 调试协议）** | ✅ 已探通（`archive/cdp_probe.py`） | 更干净（`Input.insertText` 天然免前台），但**需要 QQ 以调试端口启动**，等于给宿主机开一个任意代码执行入口。已探通、未落地，留作备选 |

**汇报要点**：选型的核心不是"哪个技术强"，而是**风险与收益是否成比例**。
这个项目的目标只是"帮本人回消息"，用协议路线的风险远大于收益。
CDP 是更好的技术答案，但它把安全负担从"操作界面"变成了"守护一个调试端口"，
所以在当前场景下**不做**，但保留探通记录。

## 4. 技术难点与创新（主线）

每一个难点都按同一模板写：**问题 → 约束 → 做法 → 证据 → 代价**。

### 4.1 用无障碍接口操控 Electron 应用

**问题**：QQNT 是 Electron（Chromium）应用，界面全是自绘的，窗口枚举拿不到任何控件。

**约束**：不许注入、不许 hook、不许逆向。

**做法**：
1. QQ 必须以 `--force-renderer-accessibility` 启动，Chromium 才会把渲染树暴露成无障碍树。
2. 用 `uiautomation` 走 UIAutomation COM 接口遍历控件树，靠 **ClassName / AutomationId** 定位锚点：

| 锚点 | 实际类名 | 用途 |
|---|---|---|
| 消息列表 | `ml-list` | 读消息 |
| 单条消息 | `ml-item` | 逐条读 |
| 输入框 | `ExEditor-qq-msg-editor` | 写入 |
| 发送按钮 | `send-msg` / `send--disabled` | 发送 / 判断可用态 |
| 会话标题 | `chat-header__contact-name` | 身份复核 |
| 方向标记 | `container--self` / `container--others` | 判断消息是谁发的 |

**证据**：`archive/probe.py` + `archive/probe-tree.txt`（2026-09-11 对本机 QQNT 的全量控件树导出）。
`agent.py:1493` 起的常量表，注释里写明"全部来自 probe.py 的实测"。

**代价**：类名是 QQ 的实现细节，**QQ 升级可能改**。所以锚点全部集中定义、且有体检项
（`app/diagnose.py`）能在启动前发现"锚点找不到"。

---

### 4.2 免前台能力边界（这个项目最关键的一次实测）

**问题**：自动化操作会抢用户的前台焦点，打断用户正在做的事。

**做法 / 结论**（逐条实测得出，不是推断）：

| 操作 | 需要前台吗 | 依据 |
|---|---|---|
| 读消息 / 读标题 / 读签名 | **不需要**（最小化也能读） | `archive/probe_minimized.py`：最小化后控件数/会话数/消息数完全一致 —— 读的是 a11y **缓存** |
| 切换会话 | **不需要** | `archive/probe_switch_nofg.py`：会话列表项支持 `InvokePattern`，`Invoke()` 不受前台影响 |
| 用 `InvokePattern` 点发送按钮 | **不需要** | 同上 |
| **把文字写进输入框** | ⚠️ **必须** | 剪贴板 + 按键这条路要求窗口在前台 |

**所以设计成**：只有"写文本"这一步抢前台，写完**立刻把前台还给用户原来的窗口**（方案 C）。
模型调用（1~3 秒）刻意放在抢前台的临界区**之外**。

**证据**：`agent.py` 的 `type_text()` 文档注释详细记录了这个边界；
`archive/bench.py` 实测读取 ≈103ms。

**代价（诚实记录）**：窗口**最小化**时 `Invoke()` 会**静默失效**（Chromium 节流 renderer），
所以切会话前会把窗口从最小化还原 —— 这会产生一次可见的窗口变化。
彻底解决办法是 CDP 的 `Input.insertText`（免前台写入），**已探通未落地**。

### 4.3 往 `contenteditable` 写字的可靠通路

**问题**：`SendKeys` 打不出中文；逐字符模拟会丢字。

**做法**：
1. 用 `pyperclip` / 原生剪贴板 API（`OpenClipboard` + `SetClipboardData`）写入 CF_UNICODETEXT；
2. `Ctrl+V` 粘贴；
3. **回读输入框**（UIA 读文本）确认写进去的确实是我们要发的内容。

**中途踩到并修掉的坑（都是实跑暴露的）**：

| 坑 | 症状 | 修法 |
|---|---|---|
| 先清空再写剪贴板 | 剪贴板失败时**输入框原有内容已被毁** | 调换顺序：**先写剪贴板（无副作用），再清空** |
| 回读做原始字符串比较 | 模型输出带空行分段时，编辑器回读拿不到段间 `\n` → 校验**永远失败** → 每轮重贴 → **重试到第 224 次、卡两小时** | 改成**归一化空白后比较**（错字/截断仍然拦得住） |
| 空行被吃掉 | 发出的消息少了段落空行 | 接受这个代价并在日志里说明 —— **少一个空行远好过两小时发不出去** |

**证据**：`test_errors.py §14`（输入框安全性）、`§20`（活锁与误报）；
回读判据用真实现场文本验证过：旧判据 `False` → 新判据 `True`，而**错字/截断/空输入框仍然 `False`**。

### 4.4 窗口不可见时无障碍树会冻结 —— 怎么判定

**问题**：Chromium 在窗口被最小化/完全遮挡时会节流渲染，此时 a11y 树**停止更新**，
但**不报错**。表现是"对方发了消息，程序没反应"。

**难点**：光看消息列表**永远分不出来**"读不到"和"对方没发"。

**做法：两条独立通路交叉验证。**

会话列表（左栏）和消息区（`ml-list` 子树）是**两棵独立更新的子树**：

| 消息区 | 会话列表那一行 | 结论 |
|---|---|---|
| 有新条目 | —— | 读取正常 |
| 无新条目 | 摘要/未读**也没变** | 对方真的没发（或整棵树都陈旧） |
| 无新条目 | 摘要/未读**变了** | **消息区 a11y 树被冻结** → 让窗口真的可见 |

**证据**：`--watch` 实时读取监视器（只读，不发送）实现了这个三向交叉验证；
`EXE使用说明.md §8.1` 有完整的分诊表。

**代价**：需要用户配合（跑监视器时去 QQ 里发一条消息）。这是**诊断工具**，不是常驻逻辑。

### 4.5 桌面端只给"最新一条摘要"：双路径读取 + 降级方案

**问题**：QQ 桌面版的每个会话在列表上**只暴露最新一条消息的节选**。
想拿到完整上下文，必须先把那个会话切过去。

**约束**：切会话 = 操作界面 = 慢（1~3 秒）、要串行。

**做法：把"发现"和"读正文"拆成两步，两条路径分工。**

```
当前打开的会话 → 实时路径：step() → read_messages() → split_new() → 去抖聚合 → 入队
其它会话      → 发现路径：discover()（只扫列表）→ 占位排队（不读正文）
                              ↓ 排到时才
                         prepare()：切过去 → 一次读全 → 生成
```

关键设计：
- **发现阶段只占位不读正文** —— 因为手上只有摘要，分不清"对方又发了一句"和"同一批消息重渲染"，宁可少回一次；
- **`unread_hint`（会话项上的未读数字）是这条降级路径唯一能用的线索** —— 首次访问某会话时用它决定"保留最后几条本次处理"；
- **两阶段拆分让模型调用不占前台临界区**：准备（读+生成）可以提前做，排到风控额度再发。

**证据**：`test_discovery.py`（43 项）专测这条路；`agent.py` 里 `discover()` / `_read_into_history()` / `prepare()` 的文档注释写明了取舍。

### 4.6 绝不丢消息（本项目最花心思的一块）

**问题**：一条回复生成后、发出去之前，中间有很多环节会失败。任何一个环节处理不当，
结果都是**"这条消息永远没有人回"** —— 而对方在 QQ 那边只看到已读不回。

**做法：把"已生成的回复"当成一等公民，全程可恢复。**

| 机制 | 作用 |
|---|---|
| **回复一旦生成就冻结** | `item.reply` 不再被清空；`prepared=True` 后不重新生成（省模型调用，且内容不会变） |
| **立刻落盘** | `state/pending-replies.json`；进程崩溃/重启后恢复继续发 |
| **草稿 = 可恢复的进度** | 写进输入框后若发送失败，**保留草稿**；重试走 `send_text(resume=True)`，检测到草稿还在就**跳过重新粘贴**，只做校验 + 触发发送 |
| **迟到消息结转** | 回复生成**之后**才到的消息**不并入**这一条（那句话是按旧内容写好的），而是记进 `late` 桶；等老的发完，**新建一条**并做一次完整重读 |
| **排序表达承诺优先级** | 队列把"已定稿待发"的项排在前面 —— **挤压时先发老的** |
| **退避阶梯，但永不放弃** | 失败 1~8 次：约 2s → 5s → 15s → 30s → 1min → 2min → 5min → **10min**，之后保持 10 分钟一次；**不丢弃** |

**刻意选择的取舍（要主动说明）**：

1. **宁可重复，不可丢失**：落盘在"发送之前"。若进程恰好在"已触发发送"与"标记成功"之间被杀，
   重启会重发一次 → 极端情况下多一条重复消息。这是有意选的。
2. **清空上下文时连带丢弃待发回复**：这是冲突（"不丢消息" vs "忘记"），
   解决方式是**用户指令优先 + 明确告知**（打印被丢弃的内容与原因），不静默处理。

**证据**：`test_errors.py §15`（不丢回复，22 项）、`§18`（掩码回归）、`§19`（彻底清理）、
`reply_queue.py --selftest`（68 项，含 `dump_state`/`load_state` 往返）。

**仍未解决的一处（诚实列出）**：`Invoke()` 返回成功但消息**实际没发出去**的"假成功"
目前检测不出来。真正的解法是**发送后回读消息列表校验**，
但它需要仔细设计（读得太早会误判失败 → 触发重复发送）。已记为下一步。

### 4.7 绝不发错人

**问题**：目标是"跟朋友聊天"，**发错人**的后果比"没回"严重得多。
而桌面 UI 上，"当前打开的是哪个会话"随时可能因为用户手动点击而改变。

**做法：三次校验 + 捕获签名。**

```
type_text          ← 抢前台写入
wait_send_enabled  ← 免前台，等按钮恢复
回读输入框          ← 免前台，确认写进去的就是我们要发的内容
guard()            ← 免前台，复核「现在打开的还是不是那个会话」（比标题更严：签名）
Invoke 发送按钮     ← 免前台
```

**第三道闸的关键**：写入前捕获"会话签名"（标题 + 消息条数 + 末条指纹），
写入后再取一次，**两者必须完全一致**。它挡的是「模型生成期间，人手动切了会话」
—— 那时 `InvokePattern` 会把这段文字发到**另一个会话**的输入框里。

**身份复核用 QQ 号而不是昵称**：昵称可以重名、可以改备注；QQ 号不会。
拿不到号时降级为只校验标题，并**明确记一条 WARN**（降级要可见）。

**证据**：`test_send_guard.py`（真机，175 行）实测这三道闸；
`agent.py:3880` `deliver()` 的文档注释。

### 4.8 可诊断性：73 条错误码 + 反假诊断

**问题**：这个项目的失败模式大量是"**看起来一样的**"——
"读不到"和"没消息"看起来一样，"发送失败"和"没触发"看起来一样。
如果报错只给一句"失败了"，排查成本全部落在用户身上。

**做法：一条码 = 一个根因 + 可执行的抓手。**

```
python -X utf8 error_codes.py     # 目录自检 + 按域统计
```

| 域 | 条数 | 覆盖 |
|---|---|---|
| CFG 配置 | 7 | 密钥缺失、格式错误、非 ASCII 字符 |
| ENV 环境与启动 | 8 | 管理员权限、锁屏、数据目录不可写 |
| FG 前台与焦点 | 4 | 抢不到前台、归还失败 |
| LLM 模型接入 | 12 | 鉴权 / 限流 / 超时 / 空回复 / 编码错误 / 未分类 |
| PATH 路径与磁盘 | 3 | 落盘失败、文件损坏 |
| PROC 进程与任务 | 7 | 常驻冲突、子进程退出、单轮超时 |
| QQ QQ 发现与准入 | 7 | 找不到窗口、无障碍未生效、锚点缺失 |
| READ 消息读取与准入 | 2 | 读到但全被跳过、会话覆盖不全 |
| SEND 发送链路 | 16 | 剪贴板、按钮未恢复、回读不符、签名变化、撤单、草稿保留 |
| UIA 无障碍接口 | 4 | COM 线程、调用超时、Pattern 不可用 |
| WEB 控制台服务 | 3 | 端口、令牌、请求异常 |

**四条硬规则（都有回归测试守着）**：

1. **一个错误码只对应一个根因**，`fixes` 必须给**可执行的抓手**（界面元素名 / 路径 / 命令 / 明确动词），不写成解释。
2. **兜底码不得断言具体根因** —— 任何"未分类异常"都落到中性的 `E-LLM-012`，
   而不是硬套成 `E-LLM-002「连不上接口」`。
   *（现场事故：密钥里混进中文导致 `UnicodeEncodeError`，被误报成"网络不通"，
   给出六条全是错的建议 —— **假诊断比不报错更坏**。）*
3. **失败之后不得再报一条互相矛盾的后续错误** —— 根因已报过时，只留一句不含码的"后果"说明。
4. **报错抑制** —— 常驻循环每 0.8s 一轮，持续性故障会秒刷屏。同一码 60 秒内只完整报一次。

**证据**：`test_errors.py`（252 项）里的 `§17 不许假诊断`、`§16 静态体检`（pyflakes 未定义名 +
tokenize 注释扫描）、`§11 源码里不许有无码的失败`（源码扫描会拦住裸 `log("ERR", ...)`）。

## 7. 工程约定（硬性，改动前先读）

1. **路径解析只有一个事实来源**：`QQ_AGENT_HOME → exe 目录 → 源码目录`；
   其它模块引用它，**绝不各自重算 `__file__`**；相对路径一律按数据目录解析，**不看 CWD**。
2. **密钥三文件分离**，API Key 绝不写进 `config.json`，接口只回掩码。
3. **全进程只有一条线程碰 UIA**（`CUIAutomation` 是进程级单例，跨线程会静默返空）。
4. **停止常驻用哨兵文件** `state/STOP`，不用 Ctrl+C。
5. **会碰 QQ 的任务必须串行**，常驻运行时一律禁用。
6. **纯 ctypes 调用一律显式声明 `argtypes` / `restype`**（64 位句柄截断是静默的）。
7. **改完必须跑**：`test_errors.py` + `test_ui.py` + 重新 `build.bat` + `test_exe.py`。
8. **一个错误码只对应一个根因**，新增报错必须走 `report()` / `E.envelope()`，
   不允许裸 `log("ERR", "失败了")` —— 有源码扫描守着。

## 附：本次审查发现的、值得记进汇报「踩坑」环节的三个案例

这三个都是**实跑暴露、靠推理发现不了**的问题，也是最能说明工程成熟度的材料：

| 案例 | 表面症状 | 真实原因 | 教训 |
|---|---|---|---|
