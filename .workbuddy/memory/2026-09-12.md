## 00:0x–00:2x · 错误体系：一个码只对应一个根因

### 起点

用户要求：「确保所有可能出现的问题都有完善的对应报错反馈，避免报错混淆，帮助精准定位」。

排查后发现，真正的混淆源不是「报错太少」，而是**一句话覆盖多个根因**。
最典型的一句在 `run_forever` 里：

```
找不到 QQ 窗口。请确认 QQ 已启动，且带 --force-renderer-accessibility 参数。
```

它同时压在三个根因上，而处理动作完全不同：

| 真实根因 | 正确动作 | 按那句话去做的后果 |
|---|---|---|
| QQ 没启动 | 启动 QQ | 无损失 |
| QQ 在跑但窗口缩在托盘/最小化 | 把窗口显示出来 | **白重启一次，正在输入的文字会丢** |
| 窗口可见但无障碍没生效 | 完全退出后带参重启 | 白折腾 |

报错混淆的代价是**把人引向错误的修复动作**，比没有报错更坏。

### 本轮抓到的真问题（都是检查项自己抓出来的）

1. **`resolve_api_key` 依赖当前工作目录**（最值钱的一条）。原写法：
   ```python

       path = abs_here(path)
   ```
   「CWD 下刚好存在同名文件」时会优先用 CWD 那个 → 从项目目录启动读到项目里的密钥，
   从别处启动读到别的（或读不到）。表现为「同样配置换个目录结果就不一样」。

2. **8 处「说了失败但没给码」**的降级报错（上下文损坏/落盘失败、清理草稿、OCR、刷新指纹、扫会话列表、收尾三步）。

5. 3 条过于笼统的 `fixes`（写成了解释而不是动作）。

### 两条防回归检查（会随代码增长自动生效）

## 19:1x–19:2x · 现场反馈：「当前会话的新消息捕获不到」

### 用户报告

在 VM 上跑，**当前打开的会话收不到新消息**（无回应）。用户的猜想是「此 bug 是否以
当前会话为触发条件」，并给了 QQ 内的实际会话（含刻意的「重复发同样内容」测试）。
我无法读图（当前模型不支持图像输入），所以从代码结构 + 症状入手。

### 结构上确认了用户的猜想方向

两条路径分工明确，代码里就写着：

```
当前打开的会话 → 实时路径  step() → read_messages() → split_new() → _ingest() → _admit()
其它会话      → 发现路径  discover()（扫会话列表）→ 占位 → prepare() → _read_into_history()
```

`discover()` 里有 `if cur_title and s.display_name == cur_title: continue`（agent.py 跳过当前会话，
注释写明「已打开的会话交给 step() 的实时路径」）。**所以「只有当前会话收不到」指向的必然是实时路径。**

### 找到的真实缺陷：实时路径会**静默**丢消息

`_admit` 对拒收只返回一个短句，而「方向判反」那一支是 `return [], ""` ——
**连短句都没有**。于是：

    「对方发了消息但被判成自己发的」→ 被悄悄扔掉 → 日志里一个字都不出现
    → 与「对方根本没发消息」在日志上**完全无法区分** → 只能靠猜

这就是本类问题难查的根源。已修：

| 改动 | 效果 |
|---|---|
| `_admit` 拒收一律给原因，原因里**直接写验证方法** | 日志里出现 `SKIP 方向判定为『me』…跑一次「只读诊断」核对【我方】/【对方】` |
| 新增 `Agent._report_round()` | 本轮读到 N 条但一条没收下 → 报 `E-READ-001` 并列出**原因分布** |
| 心跳加 `read / fresh / skipped` 三个计数 | 界面「常驻运行」卡片直接显示；三者不相等就要留意；还加了一条 warn 提示条 |
| 新增 `E-READ-001` / `E-READ-002` + 新域 `READ`（消息读取与准入） | 错误码 61 → 63 |

### 新增 `--watch` 实时读取监视器（只读，控制台里也有按钮）

专门回答「新消息到底有没有被读到」。启动后提示用户**去 QQ 里发一条消息**，
1 秒内应看到 `★ 新增 1 条` 并打出【我方】/【对方】+ key + 正文。三重交叉验证：

1. **方向对照** —— 新条目显示【我方】即方向判反（常驻会跳过）。
2. **key 稳定性** —— 同一段正文换出不同 key ⇒ 消息 ID 读不到、退化成内容指纹兜底
   ⇒ **重复发同样的话会被当成同一条静默丢弃**。用户的测试恰好是「重复发消息」，
   这条检查就是冲它去的。
3. **与会话列表交叉验证** —— 会话列表那一行（摘要/未读）是**另一条独立读取通路**。
   它变了而消息区没读到新条目 ⇒ **消息区 a11y 树被冻结**（QQ 窗口被最小化/完全遮挡，
   Chromium 节流渲染），而左栏还在更新。单看消息列表永远分不出这两种情况。

## 19:24–19:30 · 现场反馈②：「心跳已停更 1min+」—— 一个**必然误报**

用户问：经常看到「心跳已停更 1min+」，可能是什么问题？与 VM 性能有关吗？

### 结论：主因不是 VM，是我的阈值写错了

可证的设计缺陷，两条数字一摆就成立：

| 事实 | 值 |
|---|---|
| 心跳只在**整轮循环结束时**写一次 | —— |
| `supervisor.heartbeat()` 的 stale 阈值 | **硬编码 30s** |
| `llm.timeout_seconds` 默认 | **60s** |
| `prepare()` 里的模型调用 | **同步跑在主循环线程上** |

⇒ 只要一次模型调用超过 30s（含卡到 60s 超时），界面**必然**弹出「心跳已停更，进程可能卡住了」。
不是故障征兆，而是设计与实际耗时脱钩。而且它把人往错误方向带（去重启一个健康的进程）。

### 关键认识：「不占前台」≠「不阻塞循环」

`prepare()` 里原本写着注释「模型调用（不占前台；故意放在 UI 临界区之外）」。
这句话没错，但只解决了**前台争用**，没解决**主循环阻塞** ——
模型调用期间既不读消息、也不写心跳。这同时解释了上一个 bug 的一部分：
一段慢的模型调用会让当前会话的新消息在最长 60s 内完全不被读取。

### 修法：心跳带「阶段」，阈值改用该阶段自己的上限

`agent.set_phase(name, budget)` 在每个慢阶段入口写三样东西：

```
phase          现在在哪一步        → 界面「调模型　已 42s」
phase_since    这一步从何时开始
stale_after    这一步的合理上限    → 取代硬编码的 30s
+ prev_phase / prev_phase_seconds / phase_stats → 界面「各阶段耗时排行」
```

各阶段上限：调模型 = `llm.timeout+15`；发送/扫列表 = 30；读消息 = 20；空闲 = `轮询间隔+15`。
`supervisor.heartbeat()` 只负责用 `stale_after`，不再自己拍一个数（缺字段时退回 30s 兼容旧心跳）。

新增 `E-PROC-007`（单轮耗时远超轮询间隔，带阶段/耗时/CPU 核数），错误码 63 → **64**。

### 顺带解决「是不是 VM 太慢」这个问法

新增的**各阶段耗时排行**（平均/最大/次数）就是直接证据：

- 慢在「调模型」→ 接口问题，不是 VM；日志里会有 `E-LLM-003` 超时
- 慢在「读消息 / 扫会话列表」→ 才是虚拟机 CPU 或渲染问题（UIA 是跨进程 COM 调用）
- 阶段名长时间不变且超过它自己的上限 → 真的卡住

VM 确实是**放大器**而非主因：1 vCPU 时 QQ(Electron) 与 Python 抢核；控制台窗口被关掉
会让 Chromium 节流渲染；而**虚拟机被挂起/暂停**（宿主机睡眠）会让心跳停更几分钟，
恢复后一次性追上来 —— 这一条才是真正的"虚拟机问题"。建议 2 vCPU + 4GB 起步。

### 验证

| 测试 | 结果 |
|---|---|
| `test_errors.py` | **132 / 0**（新增 §13 心跳阶段感知 21 条） |
| `test_ui.py` / `test_exe.py` / `test_text_port` / `test_discovery` | 104 / 45 / 57 / 43，全 0 失败 |
| exe 内自检 | 「64 条错误码，目录自检通过」 |

文档：`EXE使用说明.md` 新增 §8.2；`README.md` 新增「心跳：为什么它必须带上『阶段』」。

## 19:32–19:36 · 现场反馈③：盯着 VM 界面观察到的「粘贴又删掉」

### 用户观察

> agent 呼出 QQ 界面后，复制粘贴了一段文字，并返还了前台焦点，并再次呼出了 QQ，
> 却将输入框内未发出的文字删掉了。

### 定位：这是 `_abort_cleanup`（中止发送后的清理），不是错乱

完整因果链：`type_text` 抢前台 → 粘贴 → `_release_foreground` 归还 →
发送前某道闸没过（E-SEND-002/003/006）→ 本条作废 → 清理"已经粘进去的那句话"
→ 用户看到第二次呼出 + 删除。

**但原实现有一条我承认错了的设计**：清理时若 QQ 不在前台，会 `force_foreground`
把它抬起来再删。这等于把「用完即还焦点」的承诺撕了 —— 用户被打扰**两次**，
第二次纯破坏性；**万一用户此刻正在输入，被删掉的就是他自己的字**。

### 修掉的三件事

**① 先做无副作用的检查，再做有副作用的动作**（`type_text` 顺序反了）

```python
# 改前：clear_editor() → copy_to_clipboard()
#   → 剪贴板若失败，输入框原有内容（可能是用户打了一半的话）已被 Ctrl+A/Delete 毁掉
# 改后：copy_to_clipboard() 是纯内存操作、零副作用，所以提前；确认成功才清空
```

**② 清理改为「按打扰程度三级降级」**

| 级别 | 手段 | 抢前台？ |
|---|---|---|
| ① | `clear_editor_uia()` = `ValuePattern.SetValue("")` | 否 |
| ② | QQ 恰好还在前台 → 键盘清掉 | 否（本来就在） |
| ③ | 都不可用 → **保留草稿** + 报 `E-SEND-011`（带草稿内容） | **绝不**为了擦草稿再抢一次 |

第 ③ 种是刻意的取舍：留一段**看得见的**草稿（人就坐在电脑前，一眼能看到、顺手删掉）
远好过偷偷抢走焦点再删一次。这条也写进了错误码的 fixes 里。

**③ 「慢」要当成一等公民，而不是当成失败**

`wait_send_enabled` 原来硬编码 1 秒。慢速虚拟机上 QQ 同步按钮状态经常超过 1 秒 →
「粘贴成功 → 按钮没恢复 → 判成失败 → 中止 + 清理」→ 用户看到的就是这种无意义动作。
改成可配的 `chat.send_button_wait_seconds`，默认 **3 秒**
（`agent.DEFAULTS` / `settings._LOCAL_DEFAULTS` / `FIELDS` 三处同步，漂移测试守着）。

新增错误码 `E-SEND-010`（作废+已清理，info 级）与 `E-SEND-011`（留下草稿，warn 级），
错误码 64 → **66**。

### 教训（值得记住）

这三个问题**在源码里看着都"合理"**，只有盯着界面观察才会暴露：
顺序问题要想到"失败时留下什么状态"，抢前台问题要意识到"承诺是连续的、
不能一步按需违背"，超时问题要意识到"慢 ≠ 失败"。
所以都写进了 `EXE使用说明.md §8.3`，让下一个人不必再看一遍才明白。

## 19:48–20:0x · 策略反转：VM 场景下「绝不丢消息」成为最高目标

### 用户定的新方向

> 选定了 VM 环境作为应用场景，打扰就不再是问题。问题在于：未被回复的消息对应的回复
> 意外被删，导致部分消息永远不再被回应。所以：不删掉本应发出的消息；出现挤压或
> 后来补上的消息，也要**先发出本应发出但未发出的**，尽可能避免消息丢失。

即：**成本函数换了**。之前我把「打扰/误发」当主要成本，做的三处取舍现在全成了 bug。

### 反转的三处（每一处都会导致「那批消息永远没人回」）

| 原行为 | 为什么错 | 现在 |
|---|---|---|
| 中止时**删掉**输入框草稿 | 删的就是一条已写好的回复 | **保留**（`E-SEND-012`），队列拿同一条继续重试 |
| 重排时 `item.reply = ""` | 白花一次模型调用，内容还会变 | **保留回复**，只重试**发送**，不重新生成 |
| `attempts >= max_attempts` → `drop(aborted=True)` | 那批消息**永远没有回应** | **不撤单**，长退避重试（`E-SEND-013`） |
| 队列只在内存里 | 重启即丢；而那批消息的正文已写进上下文并被标为已读，不会再被认成新消息 | **落盘** `state/pending-replies.json`，启动恢复（`E-SEND-015`） |

另外两处"间接丢消息"也修了：

- `ensure_pending` 原来在「发现该会话又有新动静」时**作废已生成的回复** → 改为记进 `late` 桶。
- `offer_followup` 原来允许把新消息 append 进 `texts`，**即使这条已定稿** —— 那句回复是按旧内容
  写好的，并进去等于「新消息事实上没被回应」→ 定稿项返回 `deferred`，新消息进 `late`。

### 设计要点

**① 回复一旦生成就冻结**，并立刻落盘（`_save_pending()`）：
从那一刻起「这条回复必须被送出去」，失败只是让它多等一会儿。

**② 输入框里的草稿 = 可恢复的进度** → 新增 `send_text(resume=True)`：
若输入框里仍是那句话，**跳过重新粘贴**，直接校验 + Invoke。重试路径缩到最短。
草稿不在了才退回完整流程（报 `E-SEND-014`）。

**③ 迟到消息结转**（`_carry_over`）：定稿之后到的消息记进 `late`，等老的发完，
用 `submit` 新建一条并 `pending_read=True`（做一次完整重读，把迟到的和期间新来的一起读全）。
守卫用「同 scope 且不是自己」——`get(scope)` 不行，它返回列表第一条，可能就是这个 item 自己。

**④ 挤压时先发老的**：`pick()` 排序改为
`(2 if fail_count>=3 else (0 if frozen else 1), first_at, seq)`。
`fail_count>=3` 那一档是**降权但不丢弃**：一条永远发不出去的项不能霸占循环饿死其它会话。

**⑤ 堵掉最后一处撤单路径**：`prepare` 在「总读取没拿到新消息」时会 drop；
若这一条 `has_late`，改为 `requeue` 重读一遍，而不是丢掉。

### 顺带改的两个默认值

- `uia.restore_foreground`: true → **false**。不归还就没有「抢不到前台」这类失败
  （`E-FG-001/002`），发送链路更可靠；专用虚拟机上让 QQ 一直留在前台更稳。
  自己每天用的电脑上要改回 true。
- 新增 `chat.keep_draft_on_abort` = **true**。

### 已知的取舍与剩余缺口

- **宁可重复，不可丢失**：落盘在发送**之前**。若进程恰在 Invoke 之后、标记成功之前被杀，
  重启会重发一次 → 极端情况下出现一条重复消息。这是刻意选的。
- **剩余缺口（未做）**：`Invoke()` 返回成功但消息实际没出去的「假成功」仍无法检出 ——
  真正的解法是**发送后回读消息列表做校验**。它需要仔细设计（读得太早会误判失败→重复发送），
  本次未动，记为下一步。

**跟网络毫无关系。**

  并在 fixes 里明确写「这不是网络问题」；
- 兜底改到中性的 `E-LLM-012「调用模型时出现未分类异常」`，标题不断言根因，
  并在 fixes 里声明「能确定的网络错误会各自报 E-LLM-002/003」。

**② 失败之后又报一条互相矛盾的后续错误。**
`prepare` 里在 `reply` 为空时无条件报 `E-LLM-009「模型返回空内容」`，

修：`generate_reply` 记下 `self._last_gen_fail`；`prepare` 只在**根因没报过**时才报 E-LLM-009，

**③ 顺带在保存时就拦住**（`settings.validate`）：非 ASCII 的 Key/地址直接拒绝保存并指出位置，
不让它进配置文件。

守住两条原则：
- **兜底码的标题不得断言具体根因**（含一条源码检查：agent.py 里不许再出现

## 22:38 · 补记：**真正的根因找到了，而且是个数据丢失 bug**

上一节把「报错分类」修好了，但当时**根因还没定**。写回归测试时被自己的新检查
绊了一下——它把"掩码"当成了真密钥，于是顺着查下去，发现了最初的一环：

```python
# app/settings.py
def _mask(key):        return f"{key[:4]}{'•'*8}{key[-4:]}"   # 例：sk-1••••••••ghij
def _is_mask(value):   return set(value) <= set("•")          # ← 只认「全是 •」
```

`_is_mask(mask)` → **False**（掩码首尾各带着真密钥的 4 个字符）。

### 完整因果链（三处 bug 叠在一起）

```
① _is_mask 判据错 → 掩码被判成「用户真的填了 key」
② 保存设置时把掩码写进 secrets.local.json → **真实密钥被覆盖**（数据丢失）
③ 之后用这个假密钥调模型 → UnicodeEncodeError: latin-1 position 11-18
④ 我的兜底又把它报成「E-LLM-002 连不上模型接口」→ 假诊断，把人引向网络
```

**位置对得上**：`"Bearer "` 占 7 个字符，掩码前面 4 个真字符 → 那 8 个 `•` 正好落在
位置 11~18。实测复现：

```
Authorization 头 = Bearer sk-1••••••••ghij
非 ASCII 位置     = [11,12,13,14,15,16,17,18]    ← 与用户报的一模一样
```

所以用户看到的六行「网络不通 / DNS / 代理」建议，**全都指向错误方向**，
而正确动作只是「把密钥重新粘一遍」。

### 修复

1. `_is_mask` 判据改成「**出现 • 就当掩码**」——真密钥不会包含 U+2022。
2. 新增 `looks_like_mask()` 供诊断用（显式命名，避免又读错语义）。
3. `validate()`：若**已存**的密钥本身是掩码 → 直接报 `E-LLM-011` 并点明是哪个文件，
   让用户知道要重填（这正是用户当时的处境）。
4. `check_ascii_for_header()`：值里出现 `•` 时，直接说「这是掩码不是真密钥，
   是旧版 bug 把真密钥覆盖了」，并给出 U+2022 指纹。
5. 新增 **§18 回归测试**（15 条）钉住整条链路，特别是
   「**保存设置不得改动已存的密钥**」这一条 —— 那才是数据丢失本身。

### 教训

- **一个「判据太窄」的小函数，可以造成数据丢失。** `set(value) <= set("•")`
  看起来只是"判断得严格一点"，实际后果是**用掩码覆盖了真密钥**。
  凡是「判断输入是不是占位符」的逻辑，都要按**最宽**的形态认（宁可漏判成占位符，
  也不要误判成真数据）——因为两种错法的代价完全不对称。
- **界面上显示的东西，绝不能被当成用户输入回写。** 掩码是"给人看的"，
  一旦它有机会走回存储路径，就等于拿显示器上的字覆盖硬盘。
  现在 `_mask` 里保留首尾 4 位只是可读性考虑，但正因如此它"看起来像密钥"，
  更需要判据兜住。
- **假诊断会掩盖真根因**：如果没有这条回归测试，我可能就停在「修好了报错分类」，
  而用户的密钥仍然是坏的。

→ 这不是"重新读了上下文"，而是**一条基于旧上下文生成、当时没发出去的回复，

### 两条通道，都要堵

**通道一：`forget` 只认会话键，而界面写的是「会话名或片段」**

```python

hits = [s for s in names if exact or target in s]
```
用户按昵称「光みつる」/「测试目标A」输入 → **什么都匹配不到** → 只打印一句

**通道二：待发回复没被清**

`forget()` 只调 `store.forget(scope)`，**不管** `state/pending-replies.json`。
那条回复的前提已被抹掉，但重启后 `_load_pending()` 仍会恢复并发送。

### 修复

`forget()` 改成「彻底忘记」三样一起清，并**显式打印**：

| 清什么 | 不清的后果 |
|---|---|
| 会话上下文 | 等于没清 |
| 基于该上下文生成、还没发出的回复 | 重启后照原样发出，像是没清干净 |
| 轮转状态（基线标记 + 指纹快照） | 「发现」路径的指纹比对还指着旧内容 |

- 新增 `pending_path()`（提到模块级，供 forget 复用）与 `drop_pending_for_scope()`；

- 匹配不到时列出「会话键 ↔ 昵称 ↔ 上下文条数」对照表；
- 输出末尾补上「QQ 界面上的历史仍在屏幕上；若是被『发现』路径处理的会话，
  未读数字会让最后几条被重新读进来 —— 想彻底干净先点掉未读」这个**第三条通道**；
- UI 任务改名为「彻底忘记某会话」，描述/参数提示/二次确认都按真实行为重写
  （原参数提示「会话名或片段」→「昵称或会话键」）。

### 与「绝不丢消息」的冲突，必须显式

清空上下文是用户的明确指令，优先级高于"保留待发回复"。

## （9-14 22:55）现场反馈⑦：三连问题 —— 多行文本活锁 / 永不放弃 / 误报

> 注：这条是 09-14 22:55 收到的日志，按项目习惯补记在 09-12 日志之后。

### 用户给的日志（关键三处）

```
QUE '测试群B' 未发出，保持原回复原地重试（第 218 次失败｜E-SEND-012｜草稿已不在，将重新写入）
  …每 ~30 秒一次，一直涨到第 224 次（将近两小时）
ERR E-SEND-003 输入框回读与预期不符
  现场数据：期望=…）⏎⏎……我听见了。…  实际=…）……我听见了。童声…
WARN E-READ-001 读到了新消息，但一条都没进入上下文
  现场数据：跳过原因分布=方向判定为『me』×1  会话=group:963650468  方向可疑=是
  发送者=Susurrrus-本人（**就是机器人自己**）
```

### 问题一：多行文本让回读校验永久失败 → 无限重试（根因）

**看「期望」和「实际」的差别**：期望里是 `）⏎⏎……`（含空行），实际是 `）……`。

QQ 编辑器是 contenteditable，**段落是各自独立的节点**，`collect_texts()` 按节点拼文本、
段间不补 `\n`。所以模型输出里的空行分段在回读时**必然**对不上 → 原始子串比较**永远 False**。

后果不止"那一条发不出去"：`editor_contains()` 用的是**同一个判据**（判断"草稿还在不在"），
于是每次都判"不在" → 每轮都重新粘贴 → 又失败 → **活锁**（第 224 次）。

修：新增 `norm_text()` / `text_matches()`，回读与 `editor_contains` 都改成
**归一化空白后比较**。新增一条 INFO 说明"仅在空白/换行上有差异"。

**安全性没被削弱**（测过）：写错一个字 / 被截断 / 空输入框 / 完全不相干 → 仍然拒绝。
取舍明确：**少一个空行，远好过两小时发不出去。**

### 问题二：「绝不丢消息」被写成了「永不放弃且不减速」

`_retry_delay` 原来是 `min(max_hold, base*(1+fail_count*1.5))` —— 上限只有 30 秒。
一条过不去的项于是每 30 秒重试一次，把日志刷满两小时。
而且 `E-SEND-013`（"有一条反复发不出去"）**定义了却从未被触发**，
所以那份日志里**没有任何一行**说明"有一条卡住了两小时"。

修：
- 退避改**阶梯**：`[2, 5, 15, 30, 60, 120, 300, 600]` 秒。前几次仍然快（瞬时故障自愈），
  之后拉到 10 分钟一次。**仍然不丢弃**。
- 新增 `_note_stuck()`：第 5 次失败报一次 `E-SEND-013`，之后每 20 次再报一次
  （带会话/次数/最后原因/回复开头/草稿是否还在）。

### 问题三：`E-READ-001` 误报 —— 自己发的消息被当成"方向判反"

刚发完一条回复，下一轮就会把我们自己那条读回来（`direction=me`、发送者就是机器人）。
`_report_round` 把它算成"读到但一条都没进上下文"，于是**每发一条消息就误报一次
方向判反** —— 指向完全错误的方向。

根因是信息不足：光看 `direction == "me"` 分不清两件事 ——
「有明确证据是我自己发的」vs「靠头像位置猜的」。

修：
- `Message` 新增 `dir_src`（`class` / `nick` / `position` / `last_only` / `default` / `ocr`），
  `_parse_item` 在判定方向时一并记录依据。
- `_admit` 据此分两种跳过原因：`SKIP_SELF`（有证据）与「方向判定为『me』（位置推断）」（可疑）。
- `_report_round` 先剔掉 `SKIP_SELF` 再看有没有可疑项；全是自己发的就只记一条 INFO。
